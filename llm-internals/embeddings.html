Embeddings: Tokens Become Vectors

After this page you can trace exactly how a piece's row number becomes a list of numbers the model can multiply — and why "looking something up" is a multiply in disguise.

A row number is not a meaning

The last page ended on a warning, so start there. Row 15 and row 16 sit next to each other in the vocabulary — in the toy list, the pieces for "the" and "at" — and that adjacency means nothing [tokenization]. Ids are symbols, like jersey numbers: the arithmetic inside the model can multiply and add quantities, and a jersey number is not a quantity. If the model is to do anything with "the" beyond recognizing it, "the" has to arrive as numbers worth computing with — not one number, but a whole list of them, learned during training.

That is the entire trick of this page: replace each row number with its own personal list of numbers, and let the lists' patterns carry the meaning.

Lists of numbers

A vector is an ordered list of numbers — the model's unit of currency from here to the end of this manual. The dimension of a vector is how many entries it has (engineers also call the model's width d_model; both words mean the same thing here). Two entries give a point on a page; three, a point in a room; thousands, habits no picture can capture — but the algebra never changes.

What makes lists of numbers useful as meaning is that they can be compared numerically, and the workhorse comparison is the dot product: multiply the matching entries pairwise, then sum. It is the cheapest possible question you can ask about two vectors — "do your entries agree?" — and almost every mechanism in the rest of this manual is built out of it.

Worked example — dot products by hand

a = [ 1  2 ]
b = [ 3  4 ]
a . b = (1 x 3) + (2 x 4) = 11      (entries agree in sign and size)

c = [ -2  1 ]
a . c = -2 + 2 = 0                  (no net agreement — unrelated)

The reading: a large positive dot product means strong agreement, a dot product near zero means no relationship, and a negative one means opposition. During training, pieces that appear in similar contexts drift toward vectors with large mutual dot products — "similar meaning" in this manual always reduces to some version of that statement.

A dot product measures agreement along one direction at a time, and a wide vector holds many directions at once. Two pieces can agree along one stretch of their entries and disagree along another — near-twins by one measure, strangers by the next, with no conflict between those two verdicts. That is what width buys: each additional stretch of entries is another axis along which two pieces can be alike or unalike, independently of all the others. Whenever a later page says a mechanism compares two pieces, the comparison will be a dressed-up version of this multiply-and-sum.

The lookup table

Where do the pieces' vectors come from? One big learned table. The embedding matrix has one row per vocabulary entry, each row a vector of the model's width. The embedding of a piece is its row — and looking a piece up means copying that row out. Id 15 in, row 15 out: in the toy list, that is the piece for "the", copying out whatever numbers training has written there [tokenization]. Every parameter in this table is learned; before training, all rows are effectively random noise.

Now the disguise. A one-hot is a vector of zeros with a single one — a pointer with a one in the position of the thing pointed at. Multiply a one-hot by the table and you get exactly the pointed row back:

Worked example — lookup as a multiply

one-hot for id 2:      [ 0  0  1  0 ]

          [ 1  2  0 ]
table E = [ 3  1  1 ]
          [ 5  0  2 ]      <- row 2
          [ 0  4  3 ]

[ 0  0  1  0 ] @ E  =  [ 5  0  2 ]      (the row copy, done by multiply)

Why bother? Because it makes "select a row" and "multiply by a table" the same operation. A matrix multiply is just organized dot products: entry (i, j) of the result is the dot product of row i from the left matrix with column j from the right. The one-hot's zeros annihilate every row but one, and its single one copies that row through. To the hardware, the model's entire front door is one multiply — no special lookup circuitry anywhere.

Note

Scale check: GPT-3's table is 50,257 rows by 12,288 entries — about 617 million learned numbers in this one table [components], roughly a third of one percent of the whole model. The floors are where the rest lives.

The width is a design choice

How many entries should each row have? Wider vectors can hold more distinctions — more ways for two pieces to be similar along different aspects — but every multiply in the model costs proportionally more. Widths range from the low thousands to five digits: GPT-3 uses 12,288 entries per piece [model-configs]; Llama 3's eight-billion model uses 4,096 [model-configs] and spends the savings on more floors instead.

One rule is absolute: every table in a given model shares the same width. That is what lets one floor's output feed the next floor's input without any adapters — the whole model is a chain of operations on lists of the same length.

Width is also paid for out of the same budget of learned numbers as everything else. Make each row wider and the table's cost grows as vocabulary size times width; the same budget could instead buy more floors of processing. Designers therefore choose width, floor count, and vocabulary size together, as one joint trade — which is why finished models publish their full configuration alongside their weights: the configuration is the list of choices that rebuilds the machine exactly.

What runs through the floors

With lookup defined, the running picture: each piece becomes its row, and that row is then revised, floor by floor, all the way to the final score list. The hidden state is the working vector for one position — it starts as the piece's embedding and accumulates edits as it climbs. When you read "the model processes the text," picture a column of such vectors, one per piece, each being refined in parallel.

And when engineers need to talk about many of these at once, they reach for the general word: a tensor is a box of numbers with any number of axes — a vector is a one-axis tensor, a table a two-axis tensor, and one text's worth of hidden states is a grid of pieces by width. Stack several texts and a third axis appears. The word adds no machinery; it just lets "multiply these boxes of numbers" be said in one breath.

One habit will pay off for the rest of this manual: whenever a mechanism is described as doing something to one piece, read it as doing that thing to every piece's hidden state at once — the states stack into a grid, and the operation becomes one big multiply over the whole grid. The prose stays sequential because English is; the arithmetic is parallel because the hardware is. Every floor ahead is built in that style.

One property of everything built so far deserves a last look, because it is about to become a problem. Swap two pieces in the input and every lookup still returns the same rows — the front door is order-blind. "Dog bites man" and "man bites dog" enter as the same bag of vectors. The next page marks order onto them.

Takeaways

  • A vector is an ordered list of numbers — the model's unit of currency, compared by dot products.
  • Looking a piece up copies its row from the embedding matrix; a one-hot makes row-copying a matrix multiply, so the front door needs no special circuitry.
  • The width is a design trade: more entries per piece, more distinctions, proportionally more cost — and one shared width per model.
  • The hidden state is the per-position working vector, revised floor by floor from its embedding onward.
  • Everything so far is order-blind — swap two pieces and nothing notices. Next page: marking order.
