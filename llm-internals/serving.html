Serving: Batching, PagedAttention, FlashAttention

The last page left the card holding one conversation's keys and values and asked what a production system does when many arrive. This page is that system: how it keeps a GPU fed, why it slices caches into blocks, and what happens inside a single attention step.

One request, one starving GPU

Start from the floor the loop page derived. A decode step reads every weight once and produces one piece; on a 7B model that is roughly one unit of arithmetic per byte read, against a machine whose balance point sits at one hundred fifty to six hundred [serving]. The arithmetic units idle. The memory system runs flat out. One request, alone, wastes most of the card [serving].

The idle capacity has a source waiting outside: other requests. Run the same decode step for many requests at once and the weights are still read once — but now they serve a piece for each request in flight. The arithmetic per byte multiplies by the request count; the memory traffic stays put [serving]. This is batching — grouping requests so one weight sweep serves them all — and it is the founding trick of every serving system [serving].

The arithmetic of sharing, at three sizes [serving]:

Per-piece pace stays roughly flat — each request still gets its piece per step — while the tokens per second across all requests, the system's throughput, climb nearly linearly, until the step finally turns compute-bound [serving].

Keeping the batch full

Batching, done naively, has a hole. Collect a group of requests, run the whole group to completion, start the next: that is static batching, and it idles. Requests finish at different times — a two-line reply against a two-hundred-line one — and a finished request's slot sits empty until the slowest member of its group is done [serving].

The fix schedules at every step. Iteration-level scheduling runs the scheduler at every decode iteration — every piece-step — admitting new requests and evicting finished ones between steps; the vLLM engine calls it continuous batching [serving]. The slot empties at one step; a waiting request fills it at the next.

One wrinkle: the requests in a step no longer share shapes — each carries a cache of different length, so attention cannot run as one grouped operation. Orca's answer, selective batching: run the shape-compatible parts together — the embedding lookup, the feed-forward layers, the output projection, all elementwise or matmul work over pieces — and run attention per request [serving].

The payoff was the paper's headline: Orca, the system that introduced the trick, reported over thirty-six times the throughput of the static-batch baseline on a 175B model, with one-point-one to nine-point-one times across settings [serving].

The cache, cut into blocks

Batching fills the card's arithmetic; the next problem is the card's memory. Every request in flight brings a KV cache that grows as it generates. The obvious bookkeeping — reserve each cache as one contiguous span, sized for the maximum length the request might reach — wastes most of the memory: reserved-but-unused space in every short reply, and gaps between reservations that fit nothing. Measured on the systems before the fix: sixty to eighty percent of cache memory wasted, and a single long sequence on a 13B model could carry 1.7 GB of keys and values [serving].

The fix is an operating system's trick, applied to the cache. PagedAttention — the vLLM engine's name for it — partitions each request's cache into fixed-size blocks, sixteen pieces by default, stores those blocks wherever there is room, and maps each request's logical sequence of pieces to its physical blocks through a block table [serving]. Pages, a page table, allocation on demand: virtual memory, for keys and values.

Waste drops below four percent of total memory [serving]. And the indirection buys something contiguous caches cannot: sharing. Two requests with the same opening — the same system prompt, the same worked examples — can point at the same physical blocks, copied only when one of them writes a divergent piece [serving].

End to end, the whole stack — continuous batching plus paged caches — served two to four times the throughput of the earlier systems, and cut latency two to four times at matched pace [serving].

Inside one step: tiling the attention

One more layer down. Everything above manages work between steps; FlashAttention speeds the attention inside every step [serving]. The naive kernel computes a score for every query against every key — an n-by-n grid — and writes that grid to the card's high-bandwidth memory, then reads it back to combine. For a thousand-piece sequence that is a million scores round-tripped; attention was bound not by arithmetic but by the memory traffic of its own intermediate [serving].

The fix is tiling: load small blocks of queries, keys, and values into the on-chip SRAM next to the arithmetic units, compute partial softmax results per tile, and rescale as more tiles stream in — an online softmax, running tile by tile [serving]. The n-by-n grid is never materialized in main memory at all. And the math is exact — the same numbers, computed in a different order [serving].

The measured effect: attention alone up to 7.6x faster on GPT-2; whole-model speedups of 3x at thousand-piece sequences and 15% on BERT-large; memory that grows linearly with sequence length instead of quadratically — up to 20x saved at 64K pieces, which is what made very long sequences practical at all [serving].

The three fixes stack cleanly [serving]: FlashAttention accelerates the attention inside each step — prefill and long sequences most of all; PagedAttention manages the keys and values between steps; continuous batching keeps the card full across steps. Kernel, memory, schedule — one system.

The knob every operator turns

With the machinery in place, the operator's dial is the batch size, and it trades two numbers against each other. Bigger batches mean more throughput — but longer queues before a new request is admitted, so TTFT grows; and some TPOT growth too, since each step's cache reads grow with the batch [serving].

Chunked prefill is the smoothing move: split a huge prompt's prefill across several steps, interleaved with decode, so a thousand-piece question does not freeze every reply mid-stream [serving].

This page filled the card's idle arithmetic. The floor itself — one full sweep of the weights per piece — is still untouched: every byte of every weight, read every step. The next page attacks the weights: make each byte smaller, and the same sweep carries more pieces.

Takeaways

  • At one request, decode runs at roughly one unit of arithmetic per byte against a machine balance of 150-600 — the GPU starves; batching amortizes one weight read over every request in flight.
  • Static batches idle finished slots; iteration-level scheduling — continuous batching — admits and evicts at every decode step, and selective batching runs the shape-compatible parts together, attention per request.
  • PagedAttention cuts each cache into fixed-size blocks mapped through a block table — virtual memory for keys and values — dropping waste from 60-80% to under 4% and letting shared prompts share blocks.
  • FlashAttention tiles attention through SRAM with an online softmax: exact math, the n-by-n score grid never materialized, memory linear in sequence length.
  • Throughput and TTFT trade off along the batch dial; chunked prefill smooths the mix — and the weight sweep per piece remains the floor the next page attacks.
