Part Five — The Frontier

End to End: One Request, Start to Finish

Every page so far built one mechanism or priced one cost. This page runs a single request through all of it — from the moment your code sends a messages array, through doors and templates and loops, to the last piece of text rendered on a screen. Nothing new gets built here; everything gets used.

What leaves your machine

You do not send a chat. You send a structured request: an array of messages — each one a role and a string of text — plus the sampler's parameters and a stream flag asking the server to answer in pieces as they are produced [e2e].

The roles are a fiction that survives exactly one step: system, user, assistant — three labels that matter at the template and then vanish. The parameters are the knobs the sampling page turned — temperature, top-p — sent along for every step of the loop [e2e].

Why a stream flag at all? Because the machine cannot hurry — one sweep per piece is the law — but a reader does not wait for the last piece to start reading. Streaming does not make the reply faster; it changes where the wait is felt: the first piece lands at time-to-first-token, and the rest arrives while you read the beginning.

Through the provider's door

The request crosses transport security and hits a frontend: authenticate the key, check the rate limit — the unglamorous machinery every web service shares [e2e].

Then the interesting door: a scheduler picks which serving instance takes the request, and its ledger is memory — room for the weights plus the KV cache of every request already in flight. This is the loop the serving page walked: admission is continuous, requests join mid-flight, and the block table grows as prompts arrive [e2e].

Why memory and not arithmetic? The weights are spoken for the moment the instance loads them; the only quantity that grows with admissions is the cache of in-flight requests — every accepted prompt adds keys and values for each of its pieces in each layer. An instance turns requests away not because its arithmetic is exhausted but because there is nowhere left to put the bookkeeping of attention.

The string the model actually sees

Before any arithmetic, the messages array becomes one flat token string — the chat template the post-training page dissected. Role labels turn into special delimiters; the model never sees the word user or assistant, only the pieces that spell the marks around each turn [e2e].

Then the tokenizer cuts the string into pieces. What the model receives — all it ever receives — is that one sequence, with a role's worth of delimiters around each turn [e2e].

There is no session inside the machine, no memory, no role state — the delimiters are the entire protocol. An assistant turn ends where its mark says it ends; a new user turn begins where the next one says so. Every behavior the post-training page attributed to roles lives in how training conditioned the model on these marks [e2e].

The seconds you wait

Now the loop page's clock runs. Prefill: one compute-bound sweep over every prompt piece, filling the KV cache; the first sample comes out the far end, and time-to-first-token is done [e2e].

Perceived latency has one more term before any arithmetic: the queue. A request admitted behind a burst waits its turn at the scheduler, and on a busy endpoint that wait can dominate everything the machine itself does [e2e].

Then decode: sample a piece, append it, forward, repeat — memory-bound, one sweep of the weights per piece, the ceiling the loop page priced. Your perceived typing speed is that decode rate bent by batch pressure: shared with other requests, it settles well under the lone-request ceiling. A hosted reply moving at sixty pieces a second is a busy machine, not a broken one [e2e].

That ceiling, concretely: a lone seven-billion-weight model runs at roughly one hundred forty-six pieces a second on one class of card. A hosted reply moving at sixty is sharing the card: every step of the batch carries more arithmetic on the same weight read, and as that intensity climbs toward the card's balance point, each step takes longer for every request riding it.

Three things stop it: the end-of-sequence piece, a piece-count limit from the request, or the client hanging up. On stop, usage is tallied — prompt pieces against completion pieces [e2e].

What comes back, and what it costs

With the stream flag set, the reply travels as server-sent events: the HTTP response stays open, and the server pushes small labeled chunks down it — each a data line carrying a delta, a fragment of text, framed by a blank line, with terminal events closing the stream. Without the flag, the server buffers everything and returns one structured blob at the end [e2e].

The deltas are text, and turning pieces into text is not instant: detokenization happens on the fly, and a multi-byte character split across a piece boundary is buffered until its bytes complete [e2e].

The bill arrives with the usage tally, and its shape is the lesson: input and output are priced separately, output several times higher per piece — the phase asymmetry of the loop, reflected in a rate card. Input pieces share one parallel sweep; every output piece demands its own serial pass [e2e].

Three perceptions, mapped

It forgot what we said yesterday. The model is stateless between requests: nothing persists. Yesterday's turns were either re-sent as part of today's context — re-prefilled, re-cached — or never sent at all [e2e].

And a conversation compounds. Turn by turn the request grows — today's prompt carries every earlier turn plus the new one, because the machine keeps nothing between requests. The cost of a long chat is not storage but repetition: each reply is computed against the entire history again, prefilled fresh unless the engine held on to the cached remains of the same prefix.

It knows about one thing but not another. The known thing was in the pretraining corpus before the knowledge cutoff; the other was not — and nothing at inference reads a database unless the application builds retrieval or tools around the model [e2e].

Takeaways

  • A chat request is a messages array plus sampler parameters; roles are labels a template turns into delimiters — the model only ever sees one token string.
  • Admission is a memory ledger: the scheduler weighs the weights plus in-flight KV cache, and requests join a continuously running batch.
  • Your seconds map to machinery: time-to-first-token is queueing plus prefill; typing speed is the decode rate — the loop's ceiling bent by batch pressure.
  • Streaming is server-sent events over an open response: data-line deltas, on-the-fly detokenization that buffers characters split across piece boundaries, terminal events to close.
  • Output is priced several times above input per piece — the serial decode pass reflected in a rate card — and the model is stateless between requests, its knowledge frozen at the pretraining cutoff.
