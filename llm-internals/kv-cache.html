Part Four — Inference at Scale

The KV Cache

The last page priced the loop and ended on a hidden cost: attention work thrown away at every step. This page is the fix — a memory that grows one row per piece — and the bill for it: at the longest windows, one conversation's memory reaches the size of the model's own weights.

The work that gets thrown away

The last page ended on a hidden cost; name it precisely. When the model generates a new piece, that piece's attention must look at every piece before it — the question and everything generated so far. Looking requires keys and values: each earlier position, in every head of every layer, produced a key vector and a value vector when its forward pass ran [inference].

The naive loop recomputes them. Each step forwards everything so far, from scratch — which recomputes, for the identical positions, keys and values that earlier steps already computed. Same weights, same inputs, same outputs: the work is not approximated, it is repeated [inference].

Why is the repeated work identical? Causality. The causal mask from Part One's attention page lets a position see only the positions before it — so the key and value a position produces depend on the pieces up to it and nothing after. Appending piece forty changes nothing about the keys and values of pieces one through thirty-nine; recomputing them re-derives the same numbers from the same inputs. The recomputation is not refining an estimate — it is the same arithmetic, run again, because nothing kept the result.

Count it on the toy — a three-piece prompt, ten generated pieces. Step one forwards three pieces; step two forwards four; step ten forwards twelve. Three plus four plus five, on up to twelve: seventy-five token-forwards to produce ten pieces [inference]. The per-step work grows with the reply so far, so the total grows with its square — and every wasted forward re-reads all the weights besides [inference].

Keep the keys and values

The fix is to stop throwing the work away. On the prefill pass — the single forward pass over the whole prompt — every position, in every head of every layer, produces its key and value vectors. Keep them. That store is the KV cache Part One named: nothing but the keys and values from every position processed so far [inference].

After prefill, each new piece needs a forward pass over itself alone. Its query scores against every cached key; the resulting attention weights combine the cached values; and the key and value the new piece produces in that same pass are appended to the store, ready for every later piece [inference]. One new row per piece, per layer, per head — the cache is append-only.

Notice what the cache does not store: hidden states, block outputs, query vectors. Each new piece's query is computed fresh, used once against the cached rows, and discarded — only its key and value rows persist [inference]. The store is narrow on purpose: exactly what later pieces will need, and nothing they will not.

The two paths through the loop differ by one expression — forward everything so far, or forward the new piece and consult the stash:

Exact, not approximate: the new piece's attention needs precisely those cached keys and values, and recomputing them would yield the identical numbers. The script runs both paths and asserts it — same ten pieces either way [inference].

What the memory costs

Speed was bought with memory, and the memory can be priced to the byte. The cache holds, for every piece so far, a key vector and a value vector in every head of every layer. Bytes per piece = two, for key and value, times layers times kv heads times head width times the bytes of the stored format [gpus].

Walk the factors — each is a Part One concept. Two, because every position stores both a key vector and a value vector. Layers, because every transformer block keeps its own attention, its own keys and values, at its own place in the stack. KV heads, because GQA shares one set of key-value heads across groups of query heads — the count the design already shrank. Head width, the length of each stored vector. And the stored format's width: two bytes per number in half precision. Multiply the machine's memory geometry by the length of the conversation, and the bytes fall out.

  Llama 2 7B — 32 layers, 32 kv heads, 128 wide, fp16:
    2 x 32 x 32 x 128 x 2 = 524,288 B = 512 KiB per piece
    at 4,096-piece context:   2 GiB

  Llama 3 8B — 32 layers, 8 kv heads, 128 wide, fp16:
    2 x 32 x 8 x 128 x 2 = 131,072 B = 128 KiB per piece
    at 8K context:            1 GiB
    at 128K context:         16 GiB — one sequence's cache,
                              the size of the model's own weights

  (GQA's cut: 32 kv heads -> 8 = 4x fewer bytes per piece)

Read the last line of the panel twice. At the 128K context window Llama 3 ships with, one sequence's cache — 16 GiB — reaches the size of the model's own weights, roughly 15 GiB of them [gpus]. The memory holding one conversation rivals the memory holding the machine.

This is what GQA was for. Part One's multi-head page described the design: fewer key-value heads, groups of query heads sharing them. Llama 2 7B kept thirty-two key-value heads; Llama 3 8B keeps eight. The cut lands directly here — 512 KiB per piece against 128 KiB, a straight four-times reduction in cache bytes [gpus]. Part One covered what the sharing costs in expressiveness; this page is what it buys.

The trade, and what it caps

With the cache in place, the decode floor from the last page gains a second term. Each generated piece now costs: read every weight once — the term the weight sweep set — plus read the whole cache, which grows with every piece so far, plus a trickle of arithmetic [inference]. At short windows the weight term dominates; at long ones the cache term closes in.

The cache is also a choice, not a law. The alternative is recomputation — trading the memory back for the quadratic work the loop just escaped. Systems pick per situation: memory is the scarce resource at long windows and many simultaneous requests; arithmetic is scarce everywhere else [inference].

And the cache is per sequence. Weights are read shared; caches are not — every conversation brings its own, growing with its window and its reply length [inference]. A card that holds a model's weights with room to spare holds only so many long conversations before the room fills with keys and values. What a production system does about that — how it packs this memory, moves it, and keeps many replies flowing at once — is the next page.

Takeaways

  • Each new piece's attention needs the keys and values of every earlier position; recomputing them every step makes the loop's work grow with the square of the length — ten toy pieces cost seventy-five token-forwards.
  • The KV cache keeps them instead: prefill fills the first rows, every decode step appends one row per layer per head, and each new query reads them all.
  • The cached path is exact — both paths emit identical pieces; the script asserts it, and the fork is one conditional expression.
  • Bytes per piece = two × layers × kv heads × head width × dtype bytes: 128 KiB for Llama 3 8B, 512 KiB for Llama 2 7B — GQA's four-times cut, straight off the cache bill.
  • At a 128K context window, one sequence's cache reaches the model's own weight size; weights plus every sequence's cache must fit the card — which caps how much can run at once.
