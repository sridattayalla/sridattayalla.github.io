Multi-Head Attention and GQA

After this page you can say what changes when a floor runs thirty-two gathers instead of one — and why the biggest models deliberately shrink the offering side.

On this page

  1. One gather is one opinion

One gather is one opinion

The last page ended with a pronoun holding cat-ness: one gather, one mixture, one new vector per piece. Nothing on this page replaces that machinery. The change is the count.

One gather per position forces a compromise. A real position wants several relationships at once — the noun it refers to, the verb it belongs to, the neighbors it sits between, the topic of the passage so far. A single weighted average can only blend those into one mixture, splitting its budget among them. If reference needs "cat" and the action needs "ate", one gather gives each a share and neither the full picture.

The architecture's answer is blunt: run the whole apparatus several times per floor, in parallel. Not by copying the width — by slicing it. Each slice gets its own tables, asks its own question, runs its own gather. The floor's output stops being one opinion per position and becomes several.

Slice the width, run the same recipe

The arrangement has a name. Multi-head attention splits the working width into heads — each head owning a slice of every piece's vector — gives each head its own asking, offering, and payload tables (each d_model by d_head, the slice width), runs the same gather recipe on every slice in parallel, concatenates the results back to the full width, and mixes them through one shared output table, W_o [components].

Concrete numbers, from the 8B model's floor: working width 4096, thirty-two heads, each slice 128 wide [model-configs]. The asking table W_q is 4096 by 4096 — its output is the full working width, which then reshapes into thirty-two slices of 128. The offering and payload tables are narrower — 4096 by 1024 — for a reason that arrives later this page.

The structural fact to hold onto: heads are blind to each other. During the gather, head three's score grid knows nothing of head seven's — no shared scores, no averaging across heads. The only place head outputs meet is after concatenation, through W_o. Every coordination between heads happens there, or in the floors above.

Worked example — the 8B floor's gathering half, shapes only

the 8B model's floor, gathering half — shapes only:

  piece vectors X:              (n, 4096)     n pieces, working width 4096

  asking copies   X @ W_q:      (n, 4096) -> reshape (n, 32, 128)
                                one 128-wide slice per query head

  offering copies X @ W_k:      (n, 1024) -> reshape (n,  8, 128)
  payload copies  X @ W_v:      (n, 1024) -> reshape (n,  8, 128)
                                8 KV heads; each serves a group of 4

  per head:  scores (n, n) -> weights (n, n) -> gather (n, 128)
  (every query head runs its own grid, against its group's shared keys)

  all 32 gathers, concatenated:        (n, 4096)
  mixed by W_o (4096 x 4096):          (n, 4096)

Read the panel with the last page's machinery in mind and notice that nothing new happened. The same three copies, the same score grids, the same softmax and gather — one set per head, over narrower slices. Even the position rotation runs unchanged, inside each slice.

What the extra finders buy

What do the heads look for? Each head's tables start at random values, and training pushes them wherever regularities in the text help next-piece prediction. The architecture guarantees only the division of labor: thirty-two independent pattern-finders per position, each filling its own slice of the width. Nothing forces them to specialize; specialization is what training makes of the room.

One budget detail is easy to miss: slicing does not multiply the width. Thirty-two heads of 128 entries still total 4096 — the same working width, divided. Multi-head buys more simultaneous questions, not more room per question. The trade-off is real: fewer, wider heads give each finder more entries to work with; more, narrower heads give each position more finders.

Where the dial settles is strikingly consistent across families: GPT-3's largest model and the Llama line both land on 128 entries per head — the former with 96 heads across a 12,288-wide vector, the latter with 32 across 4096 [model-configs].

Sharing the offering side

Now the asymmetry that motivates the rest of the page. When the model generates — extends text one piece at a time — each new piece brings one asking copy per head: cheap, transient, used once. But its gather must meet every earlier piece's offering copy, and gather from every earlier payload. The offering side therefore accumulates as the text grows: keys and values for every piece so far, per head, per floor.

That accumulating store has a name, and the model keeps it deliberately. The KV cache is the stored key and value rows for every piece processed so far: as the model first reads the text it computes each piece's offering and payload rows and keeps them, so that each later piece's gather meets those stored rows instead of forcing the model to rebuild them [inference]. One new piece adds one new row per key-value head; nothing already stored is recomputed.

The cost lever sits inside the store. It holds one key row and one value row per piece, per key-value head — so fewer key-value heads means a smaller store, in exact proportion. The asking side is untouched: queries are per-piece and transient.

Which invites the obvious move. GQA — grouped-query attention — arranges the query heads into groups and gives each group a single shared key-value pair of tables: one key-value head serves several query heads [components]. The 8B model runs thirty-two query heads in eight groups of four, so the store shrinks to a quarter of its full multi-head size — and the design was introduced with the quality cost measured at negligible [components].

The extreme is MQA — multi-query attention — where every query head shares one single key-value head: the smallest possible store, and a bigger quality price than grouping [components]. Grouping sits between the extremes, and close enough to full multi-head that the biggest model families shipped it.

Why sharing works at all: within a group, each query head still runs its own score grid against the shared keys and gathers its own mixture from the shared values. Four askers with four different questions consult the same labeled shelves. What the group shares is infrastructure, not opinion.

  grouped (GQA-8):     8 KV heads     8 units    one quarter

  quality: GQA-8 measured within rounding of full multi-head

One side effect lands in the tables: the offering and payload tables narrow with the group count — in the 8B model, W_k and W_v are 4096 by 1024 rather than 4096 by 4096 [components].

About 42 million entries [components]. Notice what sharing did to the count: without it, W_k and W_v would each be 4096 by 4096, and the half would hold about 67 million — sharing shaved roughly 25 million entries, more than a third of the half, along with the store.

The other half of the floor is heavier — over four times heavier — and it is the next page's whole subject. The handoff is clean: the gathering half moved information between positions; the other half processes each position alone.

Takeaways

  • One gather per position forces a single compromise mixture; multiple heads give each position several independent gathers — more simultaneous questions, not more width.
  • Multi-head slices the working width (32 heads of 128 entries = 4096 in the 8B model); W_o after concatenation is the only place head outputs mix.
  • During generation the offering side accumulates — the KV cache, one key and value row per piece per key-value head — while asking copies stay per-piece and transient.
  • GQA shares key-value heads among query groups (32 heads into 8, a quarter of the store) at negligible quality cost; MQA is the one-head extreme.
  • The gathering half of one 8B floor holds about 42 million entries; the other half holds over four times more — next page.
