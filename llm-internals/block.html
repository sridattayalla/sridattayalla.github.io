Why add instead of replace

Two pages of machinery, one missing piece. The gathering half moves information between positions; the per-position half transforms each position alone. Both were shown with two details deliberately unexplained — a scaling step before, an add-back after. This page is those details, and the floor they make.

Start with the add-back, because it is the one that makes depth possible. Consider the alternative: a floor whose output is simply its halves' output. Each floor replaces its input with a fresh transformation of it. Stack thirty-two such floors and the top of the tower sees only the last transformation's version of the text — every floor must re-encode everything the floors below established, and any floor that mangles its input passes the damage up intact.

The shipped design refuses to replace. A residual connection adds a sublayer's output back onto its input — the pattern y = x + Sublayer(x) — so the input survives every floor and each half only contributes an edit [components].

Read the formula mechanically: whatever the half computes gets added to the stream, not substituted for it. The floor's job description changes from "transform the text" to "propose amendments to the text" — and amendments can be small, partial, even zero. A half with nothing useful to contribute can output zeros and do no harm.

A running vector

The add-backs give the whole tower a second reading, and the reading has a name. The residual stream is the running vector: one vector per position, starting as the embedding row, flowing up through every floor; each half of each floor reads it, computes an edit, and adds the edit in; nothing ever replaces it [components].

Three consequences worth holding. Information added at floor one is still present at the top — every later floor can read what every earlier floor wrote. Each half only ever needs to learn an edit, not a full transformation. And when Part Two runs the learning signal backward through the tower, the skip lines are the road it takes — the identity path carries it through unchanged [components].

The bookends: the stream starts as the embedding lookup's rows, and ends at the output projection — the table that turns its final content into next-piece scores.

The stream has one more property worth naming: its width never changes. It enters the first floor at the embedding width and leaves the last floor at the same width, and every half of every floor reads that width and writes that width back. The per-position half's wide middle from the previous page is internal machinery — its last table shrinks the edit back to the stream's width before the add-back. That fixed width is what makes floors interchangeable: any floor can sit anywhere in the stack, because every floor speaks the same shape.

Keeping the entries in range

The scaling steps solve an arithmetic problem. The stream's entries get multiplied by learned tables and added to by edits, floor after floor, and nothing in that arithmetic holds their size steady: run enough floors and the entries drift — large here, tiny there. The machine's nonlinear steps are scale-sensitive — the softmax over scores goes flat when scores grow, and the bend reacts to entry size — so a drifting stream eventually deafens the floors above.

The original design's answer: LayerNorm — for each position separately, subtract the vector's entry average, divide by its spread, then re-scale and re-shift each entry with learned numbers [components].

The modern answer does half the work: RMSNorm — skip the mean-subtraction; divide each vector by its own root-mean-square entry size and re-scale each entry with learned numbers. Cheaper to compute, and used across the Llama family [components]:

Placement has an answer too: pre-norm scales before the half reads the stream — x + Sublayer(Norm(x)) — rather than normalizing the half's output after it. The original paper scaled after; everything from GPT-2 onward, including Llama, scales before, because the before-arrangement is what stays stable during training at depth [components].

The assembled floor

Everything is now on the table. A transformer block is one floor of the tower: scale, gather (all heads at once), add back; scale, transform per position, add back. Each floor owns its own tables; the stream is the only thing that passes between floors [components].

The companion script's forward pass, wiring and all — the same lines the last two pages excerpted in halves, now whole:

Read it as the diagram: two pre-scaled halves, two add-backs, one final scaling before the output table. The toy runs one floor with two heads and a two-table per-position half; the 8B model runs the same wiring with thirty-two floors, grouped heads, and the three-table recipe.

Run the removal test on the assembled floor. Remove the gathering half and every position's fate is fixed from the start — the per-position half applies the same bend to each vector in isolation, and no position can ever learn which earlier piece a later "it" points back to. Remove the per-position half and the positions talk but nobody acts — the gathered mix arrives at each position, but no learned table decides what a position does with what it heard. The tower needs both, in alternation: communicate, then think, floor after floor.

The tower, counted

Stack the floors. The 8B model stacks thirty-two of them [model-configs]; the largest GPT-3, ninety-six [model-configs]. Just over eight billion entries: the floors at roughly 218 million each [components], the embedding and the separate output table at roughly half a billion each. The number on the box is an entry count, rounded.

One sentence of scale before Part Two: at every position of every sequence, the whole tower is this page's wiring repeated — nothing more exotic appears anywhere in the machine. What is still missing is the point. The tower computes, but nothing yet tells it when it is wrong. The number that does — and the rule that moves every one of those eight billion entries to push it down — is where Part Two begins.

Takeaways

  • The residual connection adds each half's output back onto its input (y = x + Sublayer(x)): floors edit a stream instead of replacing it, so depth accumulates instead of discarding.
  • The residual stream: one vector per position from embedding row to output table; every half of every floor reads it, scales it, and adds an edit.
  • The scaling steps keep entries in range: LayerNorm (subtract mean, divide by spread), RMSNorm (divide by root-mean-square — cheaper, used by Llama), placed before each half (pre-norm).
  • The transformer block is the assembled floor: scale, gather, add back; scale, transform, add back — with its own tables, stacked thirty-two times in the 8B model.
  • The full count: ~218M per floor, 32 floors, plus embedding and output tables — just over eight billion entries. Next: the number that says the machine is wrong.
