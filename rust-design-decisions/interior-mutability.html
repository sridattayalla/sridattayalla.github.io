Part Five — Mutation and Threads

Interior Mutability: Mutation Through a Shared Handle

The last page ended with a question: every owner can read the shared value, so what happens when one of them wants to write? The folklore answer — a shared reference freezes the value — is not what the rule says. This page corrects the folklore, then walks the three types the standard library ships for acting on the correction: Cell, RefCell, and Mutex, which differ in exactly one respect — when the aliasing rule gets checked.

The correction

Start from what the borrowing page established. The rule is many readers XOR one writer: while a shared reference is alive, no mutation may happen that a live alias could observe. The folklore compresses this into "a shared reference means read-only" — and the compression is wrong in a direction that matters. What a shared reference forbids is not mutation; it is mutation that an alias could catch in the act.

The distinction is invisible for types the compiler cannot look inside. For a plain vector or a string, any mutation through a shared reference could be observed through that same reference, so the borrow checker refuses all of it. But a type can be built so its state is mutated through a shared handle while no alias ever sees a torn or half-updated value — the mutation is structured to keep the contract. Rust's name for this pattern is interior mutability: a type mutating its own state through a shared handle, with the discipline guaranteed by the type's structure rather than by the borrow checker at the call site.[interior-mutability] The standard library's cell module introduces its family of wrappers in exactly these terms — types that allow mutation "in otherwise immutable contexts," its phrase for shared mutability.[interior-mutability]

Why wrappers at all? Because the compiler cannot see the discipline. If these were ordinary structs with ordinary setter methods, mutation through a shared reference would be legal for every type — including the ones whose mutation does tear state in front of aliased eyes. The pattern needs types whose public surface re-establishes the rule by construction. Each of the three picks its own enforcement point, and that difference is the whole page:

  • Cell checks nothing at run time — its methods make a violation impossible to write.
  • RefCell checks a counter at every borrow — a clash halts the program when it happens.
  • Mutex blocks — a clash waits until it clears.

The rest of the page walks the three stations left to right.[interior-mutability]

Cell: the check folds into the type

Cell is the pattern with the discipline folded into the API. Watch it work:

Read the middle lines the way the borrowing page taught you. shared is a shared reference, and set mutates through it — the program compiles, runs, and prints the bumped value. Nothing slipped past the rule; the rule moved inside the type. Cell's methods never hand out a reference into the stored value: get copies the value out — which is why it demands the stored type be copyable, the Copy trait from Part Two — and set takes a whole new value in, overwriting the old. Because no operation leaves a reference pointing into the interior, there is nothing for an alias to catch mid-mutation. The violation cannot be written, so nothing needs checking when the program runs — the check has happened already, in the shape of the API itself.[interior-mutability]

The price is that everything is wholesale. A Cell holding a counter is perfect — small, copyable, swapped in one step. A Cell holding a growable buffer is nearly useless: get cannot copy a whole vector out, so you are reduced to replacing the entire thing each time you wanted to append one element. The moment you need a real reference into shared data — to push onto a shared vector, to follow a graph edge and rewrite it — Cell's answer is no, and the next wrapper exists for exactly that moment.

RefCell: the check moves to run time

RefCell keeps the rule and moves the check. References into the interior do escape — borrow hands out a read handle, borrow_mut a write handle — and each call consults a counter inside the cell: many readers XOR one writer, enforced at the moment of the call rather than the moment of compilation.

That is the shape every graph mutation takes: take a write handle, change the data, let it drop, take a read handle, observe. The counter allows the sequence, and it would allow several readers at once; it refuses exactly what the borrow checker refuses — a writer while readers live. Refuse how? Compile the clash and see:

The clash compiles — nothing about the types is wrong — and then, in the executions where the two borrows actually overlap, the program halts. The refusal is a run-time panic: the captured message names the cell's state, "RefCell already borrowed," and the exact line doing the clashing.[interior-mutability]

That is the honest trade, stated plainly. The borrowing page's checker rejects a clash for all possible executions before the program ever runs; RefCell rejects it for the executions that actually happen, at the moment they happen. A program whose borrows never overlap in practice runs forever — the guarantee has moved from cannot happen to did not happen. You traded a compile-time refusal for a run-time one, and in exchange, shared data structures on a single thread became expressible at all.

Mutex: the check blocks instead

Move the shared data across a thread boundary and RefCell's answer collapses: its counter is plain memory with no locking, and two threads consulting it at once is exactly the race the language exists to prevent. The third wrapper keeps the rule and changes the enforcement point once more — instead of rejecting or halting, it waits.

Mutex is that wrapper. lock takes the lock, blocking the calling thread until the current holder releases, and returns a guard: a handle that carries the lock and releases it automatically at drop — the same release-at-destruction machinery Part Two used for files and buffers. The guarded region is the guard's lifetime; the language's block structure draws the critical section.

Walk the capture. The worker takes the lock, pushes, and fails mid-hold — the failure appears on the error stream, and the guard's release-at-drop still runs as the failing thread cleans up, so the lock itself comes free. But the mutex is now marked. The standard library calls this poisoning: a flag meaning "a holder died mid-update; the invariant may be broken." Every later lock on that mutex returns an error instead of a guard. The mark is advisory — nothing forces you to heed it — and the program above recovers the data anyway, pulling the guarded value out through into_inner and printing it intact.[interior-mutability]

RwLock is the sibling for read-heavy data: many readers at once, XOR one writer — the borrow checker's exact shape — with waiting instead of rejection in both directions.

A note on the guard's lifetime, from the ownership page's refusal about held values: matching on lock() as a block's tail expression keeps the guard alive past the block's locals, and the compiler catches the shape. Which is the honest tool

Which wrapper, then? The choice is a declaration of which enforcement point you accept, and the standard library makes you write it in the type:

  • Cell — small copyable state: flags, counters, tiny configurations shared immutably. The check is structural; the cost is nothing.
  • RefCell — real references into shared data on one thread: graphs, trees, caches with interior edges. Accepts that a clash halts at run time.
  • Mutex — shared state across threads. Accepts blocking.
  • RwLock — read-heavy shared state across threads. Accepts blocking so many readers can proceed together.
  • Atomics — counters and flags across threads without blocking at all: the locked instruction from the Arc on the previous page.

The wrappers compose into patterns you have already met. The canonical single-threaded graph shape is Rc<RefCell<T>>: many owners from the Rc, runtime-checked edges from the RefCell. The cycle program on the previous page was exactly this — the field swap that built the leak went through a RefCell — which is worth saying out loud: the leak was not the RefCell's doing. The counter polices borrows, not the reference-counting reachability above it.[interior-mutability]

And the framing that keeps the whole page honest: interior mutability is not a passage around the aliasing rule. It is the same rule, implemented by a library type, with the enforcement point moved — from the compiler's sight, to a run-time counter, to a blocking lock. The Book's interior mutability section makes the same point the same way: a trade of guarantee strength, declared in a type, paid only where you opted in.[interior-mutability]

The next boundary is already visible. RefCell's counter is checked at run time and knows nothing about threads; the moment data crosses a thread boundary, the check has to move into the types themselves — which is the next page.

Takeaways

  • A shared reference forbids contract-violating mutation, not all mutation; interior mutability is mutation through a shared handle with the discipline built into the type.
  • Cell folds the check into the API: values move in and out whole, no reference into the interior ever exists, and nothing needs checking at run time.
  • RefCell moves the check to run time: the same many-readers-XOR-one-writer rule, enforced by a counter at each borrow; a clash the borrow checker would reject now halts mid-run.
  • Mutex blocks instead: the guard releases the lock at drop, and poisoning marks a mutex whose holder died mid-update — advisory, and recoverable through into_inner.
  • The choice among them is a trade declared in the type — compile-time rejection, a run-time halt, or waiting: the same contract at three enforcement points.
