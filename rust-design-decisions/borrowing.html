Part Three — Borrowing

Borrowing: Aliasing XOR Mutability

Moves hand whole values away, and duplication is priced by the byte. Most of the time a function needs neither: it needs to look at a value it does not own. The ampersand is that maneuver, and around it sits the sharpest rule in the language: many readers, or one writer — never both.

Lending access

The last page ended on the gap: handing a String to a function means handing over its buffer, and duplicating a value just to read it is absurd. The maneuver Rust builds for that gap is small in syntax and large in consequence.

A reference is a handle to a value owned by someone else. You write &v to make one, and through it you can read v without owning it, moving it, or copying it. Creating and using such a handle is borrowing: the owner lends, the borrower looks, and the handle must be done before the value dies — the checker enforces that, and the next page shows the notation it uses to say so.

There are exactly two kinds. A shared reference — written &T — is a promise to read only: any number of them may aim at one value at the same time. A mutable reference — written &mut T — is a promise to have the value to yourself: read and write, and exactly one such handle at a time.

The central rule

Put the two kinds side by side and the design shows its teeth. Many handles aimed at one value is aliasing. One writer changing a value is mutation. Rust's central rule — the one the community calls aliasing XOR mutability — is that a value may be aliased or mutable, but never both at once: many readers, or one writer, never a reader in the room while the writer works.

The rule predates its name. Niko Matsakis, whose 2012 post is the concept's origin, wrote the contract in one sentence: "The contract is relatively simple: if you are reading, no one is writing, and if you are writing, no one else is reading (or writing)."[borrowing] Honesty about the phrase itself: the literal wording aliasing XOR mutability appears in no official Rust document — it surfaced in a 2021 research paper and in Google's Rust course.[borrowing] The official phrasing is plainer, from the error index: "in Rust, you can either have many immutable references, or one mutable reference."[borrowing]

The two kills

Why this rule, of all possible rules? Because it deletes, at compile time, the two failures from the first part of this book that plain memory safety could not.

The first is the container that moved — the C program whose realloc relocated the buffer under a saved pointer. Here is the Rust shape of that program:

The anatomy maps line for line onto the C one. The loop holds a shared borrow of v — the iteration itself needs it, and every x is a view into the buffer. Pushing may relocate that buffer, exactly as realloc did, which would leave every x aimed at freed memory. In C this was a sanitizer report at run time; here the two needs — the loop's shared borrow, the push's exclusive one — collide in the checker, and the program never runs.[borrowing]

The second is the data race. Two threads mutating one counter through two handles is, to this rule, the same offense as two exclusive handles in one thread — and the machinery that moves values between threads is itself typed, so the offense cannot sneak across the boundary. That half of the story, and the marks that gate it, arrives when this book reaches threads.

Read them bottom-up when an error seems senseless: the use that keeps the borrow alive is usually the line the error does not point at.

When borrows end

All three refusals shared a hidden clock: a borrow is live from its creation to its last use, and conflicts are judged against that window. That window is the lifetime of the borrow — how long the handle is actually held.

The window is smaller than you would guess from the braces. The mental model most programmers bring — the handle lives until the end of its block — was, in fact, the model of the borrow checker before 2018, and it was replaced because it was wrong: it rejected correct programs. The fix, RFC 2094, switched the checker from scope-shaped reasoning to control-flow reasoning, and the result is called non-lexical lifetimes — NLL for short. The RFC's own summary of the old state: "Lifetimes in Rust today are quite a bit more flexible than scopes (if not as flexible as we might like, hence this RFC)".[borrowing]

In the first, the loop's borrow of v ends when the loop does — the last use is the iteration itself — so the push after it is free to claim exclusivity. In the second, first's borrow ends at the println, its last use, and the push that follows is again unopposed. A borrow ends at its last use, not at its closing brace — that single sentence is the difference between predicting the checker and fighting it.

The rule is not free. Doubly-linked structures, graphs, and read-then-write patterns that genuinely need overlapping handles must pay: restructure so the borrows end earlier (the answer, most of the time); scope the mutation into its own block; reach for Cell and RefCell, the shared-handle mutation tools two parts ahead; or fall back to indexes and handles of your own. The marked-code hatch at the end of this book exists for the remainder.

Every refusal on this page was, underneath, a question about time: does the owner outlive every borrow aimed at its value? Inside one function the checker answers that question itself. Across function boundaries it cannot — unless the signature carries the answer. Writing time into types is the next page.

Takeaways

  • A reference is a handle to a value someone else owns; making one is borrowing, and it must be done before the value dies.
  • Shared handles come in any number and read only; a mutable handle comes exactly one at a time and reads and writes.
  • The central rule is aliasing XOR mutability: many readers or one writer, never both — the concept dates to 2012, and the phrase is not official.
  • The checker is flow-sensitive: a borrow is live from creation to last use, and the "later used here" annotations name the use that keeps it alive.
  • The rule deletes iterator invalidation and the data race at compile time — the same offense, single-threaded or not.
