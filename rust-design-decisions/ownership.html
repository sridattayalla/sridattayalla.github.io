Part Two — Ownership

Ownership: One Owner Per Value

The last page made a promise: one rule, checked before the program ever runs, that deletes all five failures at once. This is that rule — three sentences long — and this page takes it apart: what a move actually copies, exactly when values die, and the one guarantee Rust deliberately refuses to make.

The rule

The previous page ended with a bet: one compile-time rule that deletes all five failures at once. Here is the rule. It is three sentences, and not one of them mentions memory.

The Rust Programming Language states it: "Memory is managed through a system of ownership with a set of rules that the compiler checks. If any of the rules are violated, the program won't compile."[ownership]

Unpacked, the system is a list:

  • Each value in Rust has an owner.
  • There is only one owner at a time.
  • When the owner goes out of scope, the value is dropped.

A scope is the stretch of program between an opening brace and its matching close — a function body, a block, a loop body. When control reaches the closing brace, every value created inside that stretch dies, and the code that runs at that moment is the value's destructor, the cleanup word the previous page defined. Rule three is where deterministic destruction comes from: the death point is fixed by the shape of the code, not by a caretaker's schedule.

Rule two is the one with teeth, and it is aimed exactly at the double free. In C, p = q copies the pointer and leaves both names alive — two handles, one block, nothing to stop the second hand-back. Rust closes that door by making plain assignment a transfer for most types: the new name becomes the owner, and the old name retires. The transfer is called a move, and the rest of this page is its anatomy.

What did the assignment actually do? A String is two things: three machine words on the stack — a pointer aimed at a heap buffer, the count of bytes the string holds, the count of bytes the buffer claims — and the buffer itself.[ownership] The assignment let t = s; copies those three words and nothing else. t now owns the buffer. s retires: its words are still sitting in memory, but the compiler treats the name as if it were never initialized, and any read of it is the error above — a refusal at compile time, not a crash at run time. The buffer is not copied, and s does not hand it back: exactly one hand-back will ever happen, t's.

Making moves the default was a decision, recorded while the language was still taking shape. RFC 0019 — the proposal that settled the question — states it: "This means that structs and enums would move by default unless their type is explicitly declared to be Copy."[design-history] The reason is the C++ experience: there, a = b may run a copy constructor the type's author wrote — a full duplicate of everything the value reaches, an allocation, a surprise cost hiding behind an equals sign. Rust inverts the deal. Plain assignment is always cheap: either a move — three words, done — or the byte-for-byte duplicate that certain small types earn, which is the next page's subject. The expensive operation exists too, but it is spelled loudly, and its name waits for the next page.

When the drop happens

Rule three said the value dies at the closing brace — in outline. This section fixes the exact moment, because eventually is what the caretaker sells, and this whole design exists to sell something better.

The pattern has a name from C++: RAII — resource acquisition is initialization. The trick is to tie each resource — a heap buffer, an open file, a held lock — to a value: acquire when the value is built, release in its destructor. C++ made the trick available; Rust made it universal and unavoidable. Every file handle, lock, and socket in the standard library is a value whose destructor returns what it holds, and the language fixes the moment that destructor runs.

Which moment, exactly, is not left to chance. The drop order is rule, not schedule: local variables die in reverse order of declaration, and the fields of a struct die in the order they are written.[ownership] A program that makes every death visible:

Check the output against the rules. c dies first: the inner block closes before main ends. Then, after main's final print, its locals die in reverse declaration order — p was declared last, so it dies first, then b, then a. And inside p, the fields die in written order: one, then two. Locals unwind backward; fields die forward. The asymmetry is deliberate: fields are laid out, and destroyed, in the order they are written, while the stack unwinds from the top.

One more rule, the one that surprises programmers who met this pattern in C++: assignment destroys. Overwriting an initialized variable drops the old value right there, at the assignment, not later at the closing brace.[ownership]

The sequence is fixed by the language: build the new value, drop the old one into its place, continue. In C++ the same expression would call an assignment operator the type's author wrote — which might do anything. Here the death is where the syntax says it is, every time. That predictability is the product. It is why try-with-resources, using, and defer exist in garbage-collected languages: each is a hand-written imitation of what this page gets for every value automatically.

The honesty clause

Everything so far has been a guarantee. Here is the one Rust refuses to give — and it is written down, not implied. During 2015, while the language's safety story was being finished, a crisis the community still calls the leakpocalypse forced a decision about std::mem::forget, a function that takes a value and simply never drops it. The resolution, RFC 1066, states the resulting guarantee in one sentence: "It has never been a guarantee of Rust that destructors for a type will run."[design-history]

Read it carefully, because it splits safety in two. Memory leaked is a bug you can survive: a program that leaks slows down and wastes space, but it does not become undefined behavior. A use-after-free hands attackers the machine. Rust counts the first acceptable and the second not — and every rule on the previous pages is that counting at work.

Two consequences. First, the ordinary one: some values are shared claims — one piece of memory owned jointly by several names, each holding the claim count up. Two such handles can point at each other, and then the count never reaches zero, and the destructors never run. When this book reaches that corner of the menu, it will show the tool built for breaking such rings. Second, the rule to keep: never hang a safety argument on a destructor running. Destructors are for cleanup where a leak is survivable — releasing memory, closing files, dropping locks. The escape hatches near the end of this book exist because some code must make promises the compiler cannot check, and those promises cannot rest on destructor execution either.

One loose end from the second section. The refusal explained itself with a clause — which does not implement the `Copy` trait — and that clause only makes sense if some types do implement it and are treated more gently. They are. Integers, for one: let b = a; on two numbers leaves both names alive, with the rule unbroken. How a type earns that exemption, what the compiler checks before granting it, and what the one explicit duplicate costs — that is the next page: assignment's full menu.

Takeaways

  • Ownership is three rules: one owner per value, one owner at a time, dropped at the end of the scope.
  • Plain assignment moves most types: the new name owns the value, the old name retires, and reading it is a compile-time refusal.
  • A move of a String copies three words — pointer, length, capacity — and the buffer changes hands rather than being copied.
  • Drops happen at statically known points: locals in reverse declaration order, struct fields in written order, and assignment drops what it overwrites.
  • The honesty clause: safety is guaranteed, destructor execution is not — std::mem::forget is safe, and leaks are survivable by design.
