Part Seven — Abstraction and Synthesis

Traits: Dispatch, Coherence, and dyn

Every page so far leaned on traits without asking two questions. Why can you not implement a standard trait for a standard type — the one impl you keep reaching for? And what did that boxed error on the last page actually cost? Both answers live in the same machinery: how Rust turns a trait's method call into running code. This page opens the machinery.

The question the last page left

You have been writing traits since the ownership page — Drop on your guards, Display on your types, Error on your failures — and calling other people's since the first line of Rust you ever read. A trait is a contract: a list of method names a type promises to provide. What the contract never said is how a call to one of those methods becomes machine code. That omission hides this page's two questions.

The last page ended on a cost we never counted: read_config returned its failures as one type standing for every error the function could produce — a value typed only by what it can do. That is one of the two ways Rust turns a trait contract into code. The other is generics. They differ in who picks the concrete type — the compiler, one copy per type, or the run time, one call site for all of them — and the difference shows up in the binary, in the call itself, and in one rule about which impls you are allowed to write at all. Start with the rule, because it is the one you have already met without knowing its name.

One impl, or the link fails

Rust resolves every method call at compile time: the exact function behind a call is fixed before the program runs. That has a consequence — for any trait and any type, there must be exactly one implementation. If two crates each shipped an impl of Display for Vec<u8>, one call would have two candidates and no way to choose between them. The guarantee that this can never happen is coherence: at most one impl of a given trait for a given type, program-wide.[traits]

Coherence is enforced by the orphan rule: an impl is legal only if the trait, or at least one of the types it mentions, is defined in your crate. The Reference states it plainly:

"A trait implementation is only allowed if either the trait or at least one of the types in the implementation is defined in the current crate. It prevents conflicting trait implementations across different crates and is key to ensuring coherence."[traits]

The refusal, when you reach for the impl that owns nothing:

Read the error's last note first: define and implement a trait or new type instead — rustc itself prescribing the escape. The newtype is that escape: a wrapper struct with exactly one field. Wrap the Vec in a local struct, implement Display for the wrapper, and the rule is satisfied — the local type is yours. The wrapper is a compile-time fiction: no allocation, no extra step at run time, the same bytes in the same order. You pay in a layer of conversion at the boundary, not in the loop.[traits]

RFC 1023 and RFC 2451 later adjusted the rule's details — which types count as local enough, and when generic parameters cover — but the shape never moved: your trait or your type, or no impl.[traits]

Static dispatch: a copy per type

Generics are the first way to turn a contract into code, and they get the fast lane. Static dispatch means the compiler resolves the call: by the time the program runs, the exact function is baked into the instruction stream. Generics achieve it through monomorphization — for every concrete type a generic function is used with, the compiler stamps out a specialized copy. The Book's phrase: "the compiler turns generic code into specific code by filling in the concrete types."[traits]

Two call sites in the source, two functions in the binary: largest for the number list and largest for the word list exist as separate machine code, each with its comparison inlined down to a couple of instructions — no boxing, no table lookup, nothing between the call and the work. The bill is paid elsewhere: compile time and binary size grow with every distinct instantiation — the C++ templates experience, inherited honestly. The benefit is the zero-cost abstraction claim in its concrete form: the generic call runs at hand-written speed, because by run time it is hand-written code for your exact types.[traits]

Dynamic dispatch: one call site, many types

Sometimes the set of types is not known when the program is compiled. A plugin loaded at start-up, an error raised by any library in the program, a shape read from a data file: the caller cannot enumerate them, so a copy per type is impossible. Dynamic dispatch resolves the call at run time instead — and its currency is the trait object: a value whose concrete type is unknown, typed only by what it promises to do — dyn Shape. The mechanism is the vtable: for each concrete type, the compiler builds one table of function pointers, one slot per trait method; a call through the trait object reads the method's address from the table and jumps.[traits]

Because any concrete type may sit behind a dyn Shape, the value has no fixed size — so every reference to one is a fat pointer: two words, the data's address and the table's. The sizes prove the shape:

Sixteen bytes for a reference to the trait value, twice the eight of a plain reference — and note the middle line of the output: a slice reference is also sixteen, because slices were the first fat pointer you met, on the borrowing page — data pointer plus length, where the trait flavor carries data pointer plus table. The loop is the payoff: one call site, shape.area(), ran the Square's code and then the Circle's, each address read from its own value's table.[traits]

RFC 2113 made the syntax carry the cost:

"Introduce a new dyn Trait syntax for trait objects using a contextual dyn keyword, and deprecate 'bare trait' syntax for trait objects."[traits]

Before the keyword, Shape alone could mean the trait or the value shaped by the trait, and the compiler guessed which; now the line says what it buys and what it charges. What it charges, precisely, is a constraint on the trait itself: used as a trait object, it exposes only its object safety subset — no generic methods, no methods returning the implementing type itself. The table needs one signature per slot; a generic method would need one slot per instantiation, and instantiations have no bound.[traits]

And so the last page's question has its answer. The boxed error of any type is a trait object: one compiled call site accepting every failure in the program, bought with one indirection per call, no inlining across it, and the object-safe subset of the error trait's methods. That is what Box<dyn Error> costs — and what it bought was the open set: any error, from anywhere, through one type.

The ladder, and the bill

Put the rungs in order. Generics: the fastest code — a specialized copy per type, comparisons inlined — paid in compile time and binary size; the caller picks the type at compile time. impl Trait in a return position: the same machinery wearing a mask — the concrete type hidden from the signature, still monomorphized, still one copy per actual type. dyn Trait: one compiled call site, an indirect jump, and the open set — any type, including types that did not exist when the caller was compiled.[traits]

The choice reduces to one question: is the set of types closed at compile time? If the callers can enumerate them, let generics stamp out the copies and run at hand-written speed. If the set is open — plugins, foreign errors, anything that arrives after compilation — the trait object is the only rung that holds.[traits]

The bill, per rung: coherence occasionally forces a newtype around a type you do not own; monomorphization charges compile time and binary size; the trait object charges an indirection per call and confines its traits to the object-safe subset. Three prices, one currency: you always know which one you are paying, because the syntax says so — the generic brackets, the hidden type, the dyn keyword. You now own every piece; the last page assembles them into two programs and walks the whole loop one time.

Takeaways

  • Coherence — at most one impl of a trait for a type, program-wide — is what makes compile-time call resolution possible; the orphan rule enforces it: your trait or your type, or no impl.
  • The newtype is the sanctioned escape: a one-field wrapper is a local type and a compile-time fiction — no run-time cost, one conversion at the boundary.
  • Static dispatch monomorphizes: one specialized, inlined copy per concrete type; the bill is compile time and binary size, never run-time speed.
  • Dynamic dispatch trades a fat pointer — data address plus vtable — and an indirect call for the open set: any type at run time, one compiled call site, object-safe methods only.
  • The ladder rule: closed set at compile time, choose generics; open set at run time, choose the trait object.
