Rc and Arc: Opting Into Shared Ownership

Box hands a value to exactly one owner; graphs, caches, and shared tables want many. Rust's answer is to make sharing a typed, countable decision: a handle that bumps a counter when cloned, and a value that dies when the count reaches zero. The design is honest all the way down — including about the one thing it refuses to promise.

Opting into more than one owner

The last page ended with the exact shape of the gap: Box has exactly one owner, and graphs want many — two nodes pointing at each other, a cache and its readers, a table shared by subsystems. Part Two's rule stands in the way — one owner per value, the owner frees — and the language does not bend it. It offers an opt-in.

That opt-in is shared ownership: more than one handle counts as an owner of one value, and the value dies when the last of them dies. The counting type for single-threaded programs is Rc, and its clone is not a copy:

The run shows the whole contract. Three handles exist after two clones; dropping one leaves two; the data is readable through whichever remains. Rc::clone never touches the payload — no bytes copied, no second buffer: it bumps the strong count by one and hands back another word pointing at the same value. That bookkeeping is reference counting — each handle holds a share of the count, cloning adds a share, dropping releases one, and zero frees — and the count is the number of owners.[shared-ownership]

A tiny local GC

The comparison with a tracing collector is worth making precisely, because reference counting is one — a tiny, local, incremental one. A tracing collector waits, then walks the object graph from the roots to find what is reachable, and frees the rest. Reference counting inverts the schedule: reachability is updated at every clone and every drop, a few instructions each, and the moment the last share disappears the value is freed — no pause, no walk, no waiting for the collector to choose.[shared-ownership]

The trade has two sides. What you gain is determinism — the free happens at a named line, the last drop, not at a collector's whim, which is the property Part Two built the whole story on. What you pay is the bookkeeping itself — every clone and every drop touches the count — plus the cycle problem, which is the next section.

And the decision is per-type and visible. Rc<String> in a signature says: shared ownership, single thread. The language default stays unique ownership; sharing is something the type asks for, in writing, where every reader can count it.[shared-ownership]

The cycle

The one structure reference counting cannot survive is the one graphs are made of: nodes that point back. A reference cycle is a ring of handles in which each node holds a share of the next, all the way around. Watch two nodes do it:

Read the output against the program. Each count stands at two — one share held by the local binding, one held by the other node's field. When main ends, the locals drop, and each count falls from two to one... and stops. Each node still holds a share of the other; neither count ever reaches zero; neither value is ever freed. The destructors do not run — the output ends at the counts, with no farewell lines.[shared-ownership]

Name the failure: a memory leak is allocated memory that is never freed because the program has lost every way to make the count reach zero. The bytes are gone for the run's remainder — and so are the destructor's side effects. If the node had held an open file, the file stays open; a buffered writer never flushes. The leak is not only memory — it is every responsibility the destructor carried.

The weak fix

The fix is a handle that views without owning. A weak reference holds no share of the strong count: it does not keep the value alive, and it cannot read the value directly — it must ask. Making one is Rc::downgrade; asking is upgrade, which returns Some handle while the value lives and None after — the possibility of the value's death is written into the type of the answer. The allocation remembers the weak count beside the strong one, and that bookkeeping cell outlives the value just long enough for every weak handle to learn it died.

Break the ring by making one direction weak — the classic shape is a parent owning its children strongly while the children point back weakly — and the counts can reach zero again:

Both farewell lines print this time. When the locals drop, a's strong count is one — the only share was the local, because b held a weak handle — so a frees immediately, b follows, and the weak handles learn of the deaths and answer None to any later upgrade.[shared-ownership]

The asking is worth watching on its own:

Same value, one strong handle, one weak: while the owner lives, upgrade returns Some with a fresh strong handle; after the drop, None. No dangling read is possible — the answer's type forces the check.[shared-ownership]

The honesty clause

Here is the design decision most languages do not print on the box. Rust guarantees memory safety; it does not guarantee leak-freedom. The designers said so in writing. Niko Matsakis, in 2015: "We long ago decided that, to make reference-counting practical, we had to accept resource leaks as a possibility." And the RFC that made the honest version official: "It has never been a guarantee of Rust that destructors for a type will run." — RFC 1066, which made mem::forget a safe function on the ground that the guarantee never existed.[shared-ownership]

Read the clause with the rest of the design. Safe means: no freed memory read, no double free, no undefined behavior — the founding constraint. Leaks are ugly, and cycles cause them, but a leaked value harms no one; a freed-too-early value corrupts everything. The guarantee draws the line exactly where the damage starts, and the weak handle exists so the common cycle has a cheap, typed repair.

The atomic sibling

One boundary remains, and it is the counter itself. Rc's count is a plain increment — fast, and safe only while one thread touches it. Two threads cloning simultaneously can both read the count at one, both write two — one update lost — and the value is eventually freed twice: the double free from Part One, reborn as a counting bug. The checker therefore refuses to carry an Rc across a thread boundary at all:

Read the refusal from the bottom, the way this book has learned to: spawn demands its argument satisfy a bound, and the help line names the missing trait for Rc<String> — the one that marks a value as safe to carry across a thread boundary. Its full story, and its sibling's, arrive two pages ahead; this page needs only the fact of the refusal.

The fix is the type again: Arc — atomically reference counted — same layout, same interface, but the count updates are atomic: operations the hardware performs as one indivisible step, so two threads updating at once cannot lose either update. The cost is real and local: an atomic read-modify-write is a locked instruction — roughly ten to twenty cycles uncontended, against about one for a plain add, and worse when cores contend for the count's cache line. That is the price of sharing across threads, and the type says exactly where it is paid.[shared-ownership]

Paid, and working:

Four threads, a thousand increments each, one count — the atomics lost nothing. The same program shape with Rc would not compile; with a plain non-atomic count it would corrupt; with Arc it is correct, and the cost is visible in the type.[shared-ownership]

The menu so far, in one breath: one owner on the heap, Box; many owners, one thread, Rc; many owners, many threads, Arc. And a note on the record: Rc, Arc, and Weak entered the standard library through library changes, not RFCs — there is no accepted RFC to cite for them, however often one is improvised. Arc predates the language's first stable release, arriving as part of the transition away from the garbage-collected pointers of the language's earliest designs.[shared-ownership]

Every owner can read; what happens when two of them want to write? The shared handle needs a new kind of mutation — the next page.

Takeaways

  • Shared ownership is opt-in and typed: Rc in a signature says many owners, one thread; the language default stays one owner per value.
  • Reference counting is a tiny local GC — reachability updated a few instructions at a time, the free at the last drop, deterministic by construction.
  • A reference cycle defeats the count: each node holds the other's share, neither count reaches zero, and the leak takes the destructor's side effects with it.
  • A weak reference views without owning: downgrade makes it, upgrade answers Some while the value lives and None after — death is in the type of the answer.
  • Arc is Rc with an atomic count: a locked instruction per update is the visible price of sharing across threads; Rust guarantees memory safety and, in writing, never leak-freedom.
