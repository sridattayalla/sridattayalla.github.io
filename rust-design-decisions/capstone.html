Part Seven — Abstraction and Synthesis

The Whole Language in Two Programs

Fourteen pages of machinery — ownership, borrowing, lifetimes, the heap menu, the thread badges, the escape hatches — and one question left standing: does it all fit together into programs you would actually write? This page answers with two. The first is the shape every shared-state service grows into: a cache written by a few threads and read by many. The second is a small pool of worker threads fed from a queue. Every type in both programs is a decision this book has already justified; the walkthrough names each one, and the last section walks the whole loop a single time.

Program one: the shared cache

Start with the cache. Two writer threads insert three entries each; three reader threads take five read locks each; after every thread joins, main takes one last read lock and prints the tally. The final line is deterministic no matter how the threads interleave, because it runs after the joins — everything racy happened before it, under the lock's rules.[capstone]

Read the type at the center — Arc<RwLock<Cache>> — as three decisions, each one a page of this book.[capstone]

  • The struct stays plain. No Cell, no RefCell inside Cache, because nothing shares one field of the cache: the whole instance is the unit of sharing. Interior mutability is a point tool, applied exactly where mutation meets sharing — and in this program that point sits outside the struct, so the struct needs none of it.
  • Arc, not Rc. The handles cross thread boundaries, and the refusal you met on the Send and Sync page — the E0277 that names Rc as not Send — is what Rc would say here. Arc, and not a plain reference either: a spawned thread may outlive the scope that built the cache, so spawn demands owned, 'static handles — the rule working as designed, not an obstacle to route around.
  • RwLock, not Mutex. Three readers for every two writers, and a read needs only a shared reference — a mutex would charge the writers' exclusivity against the readers too, serializing reads that interfere with nothing. And the nesting order is the lock's whole trick: it guards the data, not the handle. Mutex<Arc<Cache>> would lock the pointer while every holder of a clone kept reading the pointee freely — the sharing must sit outside the lock.

The two remaining marks are smaller. The unwrap on every lock() call is the poisoning decision from the interior-mutability page: if a writer dies holding the write lock, the next unwrap halts instead of reading torn state — failure propagated exactly where it cannot be silent. And the readers drop their guard inside the loop, at a line you can point to: a guard is a value with a scope, and where it releases is written where it is bound — the lifetimes page's refusal, working in your favor now.[capstone]

Program two: the pool

The second program needs one more word before it makes sense. A thread pool is a fixed set of worker threads created once, up front, and fed work from a queue — instead of one thread spawned per task. The program below builds a minimal one: a channel carries closures from main to three workers; when main drops its sender, the channel closes, and everyone exits in order.[capstone]

Every type here is a page of the book.[capstone]

  • The job: Box<dyn FnOnce() + Send + 'static>. Four decisions in one line. Box, because a dyn value is unsized and a channel slot must be a fixed size — the traits page's fat pointer, boxed behind a stable address. dyn, because job closures are heterogeneous: one per call site, an open set, the ladder rule from the last page. Send, because the job crosses to whichever worker runs it. 'static, because the pool cannot borrow from main's stack — the same bound the cache program paid, for the same reason.
  • The receiver: Arc<Mutex<Receiver>>. Both wrappers are forced. The channel has many producers but one receiver consumed by many workers — shared ownership, because the receiver must outlive whichever worker grabs it; exclusivity, because the receiver is single-consumer by design, so the workers take turns through the mutex. The sender side needs no lock: each producer clones its own.
  • The receive: a let of its own. The recv() call happens in a let statement, and the match runs after it. The mutex guard is a temporary of that statement — it drops at the semicolon, and the lock is released before the job executes. Move the receive into the match's scrutinee, the expression it tests, and the guard lives through the whole arm: the program stays correct, but every job runs serialized through one lock, and the pool quietly stops being a pool. One semicolon is the difference.

And the shutdown: drop(tx) is the entire protocol. Closing the channel makes recv() return an error — not a failure, but the designed message that no more jobs will ever arrive. The workers break out of their loops; main joins each one; the final line prints after the last job completes. Deterministic teardown, RAII applied to concurrency — and the error-handling page's lesson in miniature: this failure mode is control flow, chosen on purpose.[capstone]

The rule the whole book teaches

Why not put Arc on everything, then, if it composes this well? Because the type is the sharing policy, and the widest policy is rarely the honest one.[capstone]

A unique owner — the value itself, a Box, a plain borrow — tells the next reader who frees and when. An Arc handle says anyone may be the last, and backs the claim with an atomic counter charged on every clone and drop, plus the leak you met on the Rc and Arc page: a reference cycle keeps its members' counts above zero forever, and nothing warns you. Widening sharing is not free; it is a claim about the program's shape.[capstone]

So the rule, stated once and plainly: prefer the most restrictive type that works — the value itself, then a borrow, then a box, then shared handles — and add interior mutability only at the exact point where mutation meets sharing. The cache program shares because threads genuinely outlive the scope that built the data. The pool boxes because dyn is unsized. Everything else in both programs is borrows and plain values — and a reader can tell which by looking at any signature.[capstone]

The loop, walked once

Here is the whole book as one loop. Walk it clockwise from the top; every arrow is a refusal turned into a type.[capstone]

Memory must be freed exactly once, and the machine will not do it for you — the constraint. Rust's answer: every value has exactly one owner, and destruction follows ownership. Ownership alone is too poor for real programs, so values move between owners — and copy when they are plain data, and clone when they say so. Most code wants to use a value without taking it, so references: one exclusive or any number of shared, the aliasing rule the borrow checker enforces at compile time. References must not outlive what they point at — lifetimes, written out where inference cannot close the gap. Some values must outlive their scope or grow without moving — the heap: Box for unique ownership at a stable address, Rc and Arc when the handle must multiply. Sharing meets mutation — interior mutability: Cell, RefCell, Mutex, each moving the aliasing check to the place it can actually run. Data crosses threads — Send and Sync, badges derived from fields and composed automatically, refusals aimed at data races. Some correct programs the checker cannot prove — unsafe, the audited hatch, its invariants inherited by hand. One invariant is special — never move — so Pin wraps it in a type and the async machinery stands on it. Programs fail — two tiers: expected failure as values in Result, propagation through the visible ?, violated invariants as the halting tier. Behavior must abstract over types — traits: one impl per trait per type, a copy per type or a call through a table.[capstone]

And the two programs in the center use every piece: an owner per value, borrows checked, guards released on lines you can point to, handles shared only where threads demand it, mutation locked only where sharing demands it, failures carried as values, closures boxed behind stable addresses, shutdown delivered as a designed error.[capstone]

The bill, and the promise

What does Rust charge for the loop? Ceremony, honestly stated. The annotations: lifetimes written out when inference runs dry, a ? on every fallible call, a match arm for the case you would rather ignore. The vocabulary: Send, Sync, Pin, dyn — a name for every guarantee, learned once and then read everywhere. The discipline: the most restrictive type, the smallest hatch, the drop you can point to.[capstone]

What it buys is the first page's catalog, inverted. In safe code there is no dangling pointer, no double free, no use after free, no data race — not because you are careful, but because the programs that would contain them do not compile. The guarantees are local and mechanical: read a field's type and know who may touch it; read a signature and know what crossing it costs. The escape hatches exist — the audited block, the halting panic, the opt-outs — and each is marked in the source, each findable by the next reader.

That is the design. The promise is not that you will not make mistakes; it is that whole classes of mistakes cannot be written down. The two programs above are what the machinery looks like when it is all working: a handful of ordinary types, each one a decision you can now name.

Takeaways

  • One constraint drives the whole design: memory must be freed exactly once, and every mechanism in the book is a refusal turned into a type that answers it.
  • The type states the sharing policy: prefer the most restrictive type that works — the value, the borrow, the box, then shared handles — with interior mutability only where mutation meets sharing.
  • Both programs are the ladder in action: the cache pays Arc and RwLock because threads genuinely share mutable state; the pool pays Box, dyn, Send, and 'static because jobs cross threads unenumerated.
  • Concurrency safety is composition: badges derived from fields, locks that poison on the way out, channels whose errors are shutdown signals, teardown by dropping a sender.
  • The loop closes: from the constraint through traits and back, each mechanism exists because the previous one refused something — and the refusals, not the features, are why the safe programs compile.
