Part Six — The Escape Hatches

Unsafe: The Escape Hatch

Eleven pages of guarantees, and not one of them magical: the compiler proves what it can see and refuses what it cannot. This page is about the price of that honesty — the correct programs the checker rejects — and the marked region Rust offers for exactly them. The word unsafe does not mean broken, and it does not mean fast. It means: the compiler stops proving here, and you start.

Why the hatch exists

The previous page ended on the checker's honesty: some correct programs it cannot prove. The Book states the design flat out:

"Unsafe Rust exists because, by nature, static analysis is conservative. When the compiler tries to determine whether or not code upholds the guarantees, it's better for it to reject some valid programs than to accept some invalid programs."[unsafe-pin]

And the Rustonomicon — the manual for this territory — frames the default the same way:

"Safe Rust is the true Rust programming language. If all you do is write Safe Rust, you will never endure a dangling pointer, a use-after-free, or any other kind of Undefined Behavior."[unsafe-pin]

Between those two quotes sits the hatch itself. An unsafe block is a region opened by the word unsafe, inside which exactly five operations become legal that safe code refuses. One correction before anything else, in the Book's own words: the hatch does not turn off the borrow checker. Inside the block, borrows are still tracked, moves still happen, lifetimes still hold. What changes is a short, enumerable list:[unsafe-pin]

  • Dereference a raw pointer — an address without the checker's promises: it may be null, unaligned, or dangling, and safe code refuses to follow it at all.
  • Call an unsafe function — a function whose own contract says "caller proves the preconditions."
  • Access or modify a mutable static — global state any thread could touch.
  • Implement an unsafe trait — the previous page watched the standard library do this for Arc's badge.
  • Access the fields of a union — storage where overlapping layouts are the point.

Five doors, each opening onto territory where a promise that the machine cannot check is made by a person instead. The canonical reason to open the first one is worth a page of its own.

Read the refusal with the borrowing page's rule in mind. Two &mut from one source is exactly the shape of aliasing — and aliasing is what exclusive references exist to prevent. That the two ranges are disjoint is arithmetic: mid is a runtime number, the halves are the lower and upper parts of one length, and no overlap is possible. But the type system does not do arithmetic on runtime numbers. It sees two exclusive references into one value, draws the only conclusion its rules allow, and refuses — the honest boundary the Book described, working exactly as designed. Note even the help line: the standard library ships the answer to this exact shape, and the compiler points at it.[unsafe-pin]

Now notice what the checker still does. The returned references borrow slice — the lifetimes page's machinery still enforces that they cannot outlive it, hatch or no hatch. The block is a hole in one wall, not the demolition of the building: everything outside the five doors keeps its guarantees, and the function's signature is honest to its callers — safe to call, because the audit happened inside.[unsafe-pin]

The invariants you inherit

Open a block and you inherit the proofs the checker would otherwise have made. The property at stake has a name: soundness — the guarantee the whole design exists to deliver, that safe code cannot cause undefined behavior. A library whose safe surface lets undefined behavior through has a soundness hole, and it is the worst bug a Rust library can have.[unsafe-pin] What you personally take over comes in three families:

  • Aliasing: never materialize two live &mut to the same location. The E0499 refusal exists to prevent this; inside the block, you are the one arguing it cannot happen.
  • Validity: references must be non-null, aligned, and pointing at initialized data of the right type. Following a dangling raw pointer is undefined behavior — the founding page's failure catalog, back by hand.
  • Ownership: destruction runs exactly once per value. Misusing from_raw_parts_mut can manufacture two owners for one allocation — a double free, the C ending this book opened with.

None of these are checked when you open the block. All of them are checked everywhere else. That asymmetry is the entire cost of the hatch, and the next section is the discipline that keeps it payable.

The safe abstraction pattern

The pattern that makes the hatch livable has a name: a safe abstraction — a safe function whose body contains an unsafe block, whose entry checks establish the block's preconditions, so that callers — who can only call it safely — can never misuse it. The whole standard library is built this way: the previous page's badge assertion for Arc, and this page's split_at_mut, are the same shape.[unsafe-pin]

The Rustonomicon's discipline for writing one is short enough to memorize:

  • Keep the blocks small. Every line inside is an audit obligation, and audits scale with lines.
  • Check the preconditions at the safe boundary — the assert! in the fixture is the shape: a cheap check that makes the hand-made argument rest on facts.
  • Write the argument down. The SAFETY comment in the fixture is the convention: state what you proved and why it holds, because every later reader re-does your audit.

The costs are honest, and they compound. Everything the checker proved must now be argued by hand for that block, forever — not just once, but for every reader who inherits the code. The audit burden is the reason for the isolation discipline: keep the hatch small enough that a person can actually check it, and give the rest of the program its guarantees back through a safe signature.[unsafe-pin]

One invariant on the list you inherit is special: never move the value. It is common enough, and invisible enough, that Rust wrapped the promise in a type — the next page.

Takeaways

  • The hatch exists because static analysis is conservative: rejecting some valid programs is the price of never accepting invalid ones.
  • An unsafe block opens five doors — raw pointers, unsafe functions, mutable statics, unsafe traits, unions — and the borrow checker inside it still runs.
  • split_at_mut is the canonical case: two disjoint halves are provable by arithmetic and invisible to types, so the checker's refusal is the design working.
  • What you inherit is aliasing, validity, and exactly-once destruction — every promise the checker would have proved is now argued by hand.
  • The pattern that scales: small blocks, checked preconditions, written SAFETY arguments — a safe abstraction hands the guarantees back to every caller.
