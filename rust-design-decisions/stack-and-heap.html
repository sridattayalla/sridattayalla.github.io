Part Four — The Heap Menu

Stack and Heap: Owners and Views

The last part of this book constrained time. This one constrains space: where a value lives, who points at it, and what that costs. Rust puts the whole decision in the type, in plain sight — and the payoff is a signature that reads like a memory contract: what is borrowed, what is owned, what will be freed.

Two places, one visible decision

Values in a running Rust program live in one of two places. Inline: inside the current stack frame, or inside the value that contains them — a struct's fields, an array's elements, a local's bytes. Or on the heap: a long-lived pool that outlives frames, grows and shrinks while the program runs, and must be managed by someone. The founding constraint said Rust would manage it without a collector and without hidden machinery deciding placement for you.

The design choice that follows is that the decision is visible. Heap allocation — placing a value in that long-lived pool — never happens ambiently in Rust. It happens only when a type says so: String, Vec, Box, and their kin are library types built over the same primitive — a pointer plus an ownership policy — and because the type names them, a reader of a signature can count the allocations a function makes.

The comparison makes the choice sharp. In Java and Python, nearly every object is heap-allocated implicitly: allocating is what object creation does, the collector cleans up, and the programmer never sees a pointer. In Rust, values live inline by default and heap placement is a typed, countable decision. The book motivates the whole subject in one line — "whether a value is on the stack or the heap affects how the language behaves" — and the language's home page states the payoff: "with no runtime or garbage collector, it can power performance-critical services."[memory-layout] Three reasons, each already met in this book: the cost is visible in the type; the deallocation is deterministic, at the owner's death; and no hidden runtime decides placement for you.[memory-layout]

The canonical pair

Every placement story in Rust is a variation on one pair, so learn it once. String is the owning handle: three words in the owner's frame — a pointer to the bytes, the length in use, the capacity bought — with the bytes themselves on the heap. It grows by reallocation, it has exactly one owner, and it frees its bytes at that owner's death.

&str is the borrowed view: two words — a pointer and a length — aimed at bytes owned by someone else. Those bytes might be a String's buffer; they might be a literal baked into the program binary, which is why text literals are readable for the whole run. The view allocates nothing and frees nothing. It only reads.

The division of labor is the point. The owner pays for the buffer and eventually frees it; any number of views read it while it lives. Nothing in the heap bytes records who points at them — the words live in the owner's frame and in the views, and the rules from Part Three are what keep the two sides consistent.

Sized in words

The sizes are not folklore; the compiler prints them when asked directly:

Read the pattern, not the individual rows. Every reference to data whose length is not part of its type — text, runs of elements — is two words. Every owning handle of growable heap data is three. A reference to a single fixed-size value is one word, and next page's subject, Box, is also one word — the smallest owner there is.[memory-layout]

The middle rows of that output name the two concepts this page owns. A slice is a borrowed view of a run of elements — the type [T], which never stands alone: it is always reached through a reference, &[T]. A fat pointer is the two-word reference that reaches such data: the address, plus the length of what it reaches. &str and &[T] are both fat pointers.

A third kind of fat pointer exists — a reference to a value reached through a trait — carrying an address plus a pointer to that value's trait implementations. Its story belongs to the traits part of this book; the size fact is all this page needs: two words, same as the others.[memory-layout]

The same shape everywhere

The canonical pair is not about text specifically. The same shape repeats across the library: Vec<T> owns a run of elements — three words — and &[T] views that run — two words. Box<T>, next page's subject, owns one value behind a pointer — one word — and &T views it — one word. Owner and view, at every size.

The call takes_view(&owned) hands a &String to a function that asked for &str, and the compiler inserts the step itself: String promises to act as str when viewed, so &String flows into &str parameters. The rules are not per-type: any owner, any view, the same constraint.

The signature is a memory contract

Put the pair into a signature and it becomes a contract a reader can check without reading the body. fn f(s: &str) says: borrows, reads, allocates nothing, frees nothing. fn f(s: String) says: takes ownership, and will free the bytes at the value's death. fn f(v: &mut Vec<u32>) says: may grow the run — reallocation and all — while holding it exclusively.

Turning a view into an owner is a real allocation, priced and typed, and the compiler will not insert it for you: no silent copying, no hidden cost. The borrow was free; the conversion is not; the type says which is happening.

Views are borrowed and temporary; the simplest way to put a value itself on the heap is one word — the next page.

Takeaways

  • Values live inline by default; heap placement in Rust is explicit and typed — it happens only through a type that says so.
  • String is three words — pointer, length, capacity — owning heap bytes and freeing them at its death; &str is two words — pointer, length — reading those bytes.
  • References to data whose length is not in its type are fat pointers — address plus length — and the run they reach is a slice.
  • Deref coercion lets &String flow into &str parameters, so one borrowed signature accepts owners and literals alike.
  • A signature is a memory contract: &str borrows and frees nothing; String takes ownership and frees; the compiler enforces every clause.
