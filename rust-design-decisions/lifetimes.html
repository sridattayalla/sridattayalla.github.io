Part Three — Borrowing

Lifetimes: Constraints, Not Timers

The borrow checker answered every question on the last page by itself, because it could read the whole function body. Hand a reference to another function and the checker goes blind: it will not re-derive, at every call site, which value must outlive which borrow. So the answer travels in the signature, written in apostrophes. Lifetimes are the most misnamed feature in the language — not timers, not runtime state, but inequalities the compiler solves and then throws away.

Why the annotations exist

Every refusal on the borrowing page turned on one question: does the owner outlive every borrow aimed at its value? Inside one function the checker answers that by reading the body — every line is visible, every last use findable. A function, though, is checked once, as a unit, and its callers never see the body. They see the signature. If the signature does not state which value the returned borrow is tied to, the checker must refuse the call, because no body is available to prove it safe.

The book states the scale of the mechanism in one line — "Every reference in Rust has a lifetime" — and then shows that almost all of them are inferred: the annotations surface only where the signature alone cannot settle the relationship, where, in the book's words, "Rust can't tell"[lifetimes]

Settling it requires a word for the thing being constrained. A region is a span of the program — a stretch of the control flow — during which a reference is guaranteed to stay valid. The notation &'a T decodes as: this reference is usable within region 'a, because the value it points to is known to outlive 'a. One region outlives another when it lasts at least as long; the checker writes the claim as 'owner: 'a and treats it as an inequality to satisfy.

What a lifetime is not, then, matters as much as what it is. It is not a timer — nothing counts down. It is not runtime state — you cannot print one, measure one, or shrink one while the program runs. It is not a property of the value: the same value can be borrowed under many regions in one program. A lifetime annotation is a region variable the checker solves for, and the solution is erased before the program runs. Two spans make the whole game visible:

In the accepted shape, the borrow's region fits inside the owner's — the inequality has a solution, and the borrow is granted. In the rejected shape, the borrow's region sticks out past the owner's death, and no assignment of regions makes the program true. That is all a lifetime error is: an unsolved system, reported at the line where the contradiction was found.

The classic refusal

The error every Rust programmer meets first is does not live long enough. The program is small and the refusal is dense:

Read the anatomy in this order, not top to bottom: the binding is declared at line four; it is borrowed at line five; it is dropped at line six while still borrowed; and the borrow is used later, at line seven. The last annotation is the killer. If r were never used after the closing brace, the flow-sensitivity from the last page would shrink the borrow to nothing past line five and the program would compile. It is the use at line seven that stretches the borrow past the drop — the drop is only where the contradiction is detected, not what causes it.[lifetimes]

The misreading this breeds is predictable: does not live long enough gets read as the declaration is in the wrong place, and the learner starts moving braces. The fix is never the declaration. It is the later use: delete it, move it before the value dies, or give the borrow an owner that lasts as long as the use does. The remaining sections are about the notation that says which of those you chose.

The sugar: elision

If every reference needed its region spelled out, every signature in every program would drown in apostrophes. Most do not, because of lifetime elision: the rules that let common signature patterns leave the annotations out entirely. The rules are three.[lifetimes] Each reference in an input position gets its own fresh region when none is written. If exactly one region appears across the inputs, every elided output position receives it. And in a method, the region of the &self or &mut self receiver flows to elided outputs.

The middle rule erases the apostrophes from most of the language. The first line of the program two sections below — fn first_word(s: &str) -> &str — has one input reference, so the output inherits its region, and the checker reads the signature as if the region had been written on both. Nothing was guessed: the pattern is unambiguous, so the sugar is safe.

Structs get no sugar

Functions get the sugar because they have a fixed shape — references flow in at known positions, one result flows out — and three rules can cover that shape. A struct has no shape anyone can read at a use site. A struct value is stored in locals, returned from functions, nested inside other values, held exactly as long as whatever holds it. There is no signature to consult at each of those places, so the constraint must be stated once, in the type itself.

What the compiler will not do is pick a meaning for you; that refusal is why it demanded the annotation.

Reading the family

The last two refusals are a matched pair — two ways for a value to die while a borrow aimed at it is still live:

The first refusal, E0515, is the owner inside the function: make owns its s, s dies when make returns, and no caller's region can contain a value that is already gone — the refusal says exactly that: returns a reference to data owned by the current function. The second, E0716, is the temporary: a value created inside a statement lives only to the end of that statement, and the borrow it fed is still live at the next line, kept alive by w's use. It is the most common lifetime error in practice, and rustc's help writes the fix out: bind the value to a let first, then borrow the binding.[lifetimes]

Three misreadings account for most of the remaining flailing. Reaching for &'static everywhere: the static lifetime is the region that spans the entire program, and only two kinds of data can honestly claim it — values baked into the binary, and values deliberately kept for the whole run. Most attempts to stamp 'static onto an ordinary borrow are refusals, not acceptances. Reading 'a on an output as if it created a region: it names a relationship among the inputs and nothing more. And expecting the sugar in structs or in trait methods: elision covers function signatures, and that is all it covers.

Annotations constrain time — which spans must contain which. Where a value lives in space is a separate decision, made from a small menu of placements, and it is the subject of the next part of this book: the menu itself, and the pointer types that walk between its entries.

Takeaways

  • A lifetime is a region constraint — a span of control flow in which a reference must stay valid — solved at compile time and erased before the program runs.
  • Annotations exist because signatures hide bodies: the outlives relationship must travel in the type when the checker can no longer read the code that proves it.
  • Elision is sugar with three rules; a lone input region flows to the outputs, which is why most functions never spell an apostrophe.
  • Two input references into one output leave the relationship ambiguous — the refusal asks you to name it — and structs get no sugar: the constraint lives in the type.
  • Read does-not-live-long-enough backward: the later use keeping the borrow alive is the fact to change, not the place where the value dies.
