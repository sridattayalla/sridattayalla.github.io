Part Two — Ownership

Move, Copy, Clone

Assignment in Rust has a menu of exactly three behaviors, and the type — not the writer — picks the dish. This page is why the cheap one must be earned, what the compiler checks before granting it, and what the one explicit duplicate costs.

The menu

The last page ended on a clause inside a compiler error, the one implying that some types are exempt from moves. This page is the complete picture. Every assignment, every argument passed to a function, every value returned asks the same question — what happens to the value? — and the answer is always one of three words, chosen by the type, never by the call site.

Two of the three words name traits — a trait is a named promise a type can make: most traits are lists of methods the type must provide, but a few are just marks the compiler checks for. The menu:

  • Move — the default, from the last page. Ownership transfers; the source name retires; for a String, three words change hands and the buffer goes with them.
  • Copy — the earned exemption. A type carrying the Copy trait — a mark, not a method — is duplicated instead: assignment makes a shallow copy — the value's own bytes, and nothing they point at — and both names stay alive.
  • Clone — the explicit duplicate. Clone is a trait with one method, .clone(), that you call by name; for types that own memory, it makes a deep copy — the value's own bytes and everything they point at.

C++ serves the same three dishes but hides the prices: a = b may invoke a copy constructor the type's author wrote — a full duplicate, an allocation — indistinguishable at the call site from copying an integer. Rust's rule is that the syntax must tell the truth about cost: the cheap operation is spelled plainly, the expensive one is spelled loudly.[ownership] That rule is the whole design of this menu.

Why Copy is earned

The exemption cannot simply be claimed, and the reason is the double free you watched two pages back. Suppose bitwise duplication were allowed for any type — what would it do to a String?

Two live headers, both aimed at one heap buffer. When their scopes end, both destructors hand that buffer back — the double free again, this time wearing a struct costume. So the compiler grants the mark only under a rule you can check yourself, field by field: a type may be Copy only if every field is Copy — and the kinds of fields that own claimed memory never are.[ownership]

The name field, by contrast, is a pointer into the program's fixed text: it owns nothing, so copying it is honest. The error message draws exactly that line — this field does not implement `Copy` — and it is the double free from the start of this book, caught at compile time instead of by the sanitizer.

Copy in action

Both names survive every assignment: a and b are separate fives, p and q separate points, and pulling a value out of the array leaves the array whole. A number owns nothing — its bytes are the entire value — so duplicating it cannot create a second claim on anything. The honesty extends through aggregation: a struct of Copy fields is Copy, a tuple of Copy values is Copy, an array of Copy elements is Copy — which is why the #[derive(Copy, Clone)] line on Point succeeds: the derive asks the compiler to supply the implementations field by field, and Point's single field passes.

The derive line always names both marks, and must: the language specification requires that "everything that is Copy must also be Clone".[ownership] The pairing is not decoration. Copy types never move on assignment — but code can still ask them for a duplicate by name, and that request must find a method to call. The small mark and the named method are one contract in two forms.

The explicit duplicate

When a type owns claimed memory, assignment moves it — and if you genuinely need two live names, the move must be undone by hand. The word for it is the method that appeared in the last page's error text:

Both names print, because both are alive: the duplicate allocated a second buffer and copied every byte of the string into it. That is the cost model, and it is never hidden — a fresh claim on the heap, a full copy of the contents, sized by the data. The compiler prices it honestly too: the help line on the last page's error read consider cloning the value if the performance cost is acceptable, and that is the trade, stated by the tool whose job is to state it. No other line in the language duplicates an owner: not assignment, not passing to a function, not returning. One word, .clone(), and the cost is always in view.

The decision procedure

The whole menu collapses into one question you can ask of any type: does it own memory it must hand back?

  • No — its bytes are the whole value. Derive Copy and Clone; assignment duplicates; both names stay alive; the cost is a few bytes copied and nothing else.
  • Yes — it holds a claim. Assignment moves it; duplicate explicitly with .clone() when a second live name is truly needed; nothing implicit will ever duplicate it for you.

The dividing line is ownership itself, which is why this menu lives on the ownership pages. A number owns nothing, so copying it is always honest; a String owns a buffer, so copying its header would counterfeit a second claim. The compiler enforces the line twice — at the derive, field by field, where you met the refusal — and at every assignment, where a type without the mark simply moves.

But notice what moving costs in expressiveness. To let another function look at your String, you must hand over the whole thing — or pay for a duplicate just to have it read. That is heavy-handed, and Rust knows it: cloning every read is wasteful, and moves give away too much. Functions need to look at a value without taking it. That mechanism — and the checker that enforces it — is the next page.

Takeaways

  • Assignment means one of three things, chosen by the type: move (the default), Copy (implicit duplicate), Clone (explicit duplicate).
  • Copy must be earned: every field Copy, and no field owning claimed memory — the derive is refused otherwise, naming the field (E0204).
  • A shallow copy duplicates the value's own bytes; a deep copy duplicates everything they reach. Copy is always shallow; Clone is where deep copies happen.
  • Everything that is Copy must also be Clone — the derive line asks for both marks.
  • The decision procedure is one question: does the type own memory it must hand back? No — Copy. Yes — move, and duplicate by name when needed.
