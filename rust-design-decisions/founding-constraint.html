Part One — The Constraint

The Constraint: Safe, Fast, No Runtime

Rust's rules stop looking arbitrary the moment you watch what they forbid. This page shows the five memory failures the whole language exists to prevent — real C programs, real checker reports — and the bill the known alternative charges to avoid them.

The two routes

You know the trade from the first page: any two corners of the triangle are easy to buy in an existing language, and Rust insists on all three. Its rules only make sense against the two routes that came before — what each one costs is the motivation for the third.

The first route hires a caretaker. A garbage collector is machinery that runs alongside your program: every so often it stops everything, walks its records of every live object, decides which of them nothing can reach anymore, and hands the unreachable memory back. Your code never returns memory; it just stops pointing at things. Safety falls out of the machinery — you cannot use memory after it is gone, because it is never gone while you can still point at it.

The second route hands you the keys. In C you claim memory by asking for a number of bytes, and you hand it back yourself — whenever you like, in any order, with nothing checking. The language trusts you completely. Every program in the next section is legal, compilable C.

Rust's founding question was whether the compiler itself could prove, before the program ever runs, that every hand-back happens exactly once and no handle aims at anything that has already died. If the proof happens at compile time, the third corner comes free: no caretaker, no pauses, no resident machinery. The price is that programs the compiler cannot prove get refused — and learning to read those refusals is what the rest of this book is for.

Where memory lives

Both routes — and Rust's third one — manage the same two places a program keeps data. They are worth naming precisely, because every failure in the next section is a handle crossing between them wrongly.

The stack is an area of memory wired to function calls. Every call pushes a frame — the call's parameters and its local variables — onto the top; every return pops that frame off. The stack is fast precisely because the discipline is rigid: a local variable lives exactly as long as the call that created it, and not one moment longer.

The heap is a pool the program can claim pieces of at any time, by asking for a number of bytes, and hands each piece back when done. Heap blocks have no tie to any call: they live until someone returns them.

The asymmetry between the two is where the danger lives. A frame dies the instant its call returns. A heap block dies only when handed back. But a pointer — an address stored in a variable — can be copied anywhere: into a frame that survives longer, into a structure, into another thread. When the thing it points at dies first, the C standard is blunt about what remains: the stored pointer value becomes indeterminate, an address aimed at memory the program no longer owns (the C draft standard, N1570 §6.2.4p2).[c-failures]

Why C, in a Rust book?

Because every refusal you meet in Rust is the mirror image of one of these five programs. In C, all five are undefined behavior — the standard's category for effects it refuses to define, which voids every guarantee the moment one happens. Learn the failure, and the rule that forbids it stops being arbitrary.

A dangling pointer

A dangling pointer is a pointer to memory that has already died. The classic birth: a function hands back the address of its own local variable.

The mechanics, in order: borrow_local's frame — including the four bytes holding local — is popped the instant the function returns, and the slot is immediately reusable by any later call. The pointer survives; the thing it points at does not. The forty-two is gone; the address remains, aimed at whatever the next call stores there. The checker names the offense exactly: stack-use-after-return — using a stack slot after its call returned.

Use after free

A use-after-free is a pointer to a heap block that has already been handed back. The same shape as the dangling pointer; the memory just died by a different verb.

free does not wipe the block — it returns the twelve bytes to the allocator for reuse. The read races with that reuse: it may see the old scores, a freshly allocated object, or, if the pages went back to the operating system, a crash. Nondeterministic by construction — which is what makes this family of bugs hard to reproduce and prized by attackers.

The container that moved

An iterator invalidation is a saved pointer or index into a container that no longer matches the container's storage — because the storage moved or was handed back while the pointer was being kept. The most common form in real code: the container grows.

Growth means relocation: realloc claims a bigger block, copies the data across, and hands the old block back. The program never called free itself — the container did, on its behalf, the moment it grew. first still holds the old address, which now aims into a freed block. This is use-after-free wearing a container costume, and it is the most common shape the failure takes in mature codebases: the saved index or pointer that quietly died when the container grew.

A data race

A data race is two threads touching the same memory at the same time — at least one of them writing — with nothing forcing an order. The program below counts to two hundred thousand using two threads that each add one to the same counter a hundred thousand times.

On machines with weaker memory ordering it is worse than a lost update: without an imposed order, one core's write may not even be visible to the other. The usual C fixes — locks, or special instructions that fuse the three steps into one — are discipline rather than guarantees; the compiler happily builds the unfixed version.[c-failures]

The caretaker's bill

A caretaker deletes the first four failures by construction — memory is never handed back while anything can reach it — and shrinks the fifth to a bookkeeping problem. But the machinery is real, and it charges a real bill. Three line items.

Pauses. To find dead memory, a tracing caretaker must stop your program and walk its records. Oracle's tuning guide for its flagship virtual machine names the cheapest configuration "the serial, stop-the-world collector". Go's team, after years of shrinking pauses, wrote the target down: "We now have an objective of 500 microseconds stop the world pause per GC cycle. Perhaps a little sandbagging here."[gc-costs] Read the second sentence twice. The state of the art is an aspiration, not a guarantee — and the aspiration is measured in fractions of a millisecond, every cycle, forever.

Overhead. Every store of a pointer into an object may need recording — the write barrier. Memory sits dead between walks, unreachable but not yet handed back. And the machinery itself — the runtime you met on the first page — is resident, working whether your code is or not.

Destruction timing. When does a value die under a caretaker? When the walk gets to it — if it ever does. A destructor is the code that runs when a value dies, releasing what it holds, and a caretaker makes its timing a scheduling question. Java's deprecation of finalization states the limit flatly: "the GC provides no guarantee that any finalizer will ever be called."[gc-costs]

So every garbage-collected language re-imports by hand the discipline its machinery removed: Java's try-with-resources, C#'s using, Go's defer. Each is a way to buy back deterministic destruction — release at a moment fixed by the shape of the code, not by the machinery's schedule.

Why anyone cares

Is the danger real, or academic? Three keepers of enormous C and C++ codebases have counted their own wounds.

Microsoft's security response team, over a decade of its own vulnerability data: "~70% of the vulnerabilities Microsoft assigns a CVE each year continue to be memory safety issues."[gc-costs]

Chromium, on its security bug tracker: "Around 70% of our high severity security bugs are memory unsafety problems (that is, mistakes with C/C++ pointers). Half of those are use-after-free bugs." That count covered 912 high or critical severity security bugs since 2015.[gc-costs]

Android, where the fix is visibly working: memory-safety vulnerabilities fell from 76% of Android's total to 35% between 2019 and 2022 as new code moved to memory-safe languages — "Android 13 is the first Android release where a majority of new code added to the release is in a memory safe language."[gc-costs] In 2022 they were still 86% of critical-severity bugs — and in Android's Rust code specifically: "zero memory safety vulnerabilities discovered."[gc-costs]

C hands you no tool that prevents any of the five failures — the compiler builds all five, happily. A caretaker prevents them and delivers the bill above. Rust's bet is that one rule, checked before the program ever runs, deletes all five at once, with no resident machinery. That rule is ownership. It is the next page.

Takeaways

  • C keeps data in two places: the stack, whose frames die with their calls, and the heap, whose blocks die only when handed back.
  • All five classic failures share one shape: a handle aimed at something already dead, or two hands claiming one thing.
  • Every failure on this page tripped a checker on this machine — the reports are captures, not illustrations.
  • The caretaker route buys safety at a price: pauses, bookkeeping, and destruction timing nobody can promise.
  • Rust's answer is one compile-time rule — ownership — and it is the next page.
