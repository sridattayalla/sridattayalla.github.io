Part Six — The Escape Hatches

Pin: A Promise Not to Move

The previous page ended on the strangest-sounding invariant you can inherit: never move the value. Most values survive a move perfectly well — this page is about the ones that do not, why the compiler cannot tell them apart by looking, and the wrapper that turns the distinction into a checked fact. One promise, one opt-out, and the reason paused computations can live on the heap without fear of the floor moving.

The pointer hidden inside a value

The unsafe page inherited three families of proofs — aliasing, validity, exactly-once destruction — and ended by calling one of them special. What kind of value cannot survive a move? Picture a struct with two fields: a String, and the address of that String — a pointer stored inside the very struct that owns the data. A value is self-referential when one of its fields points into the value itself.

Move the struct and the String lands at a new address; the pointer field is bytes, and bytes do not update themselves. Follow the pointer after the move and you read whatever lives at the old address now — the founding page's first C failure, the dangling pointer, hidden inside a single value. No hatch, no trait, no second thread: a plain move manufactures it.

Why have you never met one in safe code? Because the checker refuses the shape at the source. A struct cannot hold a reference into its own body — the reference's lifetime would have to outlive the struct that contains it, and the lifetimes page's checker refuses exactly that knot. The hatch from the previous page is what makes one constructible: a raw pointer carries no lifetime, so the checker does not follow it. And notice the asymmetry when you build it — creating the pointer is safe, no hatch required; following it is the audited act. Aim the pointer with one safe write and you hold a value that is correct at exactly one address. The missing piece is a way to promise it stays there.

The promise, made a type

The missing piece is a wrapper whose entire meaning is one sentence. Pin is a wrapper around a pointer that promises: the value behind this pointer will never move before it is dropped. And pinning is the act of placing a value behind that promise. RFC 2349 wrote both the motivation and the goal:[unsafe-pin]

"A common motivation for this is when a struct contains a pointer into its own representation — moving that struct would invalidate that pointer."[unsafe-pin]

"Provide a reference type where the referent is guaranteed to never move before being dropped."[unsafe-pin]

The mechanics of keeping that promise are the box page's, promoted from convenience to guarantee. You cannot stop the owner of a stack local from returning it, passing it, or assigning it — so Pin does not police owners. Instead, the promise is made at the moment the value goes behind a handle that never moves its pointee: the Box. Moving a Box moves one pointer — the handle travels, the value stays at its heap address — and Box::pin, or Pin::from on a box you already own, is the sealing act.

And notice which line needed the hatch: not the store, which is safe, but the follow — the read through the raw pointer — with its written argument for why the address still holds.[unsafe-pin]

The opt-out, and two refusals

Before the refusals, the opt-out, because it answers the obvious objection: almost every type you will ever write points nowhere into itself. Unpin is the marker that says so — a marker trait in the send-sync page's sense, an empty badge, attached automatically to nearly every type: a String, a number, a Vec — all safe to move, always, so the promise would buy them nothing. The badge is also removed automatically when any field lacks it, and one field exists purely to do that: PhantomPinned, a marker with no data and no methods whose entire job is subtracting the default. Our struct carries it — that is the marker field from the demo — so SelfRef refuses the badge.[unsafe-pin]

Read the error's spine: the badge is missing, because it is missing within the type. The help lines point at the two sanctioned acts — the pin! macro for a value that never leaves the current scope, and Box::pin when it must — and our demo used the third spelling of the same act, Pin::from on a box we owned. What the refusal is really saying: a promise made for a stack address is a promise the owner can break by returning, assigning, or passing the value — so the constructor refuses to make it.[unsafe-pin]

Second: the promise must not be breakable afterwards. The dangerous tool is &mut — the borrowing page's exclusive reference, which permits std::mem::swap, which is a move wearing a helper's badge. Hand one out to the pinned body and the promise is void. So the accessor that would hand it out simply does not exist for our type:

The error is the design. get_mut was found — in the standard library's own source, quoted in the note — with exactly one gate on it: the badge. For a type that carries the badge, mutable access is business as usual. For ours, the method is not callable, and the promise holds.[unsafe-pin]

Why async needed it

Now the customer that made this machinery load-bearing. A future is a value that represents a computation which has started, paused, and may be resumed — not a callback, not a thread: a value. And async is the keyword that makes one: write an async function, and the compiler compiles the body into a state machine whose fields are the function's locals, paused at each suspension point and resumable from there.

Why does that need the promise? Pause an async function mid-body and look at what the state machine holds: its locals, as fields. One local can hold a reference to another local — the borrowing rules allow it inside the body — and once both are fields of one struct, that reference is a pointer into the same value. The state machine is self-referential, manufactured by the compiler, not by you. Resume it after it moved and the stale self-pointers are followed — the founding failure again, this time with no unsafe block in sight.[unsafe-pin]

That is the sentence that explains the whole mechanism. The runtime that schedules these values — the executor, the code that resumes futures — moves them constantly: into queues, into task tables, out again. Moving the body is the one fatal act; moving the handle is the scheduler's daily business. So the executor's currency is exactly our demo's type: a pinned, boxed handle — the handle moves freely through the machinery while every paused body stays put on the heap. The RFC's own phrase, "especially important recently with work on generators," was written before the async story settled; generators grew into it, and a niche tool for intrusive lists became the floor under all of it.[unsafe-pin]

The bill

The costs are honest. A pinned value cannot move — even safely, even to a better home — for the rest of its life, which for a long-lived task is the program's duration. Code that touches pinned data must speak the vocabulary: Pin<&mut T> where plain &mut T used to be — a cost every low-level library paid once, in its interface, forever. And the opt-out spreads: a field without the badge makes the containing struct lose it too, so PhantomPinned's single effect compounds through composition, the same way the send-sync badges did.[unsafe-pin]

And the symmetry with the previous page completes the design. Unsafe is the hatch out of the checker's world — the place where you make the machine's promises by hand. Unpin is the door back into the ordinary world — the place where you say, in a type, "this value points nowhere into itself; the promise would buy nothing here." Most types walk through that door by default, because most values are exactly that. The ones that cannot — the paused computations, the intrusive structures — stay behind the promise, and the rest of the program moves around them at full speed.

Every page so far has assumed the happy path: values are constructed, used, and dropped, and nothing fails on the way. Failure needs the same discipline the rest of the language has — visible, typed, and predictable. The next page is that discipline.

Takeaways

  • A self-referential value holds a pointer into its own body; a move strands that pointer — the founding page's failure, hidden inside one value.
  • Pin is one promise as a type: the value behind this pointer never moves before it is dropped; pinning happens at the moment the value goes behind a stable handle.
  • The demo's proof: the handle moved, and the field address, stored pointer, and text were unchanged — the promise held by construction.
  • Two refusals bracket the promise: Pin::new will not promise for a movable owner; get_mut does not exist without the Unpin badge.
  • A paused async function is a self-referential state machine, which is why the executor's currency is the pinned, boxed handle.
