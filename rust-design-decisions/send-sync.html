Part Five — Mutation and Threads

Send and Sync: Thread Safety in the Type System

The previous page moved one check into the types; this page is about the two that were already there. Rust's entire answer to thread safety is a pair of empty traits — badges named Send and Sync — awarded to types automatically by their shape and read by the compiler at every thread boundary. Two names, one rule each, and the question "is this safe to share?" becomes a fact you can read off a signature.

Two questions, two badges

Start where the last page ended: RefCell's counter is plain memory, and two threads consulting it at once is the race the language exists to prevent. How does the compiler know which types may cross a thread boundary? Not by reading the code inside them — the answer has to work for types whose bodies the caller will never see.

The mechanism is a marker trait: a trait with no methods and no behavior, only a name a type can carry, like a badge pinned to it. Nothing calls the trait's functions, because there are none; the compiler's checks read the badge, and that is the entire mechanism.

The badge is also awarded without anyone asking. An auto trait is a marker whose implementation is derived from a type's shape: a struct earns it when every field earns it, and loses it when any field loses it. The machinery is as old as the ownership system — the same proposal that made moves the default, RFC 0019 on opt-in builtin traits, introduced it — and the negative half is the powerful one: one non-thread-safe field refuses the badge for the whole struct.[send-sync]

The two badges the thread system reads, in the Rustonomicon's own words:

"A type is Send if it is safe to send it to another thread. A type is Sync if it is safe to share between threads (T is Sync if and only if &T is Send)."[send-sync]

Unpacked: Send is about a move — ownership transfers, the value travels, and the sending thread never touches it again. Sync is about a share — the value stays put while references to it live on several threads at once. The one-line link between them is the parenthetical: sharing a T between threads means handing out &T, so T is Sync exactly when &T is Send.

The composition rule, read bottom-up

The matrix hides the most instructive rule of all: badges compose, and the composition is written by hand. Arc<Vec<u32>> is Send — not by exemption, but by an assertion in the standard library whose entire content is a bound:

Read it as a promise with two conditions: Arc<T> may move to a new thread exactly when T may move and T may be shared. Why the second condition, when a move sounds like the single-owner case? Because moving an Arc is never really a move: the sending thread usually keeps a clone, and now both threads hold handles to the same contents. If both can act through &T at once, T had better be Sync — the share, not the move, is what actually happened.[send-sync]

Two lessons ride along. First, the help line is the language pointing at the door you meant: aliasing and mutation between threads want RwLock or an atomic — the checking and blocking wrappers from the previous page. Second, that word at the start of the standard library's assertion is the language's marker for a hand-made promise, the one the marked-code hatch at the end of this book is about. Arc pays it; Rc declines — which is the entire behavioral difference between the two counting siblings.[send-sync]

Fearless concurrency — and what it does not promise

Step back and state what the badges buy. A data race — the memory-level bug, not the logic-level one — needs four ingredients together:

  • two aliases to the same location,
  • at least one of them writing,
  • access from more than one thread at the same moment,
  • and no synchronization ordering them.

Safe Rust makes the first two unwritable in every composition. &mut is exclusive — the borrowing page's refusals, E0502 and E0499, are exactly the aliasing rejection. & looks shared but does not write — except through the interior-mutability wrappers, and those restore the fourth ingredient by checking or blocking. Crossing a thread boundary demands the badges: Send for the move, Sync for the share. The race needs all four ingredients; the types will not hand you two of them at once.[send-sync]

The community named the result. The Book's concurrency chapter: "We've nicknamed this aspect of Rust fearless concurrency." The post that introduced the phrase in 2015 said it more plainly: the type system prevents data races at compile time, and thread-safe usage is checked like memory usage. And the language's first developer had said the same from the start: correct concurrency and general memory safety "are two sides of the same coin," both served by isolation and control of mutation.[send-sync]

What the nickname does not promise is drawn just as carefully. Deadlocks: two mutexes taken in opposite orders wait forever — the badges were fine, the schedule was not. Logic races: atomics order memory, not intent; your flag flips in an order that is valid and still wrong. Leaks: the honesty clause from the counting page applies across threads too. The guarantee is data races only — but that one is total, and it is checked before the program runs.

Scoped threads: fencing borrowed data

One demand in the captured error deserves its own ending: 'static. A spawned thread may outlive the function that started it, so it may capture only owned data. What if the data is borrowed — a buffer several threads should scan? Plain spawn refuses the borrow; the answer is to shrink the promise instead:

thread::scope takes a closure and guarantees, structurally, that every thread spawned inside it joins before the closure returns — the scope itself holds the join handles. Inside that fence, borrowing is fine: the threads cannot outlive the borrowed data because they cannot outlive the scope. The closures above capture data by reference — no move, no clone — and the compiler accepts them because the fence is in the signature, not in a convention.[send-sync]

That fence has a history. The original design relied on destructors to join at scope end; a thread arranged to leak itself could break that promise, so the API was pulled before the first stable release. It returned in version 1.63 with the guarantee made structural — the scope holds the handles, and joining no longer depends on destructors running.[send-sync]

Every guarantee so far was checked from types alone. The checker is deliberately conservative — some correct programs it cannot prove. Rust's answer is a marked region where the promise is yours to make — the next page.

Takeaways

  • Send and Sync are marker traits: empty of behavior, full of meaning — the compiler reads them at every thread boundary and nothing else does.
  • Both are auto traits, derived from a type's shape: one non-thread-safe field refuses the badge for the whole struct, and wrappers propagate absence as faithfully as presence.
  • Send is the move and Sync is the share, linked by one line — T is Sync exactly when &T is Send — because sharing means handing out references.
  • Badges compose through hand-stated bounds: Arc is Send when its contents are Send and Sync, so Arc<Cell<u32>> is refused for Cell's missing badge — read the E0277 bottom-up.
  • Fearless concurrency covers data races and only those: deadlocks, logic races, and leaks remain yours; scoped threads fence borrowed data by joining structurally.
