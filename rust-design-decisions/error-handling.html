Part Six — The Escape Hatches

Errors and Panics: Two Tiers of Failure

Every page so far assumed the happy path: values are constructed, used, and dropped, and nothing fails on the way. This page is about the two ways things fail — the kind a caller can plan for, and the kind that means the program itself is wrong — and the rule Rust draws between them: expected failure becomes a value in the type, and the other kind becomes a stop you can see from the source.

Two kinds of failure

Failure is not one phenomenon. A missing configuration file is expected — the caller may retry, pick a default, or ask the user. A file that was there a moment ago and is gone now is a race — something you believed about the world stopped being true. An index you proved was in range, arriving out of range, is worse: your proof was wrong, and the program's next step cannot be trusted. Rust's error design begins by refusing to blend these.

A failure is a recoverable error when the caller is expected to handle it — anticipated, part of the contract, and the program remains trustworthy afterwards. The missing file is the canonical case. The two designs Rust rejected sit at the extremes of the same problem. Exceptions make failure invisible: any call, anywhere, may divert control flow, so every function is secretly fallible and exception safety becomes an audit you perform on all of it — the C++ experience at scale. Null pointers and errno codes make failure deniable: the type says the call succeeded, the value says otherwise, and the compiler cannot see which calls lie.

Tony Hoare, who invented the null reference, has called it his "billion-dollar mistake" — his estimate, in a 2009 talk, of what that deniability has cost.[error-handling]

Rust's answer is one tier per kind. Recoverable failure is an ordinary value, carried in the return type, confronted by every caller. The other kind is a distinct, visible operation that stops the program at the line where the belief broke. The next two sections take them in order.

Tier one: failure as a value

Tier one is an enum — the founding page's shape, nothing more:

The consequence is in the signature. A function that can fail returns Result<T, E>: the success value and the failure reason, side by side, and there is no way to obtain the one without confronting the other — the compiler enforces the match. Fallibility is documentation the type checker reads. And it cannot be silently dropped: Result carries the #[must_use] attribute, so ignoring the returned value is a warning; the way to decline the check is to write it out — let _ = f(); — an explicit opt-in to ignoring failure.[error-handling]

Why not Option everywhere — the type with the same shape and no error payload? Because the E is the contract. The parse function in the demo below returns the concrete failure type of string parsing: the signature does not just say "this can fail," it says what fails. The caller who wants the reason has it, typed. The caller who wants to accept failures of any shape can erase the types into a single boxed error — which is the demo's other function, and the subject of the last section.

The question mark: propagation you can see

Values are only half the design; the other half is how they travel. Handing a failure to the caller instead of handling it here is propagation. Without help it is ceremony: a match per fallible call, wrapping and re-wrapping the error at every floor it passes. Languages with exceptions automate this completely — and pay with invisibility. RFC 243 found the balance:[error-handling]

"Requiring an explicit ? operator to propagate exceptions strikes a very pleasing balance between completely automatic exception propagation, which most languages have, and completely manual propagation."[error-handling]

The postfix ? is that balance. Applied to a Result, it means: on success, yield the value; on failure, hand it up. The desugaring is one match:[error-handling]

The interesting piece is the From::from call. When the inner call's error type differs from the function's own error type, the operator converts — an io::Error into the function's error type, Box<dyn Error> — using a conversion the standard library provides for exactly this composition. That is the glue that lets small, concrete errors flow into larger, aggregated ones without manual wrapping at every step.

Tier two: the halt, and the walk

The second tier has a name and a mechanism. A panic is the unrecoverable tier: a macro that reports where the invariant broke and stops the current thread of execution. The stopping is unwinding — the walk back up the stack, running each value's destructor as its frame is left, until a boundary stops the walk.

Read the capture in order. The report prints first — file, line, column, and the message. Then the walk: the two guards drop in reverse order of declaration — second, then first — because leaving a frame runs its destructors from the last local to the first. That is the ownership page's drop discipline surviving failure: memory is still freed, locks still released, half-written files still cleaned up. Then the boundary catches, and main continues — the walk stops exactly where catch_unwind was placed. Notice what arrives: Err(Any { .. }) — an opaque value. You can log that something failed; you cannot ask it questions. That opacity is deliberate: this tier is for boundaries — foreign-function edges, test harnesses — not business logic. Rust's answer is not try/catch, and the payload's shape says so.[error-handling]

What belongs on this tier: violated invariants. A slice index the compiler cannot prove in range is checked at run time and halts on violation — the assert! from the unsafe page, now with its name. A missing file is expected failure — tier one. A file that vanished after you checked it is a race — a belief about the world proven false — tier two. The tier is not about severity; it is about whether the program remains trustworthy after the news.[error-handling]

The mechanism itself is a choice, not a law. The default — unwinding — exists so destructors run. The panic=abort profile setting removes the walk entirely: smaller code, no destructors on failure, and a panic kills the whole process. Embedded targets and some server configurations choose it.[error-handling]

The boundary rules

Two boundary rules complete the design. First, the walk must not cross into foreign code undefended. RFC 2945 records the history:[error-handling]

"Prior to this RFC, any unwinding operation that crossed an extern "C" boundary ... caused undefined behavior."[error-handling]

Since that RFC, the rules are defined: with unwinding on, a Rust panic escaping an extern "C" boundary aborts the process — defined behavior, not undefined; foreign unwinding crossing into Rust the same way remains off-limits; and the extern "C-unwind" ABI declares two-way unwinding for code that wants it.[error-handling]

Second, the decision procedure between the tiers, in one question: can the caller do something about it? If yes — the failure is expected and answerable — return a Result and let the type carry the contract. If no — the failure means a belief was wrong and the next step cannot be trusted — halt, loudly, at the exact line. When in doubt, prefer the value: a caller can always turn a Result into a halt; a halt cannot be turned into a Result.

The bill is ceremony. Matching, the operator, custom error types for libraries that want precise contracts, and occasionally a library shaped like anyhow or thiserror to automate the plumbing. That is the price of failure you can see — the founding page's trade, discipline for safety, paid one more time.

One convenience deserves a last look before the part ends: the single catch-all error type — Box<dyn Error> — that read_config used to accept failures of any shape.

A boxed error of any type — Box<dyn Error> — appeared three times on this page and we never asked what it costs. That question opens the last part — the next page.

Takeaways

  • Two kinds of failure: the recoverable error the caller is expected to handle, and the violated invariant that makes the next step untrustworthy — Rust refuses to blend them.
  • Tier one makes failure a value: Result carries success and reason side by side, the signature documents it, and ignoring it is a warning.
  • The question mark is visible propagation: on failure it returns, converting through From — the glue that composes small concrete errors into larger ones.
  • Tier two halts with a report and unwinds: destructors run in reverse order on the walk, so ownership discipline survives failure — and abort removes the walk for code that prefers it.
  • The decision rule: if the caller can answer it, return a Result; if a belief is proven false, halt. A Result can become a halt; a halt cannot become a Result.
