Non-blocking I/O

The previous chapter ended with a contract: you ask the kernel for data, and your thread does not come back without it. This chapter breaks that contract, on purpose, by flipping one bit in the kernel's bookkeeping for a descriptor. The flip is small. The new vocabulary it creates, a socket that answers "not ready yet" instead of confiscating your thread, is the foundation everything in the rest of this book is built on. It also introduces a trap that has burned every programmer who ever found it, so we will step on that too, deliberately, before learning to avoid it.

Flipping the contract

Every descriptor carries mode flags in the kernel's bookkeeping, and one of them is O_NONBLOCK. Set it, and the descriptor becomes non-blocking: the kernel promises that calls on it will never put your thread to sleep. If the operation can be finished right now, it is. If it cannot, the call fails immediately instead, and you learn about it through the error convention from chapter 3. On an already-open descriptor you flip the flag with fcntl:

#include <fcntl.h>
#include <unistd.h>

/* switch an already-open descriptor into non-blocking mode */
int flags = fcntl(fd, F_GETFL, 0);
if (flags < 0) {
    perror("fcntl F_GETFL");
    return 1;
}
if (fcntl(fd, F_SETFL, flags | O_NONBLOCK) < 0) {
    perror("fcntl F_SETFL");
    return 1;
}

Now ask an empty socket for data:

char buf[256];
ssize_t n = read(fd, buf, sizeof buf);

if (n >= 0) {
    /* got it: n bytes were waiting */
} else if (errno == EAGAIN || errno == EWOULDBLOCK) {
    /* nothing waiting: the answer is "not ready yet", not "broken" */
} else {
    perror("read");
}

That EAGAIN is the star of the chapter. Where a blocking socket would have carried your thread off to the wait queue from chapter 4, the non-blocking one returns -1 instantly with errno set to EAGAIN, "try again". POSIX permits a second spelling, EWOULDBLOCK, for exactly this case, and portable code checks for both; on Linux they are the same number. The crucial reading is that EAGAIN is not an error in the everyday sense. Nothing is broken. The question was just asked a moment too early, and it may well have a different answer a millisecond from now. The same answer can come from write when the socket's outgoing buffer is full: not broken, merely full, try again.

One bookkeeping detail worth noticing: the flag lives on the descriptor, not on the call. Once flipped, every operation through that descriptor follows the new contract, reads, writes, even accept on a listening socket, until you flip it back. Non-blocking is therefore a property of the arrangement between you and the kernel, recorded kernel-side, exactly like the descriptor's other open-file bookkeeping from chapter 3. Two descriptors for the same socket can even disagree, though you would need dup and a good reason to want that.

Two different questions

Stop and appreciate what just changed, because it is easy to wave past. Under the blocking contract there is one question: "give me data, and take as long as you need". The kernel answers by owning your thread for the duration. Under the non-blocking contract the question splits in two. There is still "give me data", answered with bytes or with EAGAIN. And there is now a second, separable question hiding inside the failure: "was there data at all?" That second question has a name. A descriptor is ready when the thing behind it has something for you right now: bytes to read, or room to write. Readiness is a property of the moment, and EAGAIN is how the kernel says "no, not at this instant", without promising anything about the next one.

Feel the shape of a server built on this. One thread holds descriptors for three sockets and visits them in turn: ask A, EAGAIN; ask B, EAGAIN; ask C, five hundred bytes, process them, reply. No thread was ever confiscated, so the same thread really is serving three clients, and nothing stops it from serving three thousand. This is the first honest glimpse of the design this whole book walks toward. Its flaw is equally visible: on a quiet day, almost every visit returns EAGAIN, so the thread spends its life asking questions whose answers are almost always no. Visiting in turn is exactly the busy loop below, wearing better clothes.

The deep change is who owns the wait. A blocking call confiscates your thread and hands the waiting to the kernel. A non-blocking call keeps the thread and hands you the fact of waiting. Nothing about the socket got faster; data still arrives when it arrives. What changed is who is holding the thread while the answer is pending, and therefore how many simultaneous pendings one thread can juggle. In principle: all of them. In practice, you are about to meet the catch.

The busy-poll trap

You have a socket that answers "not ready yet", and a program that wants data. The obvious next move is to keep asking:

ssize_t n;
for (;;) {
    n = read(fd, buf, sizeof buf);
    if (n >= 0) break;                       /* got something */
    if (errno != EAGAIN && errno != EWOULDBLOCK) {
        perror("read");
        return 1;
    }
    /* nothing yet... so ask again, immediately */
}

This is busy-polling: retrying a non-blocking call in a tight loop until it succeeds. It feels productive. It is the opposite. Each read is a full trip through the kernel's door, and a modern core can make millions of those trips per second, so the loop ties up one entire core at flat-out usage doing literally nothing. Your thread is runnable every instant, the kernel's scheduling code sees a hungry worker, and every cycle it burns is a cycle some other thread, on a machine with a real job, cannot have. Multiply by one loop per connection and you have rebuilt the C10K arithmetic from chapter 4 with a worse shape: before, at least, the waiters were asleep.

The trap catches good programmers because the loop works. It returns correct data, quickly, and on a demo with one connection the CPU meter is easy to ignore. Then it ships to a server with a quiet socket per loop, and the machine runs hot while accomplishing nothing. Any tight retry loop around EAGAIN, without a sleep between attempts, is this bug wearing a work uniform.

The textbook patch, sleeping between retries, fixes the CPU crime but commits a smaller one: if you sleep a millisecond between asks, you add up to that much delay to every arrival, and you are still asking about one descriptor at a time. Sleeping in a loop is busy-polling with a conscience. Neither version is what you actually want.

The missing half

Line up what you have and what you need. You have sockets that never confiscate a thread, and an error code that means "not ready at this instant". You need to serve ten thousand of them with a handful of threads. The naive loop fails because it keeps asking each socket, one at a time, forever. What is missing is the reverse arrangement: a single question, asked once, that sleeps until any one of your many descriptors has something to say, and then tells you which ones. One door-knock covering every waiter, with your thread asleep in between, paying nothing while nothing happens.

The kernel does have that question; Unix has actually grown three successive answers to it over the decades, each fixing the last one's scaling flaw. Finding out why the first two answers were not good enough is the fastest way to understand why the third one powers, nearly unchanged, every high-performance server you have ever used. That story is the next chapter.

In this chapter

  • Setting O_NONBLOCK makes a descriptor non-blocking: calls on it never put the calling thread to sleep.
  • Reads on an empty non-blocking socket return -1 with EAGAIN (or EWOULDBLOCK): not broken, just not ready yet.
  • Readiness is a property of the instant: data to read or room to write, right now; the failure code quietly answers "is there data?" separately from "give me data".
  • Busy-polling, retrying against EAGAIN in a tight loop, ties up a whole core while accomplishing nothing; it is the classic misuse of non-blocking I/O.
  • What is still missing is one sleeping question covering many descriptors at once, which is exactly where the next chapter goes.
