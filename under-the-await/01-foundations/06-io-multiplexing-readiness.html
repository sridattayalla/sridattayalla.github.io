I/O multiplexing: the readiness model

Chapter 5 left you with sockets that never confiscate a thread and an error code meaning "not ready yet", and the observation that retrying in a loop burns a core. What was missing was a single question that sleeps until any one of many descriptors is ready, then names the ready ones. That question exists. Unix has actually answered it three times, select first, then poll, then epoll, each answer fixing the previous one's scaling flaw. This chapter walks all three, because the flaws are the fastest way to understand the fix, and because the machinery this book is heading for sits directly on the third answer, nearly unchanged. This is the most load-bearing chapter in Part 1; take it slowly.

The idea: many conversations, one question

The telephone engineers had a word for carrying many calls over one cable: multiplexing. It means exactly this: several independent streams of information sharing one wire, with some mechanism for keeping them separate. I/O multiplexing brings the idea to descriptors. Instead of your program asking each socket "ready yet?" in turn, it hands the kernel one list and asks one question: "which of these are ready right now?" The call sleeps until at least one is, then returns the answer. Your thread pays for exactly one nap, no matter how many thousands of descriptors are silent.

Notice how perfectly this complements chapter 5. The multiplexing question never touches data; it only reports readiness. The reads and writes that follow are the non-blocking kind, so they cannot strand your thread either. Combine the two and the C10K arithmetic from chapter 4 dissolves: ten thousand waiters no longer cost ten thousand sleeping threads, because nobody is sleeping per-connection anymore. There is one sleeper, asking one question, and it only sleeps when there is genuinely nothing to do.

select: the first answer

The original interface builds the question out of bitmasks. You prepare three fixed-size sets of descriptors, for reading, writing, and errors, and hand all three to select along with a maximum wait. The kernel scans every descriptor in every set, notes which are ready, rewrites the sets in place to show only those, and returns a count. Your code then walks the rewritten sets and serves whoever survived.

It works, and it worked for decades. But two walls are built into the type itself. First, the sets are fixed-size, and the size is FD_SETSIZE, 1024: descriptors numbered 1024 or higher simply cannot be monitored, and a busy server's descriptor numbers climb quickly. The man page is blunt that this will never change. Second, the whole arrangement forgets everything between calls. The kernel rescans every descriptor you listed, every single time, and your code rescans the rewritten sets to find the survivors, and you rebuild the original sets for the next call because the call just destroyed them. The man page itself calls the in-place rewriting "a design error that is avoided in poll and epoll".

The second answer: arrays instead of bitmasks

The second answer replaces bitmasks with an array of small structs, one per descriptor, each holding the descriptor number, the events you care about, and a slot for the kernel's reply. No fixed cap now: the limit is just the system's cap on open descriptors per process. And the kernel fills in the reply slots rather than destroying your input, so you stop rebuilding the list every call.

But the deeper cost survives untouched. The kernel still scans every entry on every call, and your code still walks the whole array afterward to find the entries with replies. Both sides are proportional to the number of descriptors monitored, and the number of descriptors is precisely the thing that grows when you are big. At ten thousand connections, mostly idle, every wait means a ten-thousand-entry scan to discover that five sockets have work. The question was right; the bookkeeping was in the wrong place.

epoll: the kernel keeps the list

The third answer, Linux's epoll, makes one structural move: stop re-telling the kernel what you care about. An epoll instance is a kernel object that remembers. You create it once with epoll_create1 (yes, it is itself a file descriptor; chapter 3's everything-is-an-integer strikes again), and then you register each socket exactly once with epoll_ctl. From then on, the kernel maintains two lists for you: the registration list, every descriptor you asked to monitor, and the ready list, the subset with something to say. The registration happens when a connection arrives, not when you ask the question.

Here is the part worth reading twice. The kernel does not build the ready list when you ask. It appends to the ready list at the moment I/O activity happens, in the kernel's own packet-handling code, as events occur. So epoll_wait is not a scan at all; the man page describes it as fetching items from a list that is already built. Its cost grows with the number of events it returns, not with the number of descriptors you monitor, which is the difference between doing work proportional to your problems and work proportional to your size. Ten thousand idle connections cost memory, roughly 160 bytes of kernel bookkeeping each, and nothing else. No rescan, no sleeping thread, no burned core.

An echo server's core, in C

The whole pattern fits in three fragments. First, create the instance and register the listening socket, once:

#include <sys/epoll.h>
#include <unistd.h>

/* one epoll instance for the whole server */
int epfd = epoll_create1(0);
if (epfd < 0) {
    perror("epoll_create1");
    return 1;
}

/* register the listening socket, once */
struct epoll_event ev;
ev.events = EPOLLIN;              /* report "readable" */
ev.data.fd = listener_fd;
if (epoll_ctl(epfd, EPOLL_CTL_ADD, listener_fd, &ev) < 0) {
    perror("epoll_ctl");
    return 1;
}

Second, the loop: sleep on the one question, then dispatch on the answer. The last argument to epoll_wait is a maximum wait in milliseconds; -1 means wait indefinitely:

struct epoll_event events[64];

for (;;) {
    /* sleep until something happens */
    int n = epoll_wait(epfd, events, 64, -1);
    if (n < 0) {
        perror("epoll_wait");
        break;
    }
    for (int i = 0; i < n; i++) {
        if (events[i].data.fd == listener_fd) {
            /* new client: accept(), then register the new socket */
        } else {
            /* existing client: readable, drain it (next fragment) */
        }
    }
}

Third, when a client socket is reported readable, read it until the kernel says otherwise. On a non-blocking socket, that means looping until EAGAIN, not reading once:

/* inside the "existing client" branch */
for (;;) {
    char buf[4096];
    ssize_t k = read(fd, buf, sizeof buf);
    if (k > 0) {
        handle_bytes(fd, buf, (size_t)k);
        continue;                 /* maybe more: keep draining */
    }
    if (k == 0) {
        close(fd);                /* the peer hung up */
        break;
    }
    if (errno == EAGAIN || errno == EWOULDBLOCK)
        break;                    /* drained: nothing more right now */
    perror("read");
    break;
}

Count the threads in that server: one. Count the syscalls per quiet moment: zero. When five hundred clients are silent, the single thread is asleep inside epoll_wait, costing nothing, and the moment any packet lands, the kernel has already placed that socket on the ready list, so the wake-up hands your thread a precise to-do list. This loop, register once, sleep on the question, act on the answer, drain until EAGAIN, is the skeleton of every serious network server on Linux, whatever language it is written in.

Level-triggered and edge-triggered

One epoll decision remains, and it is subtle enough to deserve its own vocabulary. When the kernel reports a socket as ready, how long does the report last? The default is level-triggered: a descriptor is reported whenever it is in the ready state, and it keeps being reported on every subsequent epoll_wait for as long as data remains unread. If you read only half the available bytes, the next wait mentions the socket again. Used this way, the man page says, epoll is "simply a faster poll". Hard to break, mildly redundant.

The alternative, enabled with the EPOLLET flag, is edge-triggered: the kernel reports a descriptor only when readiness newly appears, a transition rather than a state. Read half the bytes and wait again, and you will likely wait forever: the man page walks a pipe example where epoll_wait hangs despite data sitting in the pipe, because no new arrival happened to re-trigger the report. The rule that makes edge-triggered safe is the one the echo server above already follows: always drain to EAGAIN, on a non-blocking socket, before you go back to waiting. That is why the third fragment loops.

Why would anyone accept edge-triggered's sharp edges? Fewer redundant wake-ups, and that last table row: when several threads wait on one epoll instance and an edge-triggered descriptor becomes ready, the kernel wakes exactly one of them, which the man page highlights as a deliberate optimization. The machinery at the heart of this book makes a specific choice on this exact fork; when you reach Part 4 and see which, come back here and you will know why the question was hard.

Not just Linux

Epoll is a Linux affair, but the pattern is not. The BSD and macOS world has kqueue, the same shape of idea, one queue you register with and one call that fetches ready events, with a broader appetite: it can also report child processes ending, signals arriving, timers firing, and files changing. illumos offers event ports to the same end. The APIs differ enough that portable code wraps them behind one interface, and every serious high-performance library does exactly that. Remember this paragraph; it explains a layer you will meet in Part 4.

So here is the state of the machine after six chapters. A thread can ask one sleeping question about thousands of descriptors, and the kernel will answer with a precise list. Waiters no longer cost threads, so the C10K arithmetic is dead. What remains is a change in the shape of your code: a program is no longer one thread per conversation telling a linear story, but one loop reacting to whatever the kernel says happened. That change, and the five classic ways of living with it, is Part 2. First, though, one more kernel contract deserves a look, because readiness is not the only deal on offer, and a newer kernel interface bets against it. That is the next chapter.
