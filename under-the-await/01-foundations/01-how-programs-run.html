How a program runs

You have launched programs thousands of times without once wondering what "running" means. This chapter makes you wonder, then answers. The machine underneath every language is the same: a CPU executing tiny steps one at a time, a handful of registers acting as its scratch paper, a call stack tracking where it is, and a hard border between your code and the operating system's core. C, Python, and JavaScript all compile or interpret down onto this machine, and so, many chapters from now, does the machinery this book is named after. If you want to understand how a server can hold ten thousand connections open at once, you start here.

The CPU: fast, literal, forgetful

Strip a computer to its engine and you find a chip doing one thing, over and over. It fetches an instruction from memory, decodes it, executes it, and starts again. An instruction is a single tiny step, a few bytes of machine code: add these numbers, copy this value there, jump to that address. That is the entire vocabulary. Your source code never reaches the chip as text; a compiler or an interpreter grinds it down to these steps first.

The chip keeps its working state in registers, a small set of named slots inside the CPU itself, each holding one number. Most are general scratch space. One is special: the instruction pointer always holds the address of the next instruction to fetch, and "running" is nothing more than the loop below, repeated billions of times per second.

Here is a two-line C function, and next to it roughly what a compiler emits for x86-64. Read the comments on the right; they carry the point.

int add(int a, int b) {
    int sum = a + b;
    return sum;
}

int main(void) {
    int total = add(40, 2);
    return total;
}
add:
    push   rbp           ; save the caller's frame pointer
    mov    rbp, rsp      ; start a new frame
    mov    eax, edi      ; eax = a     (first argument arrives in edi)
    add    eax, esi      ; eax += b    (second argument arrives in esi)
    pop    rbp           ; restore the caller's frame pointer
    ret                  ; jump to the saved return address

Notice what the chip never sees: variable names, types, the word sum. It sees values landing in registers, one instruction mutating them, and the return hop. Every language you have ever used ends up in this shape; the differences are buried in the translation.

The call stack: how calls remember where to go

Jumping into a function is easy. Coming back is the interesting part. When main calls add, the CPU jumps to add's code, and when add finishes, execution must resume inside main exactly where it left off, with main's locals intact. The machine's answer is one of the oldest structures in computing: the call stack.

Every live call owns a stack frame, a chunk of the stack holding that call's local variables, a few saved register values, and the return address, meaning the spot to resume when the call finishes. Calling pushes a new frame on top; returning pops it. The stack grows and shrinks all day as your program calls and returns, and a dedicated register, the stack pointer, always marks the current top.

high addresses
  +------------------------------+
  | argv, environment            |
  +------------------------------+
  | frame for main()             |
  |   locals: total              |
  |   return address: into the   |
  |     code that called main    |
  +------------------------------+
  | frame for add()              |
  |   locals: a, b, sum          |
  |   return address: into main  |
  +------------------------------+   <- stack pointer (rsp)
  |        (free space)          |
  +------------------------------+
low addresses

When add returns, its frame is not cleaned up so much as abandoned: the stack pointer slides back down, and the next call writes over the same bytes. Nothing needs tidying, because a frame's lifetime is exactly the lifetime of its call. That discipline, lifetimes bounded by calls, is why stack space is nearly free.

Linux gives each running program a stack of 8 MiB by default. That figure is virtual: the system reserves the address range but only converts pages to real RAM as the stack actually touches them. Deep recursion turns reservation into commitment very quickly.

Recursion makes the pile visible. Each recursive call pushes another frame, so a missing base case grows the stack until it slams into a guard page and the program dies with a stack overflow. Python raises RecursionError instead, stopping you at a fixed frame count, but the underlying geometry is the same one you can feel in C.

The heap: memory that outlives the call

The stack's rule, "die with your call", is exactly wrong for data that must survive it. Return a string the caller will keep for an hour, and that string cannot live in a frame that vanishes the instant you return. So practical languages offer a second region, the heap: a pool of memory where values live for as long as someone can reach them, independent of any call.

In C you work it by hand. malloc claims a region, free gives it back, and you chase the bugs when you get the bookkeeping wrong. Python and JavaScript hide the same region behind a garbage collector, which reclaims values once nothing can reach them. Either way, the division of labor is the same:

Call stackHeap
lifetimeexactly as long as the call until freed, or until nothing can reach it
who manages itthe call itself: push and pop you, or a garbage collector
costnear zero: move one pointer real work, sometimes a kernel request

One subtlety worth a sentence: each program sees its own private memory map. The addresses in your pointers are not physical locations; they are positions in a per-program virtual map that the kernel and the hardware translate behind your back. That is how two programs can both use address 0x400000 without colliding, and it is also part of the wall between programs, which brings us to the last piece of the machine.

Two worlds: user space and kernel space

CPUs can run at more than one privilege level. x86 hardware calls these levels rings, and operating systems use two of them: ring 0, fully privileged, and ring 3, restricted. The hardware itself enforces the rules. Code running in ring 3 cannot execute certain instructions, cannot touch the machine's control registers, and cannot read memory belonging to ring 0.

Your program runs in ring 3, a world called user space. It is a comfortably furnished cage. Your code can compute anything it likes with its registers, its stack, and its heap, but it cannot touch the disk, the network card, the screen, or another program's memory. All of that belongs to kernel space, the ring 0 world where the kernel, the operating system's core, lives and works on everyone's behalf. Without that wall, any buggy program could read another program's secrets, or hang the whole machine.

The kernel is not magic. It is a program, merely the most privileged one on the machine. Your program talks to it through one strictly controlled interface, and every request for a real resource crosses that line: every byte read from a socket, every file opened, every fresh chunk of memory the system hands out. Think of it as a bank teller's window. You cannot walk into the vault; you make a request, and the teller does the vault work on your behalf. Chapter 3 shows you the door itself. For now you only need the geography: there are two worlds, and the boundary between them is the most important line on the machine.

One last observation, and it is the one to keep. Everything a running computation needs is registers plus a call stack. Freeze a program mid-call, save those two things somewhere, restore them later, and it continues as if nothing had happened. That is not a fantasy. It is how the operating system keeps many programs alive on a few cores, which is the next chapter, and it is how, far ahead in Part 3, a suspended piece of work survives without a machine of its own. Hold the image: a frozen stack, waiting to resume.
