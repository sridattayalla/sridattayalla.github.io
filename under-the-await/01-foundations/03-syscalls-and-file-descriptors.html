Syscalls and file descriptors

You now know the machine has two worlds and one boundary between them. This chapter is about the door in that boundary. Every interesting thing your programs do, reading a file, accepting a network connection, sleeping, printing a line, is a request carried across it, and the kernel answers with small integers and error codes. Once you can see those crossings, you can count them, measure them, and eventually eliminate the ones you don't need. That last skill is most of what "high-performance I/O" means, so the door itself is worth ten minutes of your life.

The syscall: a controlled doorway

A syscall, short for system call, is your program's only way to ask the kernel for anything. There is no polite function library shared between the worlds; there is a machine instruction. On x86-64 it is literally named syscall, and it is a trap instruction: a special step that does not do arithmetic but instead flips the CPU into kernel mode and jumps to a fixed entry point that the kernel installed at boot.

The choreography is rigid, because rigidity is what makes the doorway safe. Your program places a syscall number in one register and the arguments in a few others, then executes the trap. The CPU, now privileged, lands in kernel code, which uses the number to look up a function in the syscall table, a numbered list of everything the kernel is willing to do for you. The kernel performs the work, places the result in a register, and returns to user mode, right after the trap instruction. Your thread never changed: the same registers, the same stack, just a brief, supervised visit to the other world.

Failure has a convention. Nearly every syscall returns -1 on failure and stores a small error code in errno, a per-thread slot saying what went wrong: file not found, permission denied, and, as you will learn in chapter 5, one particular "not yet" code that ends up mattering more than all the others combined.

A mode switch is not a context switch

Here is a distinction worth internalizing early. Crossing the boundary is cheap: the trip into kernel mode and back is measured at under 50 ns round trip. That is a mode switch, a privilege flip for the same thread, and it is not what chapter 2 was charging you microseconds for. A context switch, swapping which thread runs on the core, is a different and far more expensive event.

The two are related but independent. A syscall that finishes quickly, like getting the current time, never causes a switch: you cross, get your answer, and continue, with no one else ever having run. A syscall that must wait, like reading from a socket whose data has not arrived yet, is another story: there the kernel puts the calling thread to sleep, runs someone else, and that is a context switch. High-performance I/O is largely the art of getting many waits out of few threads, so keep the two costs separate in your head: crossings are almost free; waiting is what costs.

File descriptors: everything is an integer

When the kernel agrees to do something ongoing for you, open this file, connect this socket, it needs a way for you to talk about it later. The answer is beautiful in its smallness: a file descriptor, a small non-negative integer that indexes a per-process table the kernel keeps. Descriptor 3 is "entry 3 in my table of ongoing arrangements with the kernel". The integer is yours; the table entry belongs to the kernel, and it points at the kernel's own bookkeeping for that arrangement, formally an open file description, which remembers things like your position in the file and the mode you opened it in.

Every process starts with three of them, wired up before your main runs:

DescriptorMeaningUsual wiring
0standard inputyour terminal, or a pipe
1standard outputyour terminal, or a pipe
2standard erroryour terminal
3 and upwhatever you open nextfiles, sockets, pipes, and stranger things

That last row is doing heavy lifting. Files, TCP sockets, UDP sockets, pipes, the terminals your shell wires together, even kernel objects with no file behind them at all: all of them are file descriptors, all reached with the same read, write, and close calls. Unix decided decades ago that one uniform interface for byte streams beats a special interface per thing, and that decision is the foundation this entire book stands on, because the machinery of chapter 6 monitors many descriptors at once without caring what they are.

Two descriptors can point at the same underlying arrangement. Duplicate one with dup, or fork a process into two, and both sides hold integers referring to the same kernel-side bookkeeping. Closing your descriptor does not close the other one; the arrangement dies only when the last descriptor referring to it is closed. This sharing is why a shell can reconnect a program's output to a file and why the descriptor, not the file, is the thing your code actually holds.

strace: the X-ray machine

Everything above is invisible in normal programming, which is a pity, because Linux ships a tool that makes every crossing visible. strace runs your program and prints every syscall it makes, with arguments and results. If you adopt one investigative habit from this book, make it this one.

$ strace ./hello
execve("./hello", ["./hello"], 0x7ffc9c50 /* 24 vars */) = 0
brk(NULL)                               = 0x55e0dbaf0000
openat(AT_FDCWD, "/etc/ld.so.cache", O_RDONLY|O_CLOEXEC) = 3
...
write(1, "hi\n", 3)                     = 3
exit_group(0)                           = ?
+++ exited with 0 +++

That is the complete life of a program that prints three characters: the kernel loads it (execve), sets up its memory, and the very first thing after the trimmed setup noise is the write you asked for, followed by exit_group, the door marked exit. A dynamically linked binary makes a few dozen calls before main even runs; a statically linked one makes almost none. Put a real server under strace and you will see accept, read, write, and close churning in a loop, each line one trip through the door you now know the shape of.

The full dance in C

Here is the whole chapter as a program: open a file, read from it, write the bytes out, close it. Four calls, four crossings, every failure checked the way C demands.

#include <fcntl.h>
#include <stdio.h>
#include <unistd.h>

int main(void) {
    int fd = open("notes.txt", O_RDONLY);    /* get a descriptor */
    if (fd < 0) {
        perror("open");                      /* prints errno's message */
        return 1;
    }

    char buf[256];
    ssize_t n = read(fd, buf, sizeof buf);   /* fill buf, up to 256 */
    if (n < 0) {
        perror("read");
        close(fd);
        return 1;
    }

    if (write(STDOUT_FILENO, buf, (size_t)n) != n)
        perror("write");                     /* STDOUT_FILENO is 1 */

    close(fd);                               /* give the descriptor back */
    return 0;
}

Read it as a dialogue. You ask for a descriptor and get back, say, 3. You hand 3 to read with a buffer and a maximum length, and get back how many bytes actually arrived, possibly fewer than you asked for, or -1 with errno explaining the problem. You hand 3 to write with the bytes. Finally you hand 3 to close, and entry 3 is free for the next arrangement.

Notice the error convention: -1 plus errno, where errno is stored per thread, so two threads failing simultaneously cannot scribble over each other's reasons. C's perror just prints a readable version of it. Higher-level languages wrap all of this; Python's open() eventually performs exactly this dance.

Two instruments, then: a door with a strict knock, and integer handles for everything the kernel does for you. One question remains before the story gets interesting. What exactly happens when you knock, asking for data, and there is no data yet? The answer involves a sleeping thread, a queue inside the kernel, and the arithmetic that breaks naive servers, and it is the next chapter.

In this chapter

  • A syscall is a request through the boundary, made by placing a number and arguments in registers and executing a trap instruction; the kernel dispatches via its syscall table.
  • The mode switch across the boundary is cheap, well under a microsecond; a context switch caused by a waiting call is the expensive event.
  • File descriptors are small integers indexing the kernel's per-process table; files, sockets, and pipes are all reached through them.
  • Failures return -1 with a per-thread errno; successes return the answer, often the count of bytes moved.
  • strace shows every crossing a program makes, the cheapest possible education in what your software actually asks the kernel to do.
