Blocking I/O and the C10K problem

Chapter 3 ended on a cliffhanger: you knock on the kernel's door asking for data, and there is no data yet. This chapter is the answer, and the answer is where your thread goes while it waits. That single mechanism, called blocking, is the default behavior of nearly every I/O call you have ever written, and it is simultaneously the most comfortable idea in network programming and the reason a naive server falls over at ten thousand clients. Both halves are true, and this chapter does justice to each.

What blocking actually is

A call is blocking when your thread enters the kernel to ask for something and does not come back until the something exists. The thread does not spin and does not burn CPU. It sleeps, deeply and officially, and the kernel shakes it awake when the answer arrives. The step-by-step, for a read on a socket with an empty receive buffer, is worth walking slowly:

  1. Your thread traps into the kernel, as in chapter 3, asking for bytes from descriptor 3.
  2. The kernel checks the socket's receive buffer and finds it empty.
  3. Because the descriptor is in its default mode, the kernel does not answer "nothing yet". Instead it moves the thread off the ready list of runnable threads and onto a wait queue attached to that socket, marking it sleeping.
  4. The kernel's scheduling code immediately picks another runnable thread and performs a context switch to it. Your thread has left the building.
  5. Some time later, a packet lands. The kernel's network code fills the socket's buffer, finds the wait queue behind it, and moves your thread back onto the ready list.
  6. Sooner or later a core becomes free, the scheduling code picks your thread again, another context switch restores it, and the read finally returns with the bytes.

Reads are the common case but not the only one. accept blocks waiting for a new connection, connect blocks waiting for a handshake, and write can block when the socket's outgoing buffer is full. The unifying idea is the wait queue: whenever a kernel call cannot finish now, the calling thread beds down on a queue tied to the thing it is waiting for, and the kernel lends the core to someone else. From inside the program, this is a gift: your code reads like the story it tells. Ask for data, get data. The complexity of waiting is someone else's problem.

One misconception to retire early: a blocked thread is not wasting CPU. It consumes no cycles while it sleeps. What it consumes is a whole OS thread, stack, kernel bookkeeping, and all, per thing being waited on. The waste at scale is threads, not spinning. Remember that; it sharpens every tradeoff that follows.

A thread per connection: the honest default

Given blocking calls, the natural server writes itself: accept a connection, hand it to a fresh thread, let that thread's reads and writes fall asleep whenever they must. Every connection gets its own private thread, blocking is fine because each thread has nothing else to do, and the code stays dumb in the best way. In Python it fits on one screen:

import socket
import threading

def handle(conn):
    with conn:                      # closes the descriptor on return
        while True:
            data = conn.recv(4096)  # sleeps until bytes arrive
            if not data:
                break               # the peer closed the connection
            conn.sendall(data)      # echo the bytes back

listener = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
listener.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
listener.bind(("0.0.0.0", 8080))
listener.listen(128)

while True:
    conn, addr = listener.accept()  # sleeps until a client connects
    threading.Thread(target=handle, args=(conn,)).start()

Read it and notice how little there is to get wrong. Each connection is a file descriptor (chapter 3) owned by one thread; each recv is a knock on the kernel's door that turns into a nap when the client is quiet; each nap is a context switch (chapter 2) someone else pays for. For an internal tool, a database with twenty clients, or a build server, this design is not merely acceptable. It is correct: simple, debuggable, and honest about what the machine does.

The arithmetic of ten thousand

In 1999, Dan Kegel wrote a page titled "The C10K problem" that opened with a question: "It's time for web servers to handle ten thousand clients simultaneously, don't you think?" His observation was that hardware had stopped being the excuse. A busy site of the era already pushed ten thousand simultaneous clients through a single Gigabit Ethernet pipe; the machine could move the bytes. What could not move them was the server software, and thread-per- connection designs were exhibit A.

Run the arithmetic of one thread per client at ten thousand clients, using the numbers from chapter 2. Each thread reserves its own stack, 8 MiB by default on Linux, so 10,000 threads reserve roughly 80 GB of virtual address space. That reservation alone survives on a 64-bit machine, but it is not free: page tables and kernel bookkeeping for every thread, real RAM for every page of stack actually touched, and hard ceilings, since Linux limits a process to a few thousand to a few tens of thousands of threads depending on configuration. Creation cost compounds it: at roughly 5 to 20 µs per thread, creating ten thousand of them takes a noticeable fraction of a second, every time a burst arrives. And then the waiters start waking up.

A server with ten thousand connected but idle clients is fine: idle threads sleep cheaply. The pain arrives when traffic makes them runnable together. Hundreds or thousands of runnable threads per core mean the kernel's scheduling code switches constantly, each switch costing roughly 1.2 to 2.3 µs of bookkeeping plus the cache damage from chapter 2, and much of the work accomplished per switch is tiny: read a few hundred bytes, write them, sleep again. The machine spends its life swapping threads instead of moving bytes. Kegel's page, tellingly, catalogs the escape routes as variations on one theme: stop dedicating a thread to each waiter.

The seductive version of this failure goes "memory is cheap now, 8 MiB times ten thousand is nothing on a 64-bit box with plenty of RAM". Virtual is not free. Page tables, kernel structures, and committed stack pages all cost real memory, and the ceiling on total threads is a wall you hit at full speed, not a slope you slide down. The problem was never that any single thread is expensive. It is that none of them ever leave.

When blocking is exactly right

Before this chapter becomes a morality tale, an honest accounting. Most software serves tens of connections, not tens of thousands: internal services, databases with a known client population, daemons, CLIs, test harnesses. For all of these, thread-per- connection with blocking calls is the right answer, because the costs above are all per-connection and the connection count is small. The design buys simplicity, the most valuable currency in software, at a price that rounds to zero. Do not redesign your way out of a problem you do not have. The C10K problem is a problem of scale, and it arrives with its own signature: thousands of mostly idle connections that must all stay open at once.

So the goal is not "never block". The goal is: when you must hold ten thousand waiters open, stop paying one thread per waiter. But blocking is a package deal between you and the kernel: you ask for data, and you do not come back without it. To keep many connections on few threads, something about that contract has to change. The next chapter changes exactly one thing, the smallest possible thing, and it starts with a socket that refuses to wait.

In this chapter

  • A blocking call carries your thread into the kernel and leaves it sleeping on a wait queue until the answer exists; a sleeping thread burns no CPU, but it occupies a full OS thread.
  • Thread-per-connection servers are simple and correct for tens of clients; their per-connection costs only become fatal through multiplication.
  • C10K (1999) named the scale where software, not hardware, became the bottleneck: ten thousand simultaneous clients on one machine.
