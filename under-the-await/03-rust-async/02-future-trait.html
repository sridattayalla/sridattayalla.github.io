The Future trait and poll

Every async system you have met so far, from epoll loops to Python coroutines, had the same skeleton: something that can be asked "are you done yet?" and something that asks. Rust reduces that idea to its smallest possible shape and puts it in the standard library. It is one trait, one required method, and one enum with two variants. Everything else in Rust async, including all of Tokio, is built on top of this page.

The whole interface

Here is the trait, verbatim, from std::future:

pub trait Future {
    type Output;

    // Required method
    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>;
}

Take it apart piece by piece.

type Output is an associated type saying what the future produces when it finishes. A future that yields a String has Output = String; one that only signals completion has Output = (). There is no error lane baked in: failures are just values, like Result<T, E>, delivered through Output.

The method is named poll, and that name is a decision. To poll a future is to ask it a single question: "can you finish now?" The answer is the return type, Poll:

pub enum Poll<T> {
    Ready(T),
    Pending,
}

Either "yes, here is the value" or "no, not yet". That is the entire vocabulary of progress in Rust async. Notice what is missing: there is no "failed", no abort, no percentage, no partial results. A future is a computation that is either finished or not finished, and if you want richer outcomes, they ride inside Output.

The parallel with Part 1's kernel machinery is exact. epoll_wait also answers a yes-or-no readiness question for many file descriptors at once, and the std documentation for Future makes the comparison explicit: futures are like epoll, not like the poll(2) syscall. Asking "are you done?" is cheap and non-destructive; demanding "give me data now" is a different, heavier operation. The name is a wink at exactly that history.

Two strange parameters

The receiver is not the &mut self you might expect. It is self: Pin<&mut Self>: a mutable reference to the future wrapped in a type called Pin. Pin is a promise about the future's address, and the reason it exists is one of the best stories in this book. Page 6 tells it; for now, read the receiver as "mutable access to this future, with a guarantee attached".

The second parameter, cx, is a Context: a thin struct that today carries exactly one useful thing, a handle the future can use to request a re-poll when it can make progress. How a future can be woken without busy-waiting is the entire subject of the next page, so for today treat cx as "the handle you must consult before returning Pending".

Futures are lazy

Here is the behavior that surprises everyone coming from JavaScript or Python. Calling an async fn does not start anything. Nothing runs, nothing registers, no work happens at all. The call merely constructs a value, the future, and hands it back to you. The body of the async fn executes only while someone is actively calling poll on it. Futures are lazy: inert data until driven.

Compare the JS and Python coroutines from Part 2. A JavaScript promise starts working the moment you create it; the event loop picks it up on its own. A Rust future sits there like an unopened letter. If nobody ever polls it, the work never happens and the value is silently dropped. This is not a flaw; it is what lets the driving code decide when and where the first step of the work runs, and it is why "create a future and forget to await it" is such a classic Rust bug.

The contract

poll looks innocent, but it is governed by one of the strictest contracts in the standard library. Both sides, future and caller, are bound by it. Learn it now and half of Part 4 will feel obvious.

#RuleWhy it exists
1Return Ready as soon as the work is donePolling is asking, not waiting; delays propagate to every caller up the chain
2Never block, and return quicklyWhile poll runs, the thing driving it can do nothing else; one slow future starves every future behind it
3Before returning Pending, save the re-poll handle from cx and arrange for it to be triggered when you can progressOtherwise nobody knows to ask again, and the future hangs forever
4After Ready, expect no further pollsPolling a finished future is undefined behavior-adjacent territory: it may panic or misbehave
5Do not be polled in a tight loop; the engine should wait for the wake-up signalRe-polling a future that has nothing new is the busy-poll trap from Part 1 again
6Tolerate unnecessary wake-ups: re-check your state every pollWake-ups may be coalesced, and engines are allowed to be sloppy in the safe direction
7On every poll, update the saved handle to the one from the current cxA future may be moved between engines; only the newest handle is guaranteed valid

Rule 4 deserves a precision: the std docs say a future polled after completion "may panic, block forever, or cause other kinds of problems", but it must never be undefined behavior. In practice, well-behaved futures panic with a clear message, which is exactly what the Delay you will write on page 4 does with its finished state.

Rule 5 is the one that makes the whole system efficient, and it rhymes with the readiness model from non-blocking I/O: ask, and if the answer is "not yet", go do something useful instead of asking again in a spin loop. Rule 3 is the missing piece that makes rule 5 possible, and it has a name and a whole page: the next one.

Why &mut self? Because a future is a state machine

Think back to the stackless coroutines of Part 2. A suspended coroutine is not a running thing; it is a saved state: the values live at the suspension point, plus a marker saying where to resume. A Rust future is the same idea with the serial numbers filed off: a value that holds its own locals and its own current position. Advancing it means mutating that state: stepping the marker, storing new locals, dropping dead ones. That is why poll takes the future by mutable reference. You are not observing a computation; you are cranking it forward one turn.

And because the state lives inside the value, the value can sit in a queue, be moved between queues, live for an hour between polls. A stack, like a call stack or a green thread's stack, cannot do that; a state machine can. Keep that image: a future is a coroutine's frozen brain, packaged as an ordinary Rust value.

Two futures, by hand

Let's write the two degenerate futures and drive them without any machinery at all. No async, no engine, no queue: just the trait, a loop, and main. First, a future that is born finished:

use std::future::Future;
use std::pin::Pin;
use std::task::{Context, Poll, Wake, Waker};
use std::sync::Arc;

struct Done;

impl Future for Done {
    type Output = &'static str;

    fn poll(self: Pin<&mut Self>, _cx: &mut Context<'_>)
        -> Poll<&'static str>
    {
        Poll::Ready("finished")
    }
}

And its opposite, a future that is never ready:

struct Never;

impl Future for Never {
    type Output = ();

    fn poll(self: Pin<&mut Self>, _cx: &mut Context<'_>)
        -> Poll<()>
    {
        Poll::Pending
    }
}

Never breaks rule 3, of course: it returns Pending without saving any way to be re-polled, so it will hang forever. It is the minimal illustration of why the re-poll handle matters. Now drive them. Building the cx argument takes one small step ahead of the narrative: we need some handle to put in it, so here is a do-nothing one, built through std's Wake trait. The next page explains every choice; the code just needs a placeholder to run.

struct NoWake;
impl Wake for NoWake {
    fn wake(self: Arc<Self>) {} // do nothing: nothing here sleeps
}

fn main() {
    let waker = Waker::from(Arc::new(NoWake));
    let mut cx = Context::from_waker(&waker);

    let mut done = Done;
    assert_eq!(
        Pin::new(&mut done).poll(&mut cx),
        Poll::Ready("finished")
    );

    let mut never = Never;
    assert_eq!(Pin::new(&mut never).poll(&mut cx), Poll::Pending);
    println!("both futures answered");
}

Notice what the driving code had to do: construct a handle, wrap it, call poll through Pin::new. That last step is free here because Done and Never are plain data with no interior references; page 6 explains when it would not be. The assert-style polling in main is honest-to-goodness engine code: crude, synchronous, and complete. Everything Tokio's workers do to a future is some industrial-strength version of exactly this call.

What you cannot see yet is how anything ever gets polled a second time without spinning. Done never needed it and Never never wanted it, so the placeholder handle got away with doing nothing. A real future sleeps for milliseconds or waits for a socket; someone must call it back. That someone is the Waker, and it is where we go next.

In this chapter

  • The entire interface is Future::poll returning Poll::Ready(value) or Poll::Pending; there is nothing else to learn at the trait level.
  • Futures are lazy: calling an async fn builds a value and runs nothing; work happens only inside poll.
  • The contract forbids blocking inside poll, requires saving the re-poll handle before returning Pending, and forbids polling after Ready.
  • A future is a state machine advanced in place, which is why poll takes it by mutable reference and why it can be queued and moved like any value.
  • Re-polling in a tight loop is forbidden by etiquette; the wake-up mechanism that makes that rule livable is the next page's subject.
