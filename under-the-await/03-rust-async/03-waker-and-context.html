Waker and Context

Page 2 ended on a cliffhanger. A future returned Pending, and rule 5 of the contract said the engine must not spin on it. So the question stands: who calls poll the second time, and how does anyone know when it is worth asking again? The answer is two small types in std::task, and together they are the hinge on which the whole system swings.

The problem: asking forever

Suppose your engine kept a list of pending futures and did the obvious thing: loop over the list, poll each one, repeat. That is exactly the busy-poll trap from Part 1, resurrected at the library level. Ten thousand futures each asked "done yet?" a million times a second: the CPU melts, and the futures, being well-behaved, keep honestly answering "no". The kernel solved this with readiness reporting: sleep until something is ready, then act. Futures need the same arrangement, but there is no kernel beneath them; they must build it out of ordinary Rust values.

The contract's rule 3 hinted at the mechanism: before returning Pending, the future must save "the re-poll handle" from its second parameter. Time to give that handle its name.

Context: the envelope

The second parameter of poll is a Context<'_>, and honesty compels a confession: today it does almost nothing. It is a thin envelope whose single documented job is to carry a reference to a Waker into the poll call. It exists as a separate type so that the signature has room to grow without every future in the world having to change, and so the borrow of the waker has a scoped lifetime. One detail matters: the Context itself is deliberately neither Send nor Sync. It lives and dies inside a single poll call. The only thing allowed to escape the call is the waker you clone out of it.

Waker: the callback, reborn

A Waker is a small, cloneable, thread-safe handle that means exactly one thing: "please arrange for the future this came from to be polled again." Calling wake() does not run the future, does not run any of your code, and does not even run on your thread necessarily. It is a scheduling request, nothing more: the engine that created the waker receives the notification and queues a future poll at its leisure.

The contract around wake is precise. Every call to wake() must be followed by at least one poll, with a happens-before relationship between them, so state written before waking is visible when polled. Multiple calls may be coalesced into a single poll: wake, wake, wake can legally produce one re-poll. Which leads to the rule you must internalize now: a re-poll is a hint, not a promise of readiness. A well-behaved future re-checks its own state at the top of every poll, because the poller is allowed to be generous with re-polls, and a future that assumed "I was woken, therefore I am ready" would be a bug in waiting.

And the thread story: a Waker is Send and Sync, and it may be fired from any thread, including threads the engine has never heard of. This is not an exotic edge case; it is the design. The timer thread you will write on the next page, the kernel-side epoll machinery that eventually stands behind Tokio, a C library's completion callback: all of them are strangers to the engine, and all of them speak the same two-syllable word, wake.

Cheap clones and two ways to fire

Wakers are cheap to clone because a clone is a reference-counted increment, Arc-style, under the hood. A clone wakes the same future the original would have; the resources for the extra handle are retained until it is dropped. There is no reason to be stingy with them: a future stores one, an I/O registration stores another, and both firing is fine.

Two methods fire the handle. wake(self) consumes the waker, which lets an implementation avoid a refcount round-trip when you are done with the handle anyway. wake_by_ref(&self) fires without consuming, and the std docs recommend it over the clumsy waker.clone().wake() pattern. The difference is pure bookkeeping; the effect on the future is identical.

One more method completes the set. will_wake(&other) is a best-effort question: "would firing you and firing the other waker wake the same future?" If it answers true, that is guaranteed; if it answers false, it might simply not know. Its use is an optimization you will see in real code on the next page: a future that is re-polled and already holds a waker can ask will_wake before bothering to replace the stored one. Miss it and nothing breaks; use it and you skip a clone. The related Waker::clone_from uses the same trick internally.

What a waker is, physically

Peel the wrapper and a Waker is a fat pointer, the same shape as the trait objects from page 1: a data pointer plus a vtable pointer. The vtable is a RawWakerVTable with four entries: clone, wake, wake_by_ref, and drop. The data pointer is whatever the engine wants it to be, as long as it is safe to touch from any thread: an Arc to some engine-side bookkeeping, typically. Building one from raw parts means going through RawWaker and the unsafe Waker::from_raw, because you are personally vouching that the data pointer is valid for all four vtable entries from any thread.

Almost nobody should do that by hand, and std offers the safe road: the Wake trait. Implement wake on an Arc<YourType>, and Waker::from(that_arc) hands you a real Waker with the vtable generated for you. One small allocation, zero unsafe. Here is a waker that counts how many times it fired, plus a workout for both firing methods:

use std::sync::atomic::{AtomicUsize, Ordering};
use std::sync::Arc;
use std::task::{Wake, Waker};

struct CountingWaker(AtomicUsize);

impl Wake for CountingWaker {
    fn wake(self: Arc<Self>) {
        self.0.fetch_add(1, Ordering::Relaxed);
    }
}

fn main() {
    let counter = Arc::new(CountingWaker(AtomicUsize::new(0)));

    let waker = Waker::from(Arc::clone(&counter));
    let clone = waker.clone();          // cheap: refcount bump

    waker.wake_by_ref();                // fires, keeps the handle
    waker.wake_by_ref();                // fires again
    clone.wake();                       // fires, consumes the clone

    println!("wake-ups: {}",
        counter.0.load(Ordering::Relaxed));   // wake-ups: 3
}

Notice what the Wake implementation receives: self: Arc<Self>, ownership of the shared counter. Your wake is the vtable entry the machinery calls; the Arc is how the data pointer travels. In a real engine the counter would be "push this job's index onto the ready queue"; the shape of the code is identical.

Look at that cycle and recognize it. It is the event loop from Part 2, but refactored: instead of the loop holding a table of "when fd X is ready, call function Y", the future itself decides which events it wants to hear about, and the loop only knows "something asked for a poll". The inversion of control of callback systems is gone; you write straight-line code, and the waker quietly carries the continuation for you. It is also the same shape as the kernel's readiness model: sleep until poked, then ask.

A word you will barely use: combinator

Before async/await syntax existed, Rust code built large futures out of small ones using combinators: wrapper types like "run A, then run B with A's output", each implementing Future by polling its children and combining their results. They still exist, and page 5 will show you that .await is doing combinator work under the hood, and page 7's engine uses one to run several futures at once. But as a user you will rarely meet the word again: the syntax ate the ecosystem that needed it. It appears here because you own the definition now, and because the concept, "a future whose poll is made of other futures' polls", is what the next three pages are about.

Which is exactly where we are. You know what a future is, what poll promises, and how a wake-up travels. What you have never seen is a future doing something real. Time to write one from scratch: a timer, with a real thread, a real deadline, and a real hang-if-you-get-it-wrong pitfall.

In this chapter

  • A Waker is a cheap, cloneable, thread-safe handle meaning "poll this future again"; firing it is a scheduling request, not an execution.
  • Every wake() is followed by at least one poll, but wakes may coalesce, so a future must re-check its state on every poll.
  • Context is the thin envelope carrying the waker into poll; only the waker is allowed to outlive the call.
  • Physically a waker is a trait object: data pointer plus a vtable with clone, wake, wake_by_ref, and drop; build one safely with std's Wake trait and Waker::from.
  • The poll, Pending, wake, poll-again cycle is the entire async engine in miniature; Part 4 just makes it fast and industrial.
