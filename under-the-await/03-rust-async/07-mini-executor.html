Building a mini executor

Pages 2 through 6 handed you every component: futures that are state machines, wakers that travel between threads, the contract, the memory rules. What is still missing is the thing at the bottom of it all: the code that calls poll, owns the wakers, and decides what runs when. That code is the executor, and this page builds two of them from std alone. The first drives a single future on the calling thread. The second drives many. Together they are about sixty lines, and they are, mechanically, a small Tokio: everything Part 4 shows you about the real engine will be some scaled-up version of a decision on this page.

block_on: one future, one thread

The simplest possible engine is a function, conventionally named block_on: run one future to completion, on this thread, and while it is pending, actually sleep. "Block" in the name is honest: the calling thread does no other work until the future finishes. It is the tool a program uses at the top of its main function to cross from the synchronous world into the async one, exactly once.

The design falls straight out of the contract. Poll the future. If it says Ready, return the value. If it says Pending, then by rule 3 it has stored our waker somewhere, so we can safely go to sleep, and the waker's job is to wake us. The loop is three lines; the only real question is how a thread sleeps and gets woken, and std has a matched pair for exactly that.

thread::park() puts the calling thread to sleep at negligible cost: no timer, no condition variable setup, the thread simply leaves the run state until something calls unpark on its handle. The matching unpark carries a saved credit: if the thread is parked, it wakes; if it is not parked, the credit is remembered, and the very next park consumes it and returns immediately. That saved credit is the answer to the race you should be worried about, "what if the waker fires between my Pending and my going to sleep": the unpark that arrives early is not lost, so the thread cannot sleep through a wake-up. Here is the whole engine:

use std::future::Future;
use std::pin::pin;
use std::sync::Arc;
use std::task::{Context, Poll, Wake, Waker};
use std::thread::{self, Thread};

struct ThreadWaker(Thread);

impl Wake for ThreadWaker {
    fn wake(self: Arc<Self>) {
        self.0.unpark();
    }
}

fn block_on<F: Future>(fut: F) -> F::Output {
    let mut fut = pin!(fut);
    let waker = Waker::from(Arc::new(ThreadWaker(thread::current())));
    let mut cx = Context::from_waker(&waker);
    loop {
        match fut.as_mut().poll(&mut cx) {
            Poll::Ready(out) => return out,
            Poll::Pending => thread::park(),
        }
    }
}

Take it line by line. The waker wraps one value: thread::current(), a handle to ourselves, and its wake is a single unpark. When any thread anywhere fires this waker, the Arc lands in our thread's pocket and the thread wakes. Back in block_on: pin!(fut) fixes the future in place, because compiler-generated futures are not safe to move once running and poll demands the promise. Then the loop: poll, and on Pending, park, which is the same sleep-until-readiness the kernel gave you in Part 1, now built from threads instead of epoll. The saved-credit semantics make the loop correct even under the early-wake race: an unpark that arrives while we are still finishing the poll is banked, and the park() returns instantly.

The std documentation itself shows this design, with a warning label worth quoting: it trades correctness for simplicity, and production engines must additionally handle intermediate unpark calls and nested invocations of the loop from the same thread. Our version inherits those sharp edges and, for teaching, keeps them. File the caveat; Part 4 shows how the industrial version earns its keep.

The full circle

Now the moment this whole part has been walking toward. Take the Delay from page 4, unchanged, and drive it with the engine you just wrote; then drive an actual async block with it:

fn main() {
    let started = Instant::now();
    block_on(delay(Duration::from_millis(50)));
    println!("one delay: {:?}", started.elapsed());

    let started = Instant::now();
    block_on(async {
        delay(Duration::from_millis(30)).await;
        delay(Duration::from_millis(30)).await;
    });
    println!("two awaits: {:?}", started.elapsed());
}
one delay: 50.2ms
two awaits: 60.6ms

Read the second demo slowly, because it is the hinge of the entire book. That async block is a compiler-generated state machine, from page 5. Its two .awaits poll a hand-written future, from page 4, whose waker is ThreadWaker::wake, from this page, and whose timer thread is a plain std::thread. Every layer is something you have built or dissected by hand. Sixty milliseconds is just two thirty-millisecond delays run one after another, and the thread slept through almost all of it: no busy-waiting, no blocked kernel calls, one wake-up per delay. The async stack, bottom to top, is closed.

Many jobs: a queue, not a loop

block_on drives one future. The interesting engines drive thousands, which changes the design in one way: there must be a place where woken futures wait to be polled. Recall Part 2's run queues: here is one being born. The plan: keep the jobs in a Vec, keep a queue of indices of jobs that are ready to be polled, and build each job's waker so that waking it means "push my index and wake the engine thread":

use std::collections::VecDeque;

struct Shared {
    ready: Mutex<VecDeque<usize>>, // indices of jobs to poll
}

struct JobWaker {
    shared: Arc<Shared>,
    index: usize,
    main: Thread,
}

impl Wake for JobWaker {
    fn wake(self: Arc<Self>) {
        self.shared.ready.lock().unwrap().push_back(self.index);
        self.main.unpark();
    }
}

The JobWaker is the entire scheduling policy of this engine in four lines: a wake re-enqueues the job and pokes the thread. Because a waker may be fired from any thread, the queue lives behind a Mutex with atomics doing the thread-safe counting inside the Arc. Now the engine loop:

fn run_all(futures: Vec<Pin<Box<dyn Future<Output = ()>>>>) {
    let mut jobs: Vec<Option<Pin<Box<dyn Future<Output = ()>>>> =
        futures.into_iter().map(Some).collect();
    let shared = Arc::new(Shared {
        ready: Mutex::new((0..jobs.len()).collect()),
    });
    while jobs.iter().any(Option::is_some) {
        let next = shared.ready.lock().unwrap().pop_front();
        let i = match next {
            Some(i) => i,
            None => {
                thread::park(); // queue dry: sleep until a wake arrives
                continue;
            }
        };
        let Some(slot) = jobs.get_mut(i) else { continue };
        let Some(fut) = slot.as_mut() else { continue }; // finished earlier
        let waker = Waker::from(Arc::new(JobWaker {
            shared: Arc::clone(&shared),
            index: i,
            main: thread::current(),
        }));
        let mut cx = Context::from_waker(&waker);
        if fut.as_mut().poll(&mut cx).is_ready() {
            *slot = None; // retire the job
        }
    }
}

Walk the loop. The jobs start boxed and pinned, uniform Pin<Box<dyn Future>> values regardless of their concrete types, which is the page 5 sizing note doing real work. Every index starts in the ready queue, so the first sweep polls everything once. Each iteration pops one index, skips it if the job has already finished (wakes can arrive late), builds that job's waker, polls once, and retires the job on Ready. When the queue runs dry while jobs still sleep, the engine parks, exactly like block_on, and any JobWaker firing anywhere pushes an index and unparks it. There is no polling in a tight loop, no busy waiting: the thread sleeps whenever there is nothing to do, and every wake is caused by an event that might genuinely make progress.

Prove it composes. Three Delays, all on one thread:

fn main() {
    let started = Instant::now();
    run_all(vec![
        Box::pin(delay(Duration::from_millis(80))),
        Box::pin(delay(Duration::from_millis(40))),
        Box::pin(delay(Duration::from_millis(60))),
    ]);
    println!("three jobs: {:?}", started.elapsed());
}
three jobs: 80.3ms

Three timers, one OS thread, and the total is roughly the longest delay, not the sum of all three. The engine polls each job once, each job's timer thread holds its waker, and the engine sleeps in between wakes. That is concurrency without additional threads: the cooperative promise from Part 2, made mechanical. Each Pending return is a yield point, and this engine's fairness policy is the queue itself: round-robin, one poll per turn, no job can starve another because no job may refuse to return Pending.

Here is a bug that was genuinely in this page's code the first time it ran, and it is subtle enough to be worth your time. Consider writing the queue pop like this:

// BUGGY: the lock guard lives for the whole match statement
let i = match shared.ready.lock().unwrap().pop_front() {
    Some(i) => i,
    None => { thread::park(); continue; }
};

The temporary MutexGuard produced in the match scrutinee is not dropped until the end of the match, so the park() sleeps while still holding the queue's lock. The program hangs, silently. When a timer fires, the waker's wake dutifully tries to lock the queue to push its index, blocks on the mutex held by the sleeping engine thread, and never reaches the unpark. Deadlock: everyone waiting for everyone, no panic, no message. The fix is the let next = ...; binding you see in the real listing, which ends the guard's life at the semicolon. The general law: never hold a lock across a sleep, and know that match scrutinee temporaries outlive their line.

What we cut

An honest accounting, because the gaps are where Part 4 lives. This engine allocates a fresh waker for every poll of every job; Tokio embeds wakers in the jobs themselves. This engine has one queue and one thread; Tokio gives each worker thread its own queue plus a shared overflow lane, moves work between them by stealing, and caps how long any job may run without yielding. This engine knows nothing about sockets or files; hooking readiness events from the kernel up to wakers is the machinery that Part 4's I/O chapters dissect in full. This engine sleeps in park waiting for any wake at all; a production engine parks inside the readiness machinery so the same sleep covers timers, sockets, and queues at once. And where this engine starts a thread per timer, the real one keeps every deadline in one data structure with a single clock.

None of those gaps change the shape. Pop, poll, park, wake: that loop is the shape of every async engine Rust has ever grown, and you now own a working one. The remaining question is why Rust built its language around this particular loop instead of the greener threads of Part 2, and that decision, its costs paid in full and its payoff banked, is the last page of this part.

In this chapter

  • An executor is the code that calls poll, owns wakers, and decides what runs; block_on is the smallest one: poll, and on Pending, sleep the thread.
  • thread::park and unpark form a credit-based sleep: an early unpark is banked, closing the wake-versus-sleep race.
  • Waking a job means "enqueue it, then wake the engine"; a Mutex-guarded queue of indices is a run queue in embryo.
  • Never hold a lock across a park: the waker that should rescue you deadlocks on the lock you never released.
  • Three delays on one thread finish in roughly the longest delay: concurrency without threads, the Part 2 cooperative model made mechanical.
