What async/await compiles to

Page 4 cost you eighty lines to hand-build one sleep. If that were the price of every async operation, nobody would write async Rust. Nobody does. The compiler writes it for you: every async fn and every .await expands into the same shapes you just wrote by hand, an enum with one variant per suspension point and a poll that advances it. This page catches the compiler in the act by building the two versions side by side, then states the rules of the transform so precisely that you could do its job.

First, what an async fn actually is

An async fn is sugar. async fn f() -> T means a function returning impl Future<Output = T>: some anonymous type that implements the trait from page 2. And per that page's laziness rule, calling f() runs none of the body. The call constructs the value and returns it. The body executes only inside poll. So the question "what does async fn compile to" is really "what is that anonymous type", and the answer is: a state machine struct.

The example

Here is a small async function with three .await points and one deliberate extra: a local, len, that is read before the first await and used after the last one, so it must survive across all three. The three awaited operations are hand-written futures in the style of page 4, so we can name their types in the hand-written twin:

async fn pipeline(raw: String) -> String {
    let len = raw.len();                     // live across ALL awaits
    let trimmed = Trim(raw).await;           // await #1
    let shouted = Shout { text: trimmed,     // await #2
                          polled_once: false }.await;
    let wrapped = Wrap(shouted).await;       // await #3
    format!("{wrapped} ({len} bytes)")
}

For this demo, Trim and Wrap finish on their first poll. Shout is the interesting one: it returns Pending on its first poll and Ready on its second, standing in for any operation that has to wait for something. Here are the three, in the page 4 style:

struct Trim(String);

impl Future for Trim {
    type Output = String;
    fn poll(self: Pin<&mut Self>, _cx: &mut Context<'_>) -> Poll<String> {
        let text = &mut self.get_mut().0;
        Poll::Ready(std::mem::take(text).trim().to_string())
    }
}

/// Not ready on its first poll; ready on the second.
struct Shout {
    text: String,
    polled_once: bool,
}

impl Future for Shout {
    type Output = String;
    fn poll(self: Pin<&mut Self>, _cx: &mut Context<'_>) -> Poll<String> {
        let this = self.get_mut();
        if !this.polled_once {
            this.polled_once = true;
            return Poll::Pending;
        }
        Poll::Ready(std::mem::take(&mut this.text).to_uppercase())
    }
}

// Wrap is Trim with a format! call: Ready on the first poll.

The hand-written twin

Now the same function written the way the compiler would, if the compiler were paid by the hour. Compare it against the async version above as you read: this is the payoff of page 4, because the shape is exactly the Delay's.

struct PipelineFut {
    len: usize,     // live across every await: a plain field
    stage: Stage,   // "where was I when I last returned Pending?"
}

enum Stage {
    Start { raw: String },
    AwaitTrim(Trim),
    AwaitShout(Shout),
    AwaitWrap(Wrap),
    Done,
}

One struct, two fields. The stage field is the discriminant: which suspension point the function is stopped at, or "not started", or "finished". Each variant of Stage carries exactly the values that must survive until the next suspension point: the not-yet-consumed argument in Start, and the in-flight child future in each Await* variant. And len, which is live across all three awaits, sits in the shared part of the struct, a field of every state at once.

Now the poll. It is a loop over the stages, driving as far forward as it can, exactly like the eager-until-Pending behavior you observed on page 2:

impl Future for PipelineFut {
    type Output = String;

    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<String> {
        let this = self.get_mut();
        loop {
            match std::mem::replace(&mut this.stage, Stage::Done) {
                Stage::Start { raw } => {
                    this.stage = Stage::AwaitTrim(Trim(raw));
                }
                Stage::AwaitTrim(mut fut) => match Pin::new(&mut fut).poll(cx) {
                    Poll::Ready(trimmed) => {
                        this.stage = Stage::AwaitShout(Shout {
                            text: trimmed,
                            polled_once: false,
                        });
                    }
                    Poll::Pending => {
                        this.stage = Stage::AwaitTrim(fut); // put it back
                        return Poll::Pending;
                    }
                },
                Stage::AwaitShout(mut fut) => match Pin::new(&mut fut).poll(cx) {
                    Poll::Ready(shouted) => {
                        this.stage = Stage::AwaitWrap(Wrap(shouted));
                    }
                    Poll::Pending => {
                        this.stage = Stage::AwaitShout(fut);
                        return Poll::Pending;
                    }
                },
                Stage::AwaitWrap(mut fut) => match Pin::new(&mut fut).poll(cx) {
                    Poll::Ready(wrapped) => {
                        this.stage = Stage::Done;
                        return Poll::Ready(
                            format!("{wrapped} ({} bytes)", this.len));
                    }
                    Poll::Pending => {
                        this.stage = Stage::AwaitWrap(fut);
                        return Poll::Pending;
                    }
                },
                Stage::Done => panic!("polled after completion"),
            }
        }
    }
}

Read the AwaitTrim arm once, carefully, because every await arm is the same sentence: move the child future out, poll it with the outer cx (wakers flow down the chain, one more reason they must be cloneable), and on Ready store the result and loop into the next stage; on Pending, put the child future back and return Pending yourself. That last move is the suspension: the next call to poll will match AwaitTrim again and resume exactly here, with the same child future, mid-operation. Suspension and resumption, in a match arm.

The constructor is one line, and the lazy rule falls out of the design for free:

fn pipeline_by_hand(raw: String) -> PipelineFut {
    PipelineFut { len: raw.len(), stage: Stage::Start { raw } }
}

Both, driven by hand

Now drive the compiler's version and the twin with the same two manual polls and compare answers. One wrinkle first: the compiler-generated future is not plain data, so Pin::new refuses it; std's pin! macro fixes it in place on the stack instead. Why that refusal exists, and why it is the single most controversial decision in Rust async, is the next page. For the demo, one macro call:

fn main() {
    let waker = /* a do-nothing waker, as on page 2 */;
    let mut cx = Context::from_waker(&waker);

    // The compiler's version: pin! because it is generated code.
    let mut fut = std::pin::pin!(pipeline("  hello  ".to_string()));
    assert!(fut.as_mut().poll(&mut cx).is_pending()); // parks at Shout
    match fut.as_mut().poll(&mut cx) {
        Poll::Ready(s) => assert_eq!(s, "[HELLO] (9 bytes)"),
        Poll::Pending => unreachable!(),
    }

    // The twin: plain data, so Pin::new is fine.
    let mut hand = pipeline_by_hand("  hello  ".to_string());
    assert!(Pin::new(&mut hand).poll(&mut cx).is_pending());
    match Pin::new(&mut hand).poll(&mut cx) {
        Poll::Ready(s) => assert_eq!(s, "[HELLO] (9 bytes)"),
        Poll::Pending => unreachable!(),
    }
    println!("both versions agree");
}

One more detail hides in the arms, and it matters enormously later. Every child poll receives the outer cx, which means every level of a nested async call tree sees the same waker. When Shout eventually returns Pending after storing that waker, one single wake-up from the outside can move the entire tree: the outer future, the middle futures, and the leaf waiting on reality. Wakers do not multiply per nesting level; they flow through. That is the property that lets a real engine wake a deep async call stack with one cheap notification, and you will see it working at scale in Part 4.

The first poll runs eagerly from Start through Trim, hits Shout's Pending, stores AwaitShout as the stage, and returns Pending: the whole function is now a value suspended at the second await. The second poll resumes inside the AwaitShout arm, Shout finishes, Wrap finishes in the same eager sweep, and Ready("[HELLO] (9 bytes)") comes out. Both versions print "both versions agree". The compiler is doing precisely what you did on page 4, minus the salary.

The rules of the transform

Source constructGenerated construct
each .await pointone enum variant holding the awaited child future and the locals live until the next suspension
locals live across an awaitfields of the state struct (like len), present in every variant they outlive
function argumentsfields from the moment of construction
the await itselfpoll the child: on Ready advance, on Pending store the child and return Pending
falling off the endstore Done, return Ready(output)
values that die before the next awaitdropped at the state transition, by compiler-inserted drop code

Two honest footnotes. First, this is the conceptual model: the real transform may add internal states for error propagation with ?, for drop cleanup, or merge variants it can prove compatible; the underlying machinery is the same coroutine transform that powers Rust's experimental generators. Second, memory: the generated struct's size is the maximum over its variants, because every state occupies the same allocation. A future holding a hundred-byte buffer alive across one await costs a hundred bytes in every state. That is why deeply nested or recursive async functions sometimes need explicit heap indirection, and why engines that store many different future types together reach for Box<dyn Future>: one fat pointer, uniform size, trading the vtable indirection from page 1 for the right to put anything in the same queue.

The wrinkle we have been dodging

There is one shape the twin above never draws. Suppose the async function borrows one of its own locals across an await, where the local is data stored inline, not behind a heap pointer:

struct Blob {
    bytes: [u8; 6],               // six bytes, no heap involved
}

async fn borrowing(blob: Blob) -> usize {
    let head = &blob.bytes[0..3]; // a reference INTO the blob itself
    something().await;            // head must survive this
    head.len()
}

After the transform, blob lives in a field of the generated struct, and head, which must survive the await, lives in a field too. But head is not a copy of the bytes; it is a reference, an address, and the address it holds points into the same struct, into the six bytes of the blob field. The future contains a pointer to itself.

Now recall page 1: futures get moved. They are handed to engines, stored in queues, shifted between threads. Move a struct that contains a pointer into itself and the pointer still holds the old address; it now points at whatever garbage occupies the old memory. Safe Rust would never let you build such a struct by hand; the borrow checker rejects the shape outright. The async transform builds it anyway, behind your back, and that is why poll's receiver is not a plain &mut, why Pin::new refused our generated future above, and why there is a type called Pin whose entire job is to make that pointer safe. That story, the one piece of this machinery with no equivalent in any other language you have met in this book, is the next page.

In this chapter

  • async fn is sugar for returning an anonymous type that implements Future; calling it runs nothing.
  • The anonymous type is an enum state machine: one variant per await point, live locals as fields, the stage as the discriminant.
  • .await compiles to polling the child future: Ready advances the machine, Pending returns Pending and resumes at the same arm on the next poll.
  • The generated struct's size is the maximum over its variants, which is what makes futures cheap to store and occasionally necessary to box.
  • A reference held across an await makes the future point into itself; moving such a value dangles the pointer. That hazard, and Pin, the type that defuses it, are the next page.
