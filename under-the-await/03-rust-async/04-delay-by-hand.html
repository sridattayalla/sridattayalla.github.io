Writing a Future by hand

You know the trait, the contract, and the wake-up mechanism. Time to pay off all three at once by building a real future with real behavior: a Delay that completes after a deadline, using nothing but the standard library. No async, no .await, no Tokio. When it is done you will have seen, in about eighty lines, every structural trick that the compiler will later do for you automatically; page 5 is exactly that comparison, side by side.

The design in one breath

A Delay is created with a duration. Being a lazy value, it does nothing until its first poll. On that first poll it arms a plain OS thread that sleeps until the deadline and then fires the waker. Every later poll just checks the clock: past the deadline means Ready, otherwise Pending again with the waker safely stored. Three states, one helper thread, one shared slot. Here is the shape:

use std::future::Future;
use std::pin::Pin;
use std::sync::{Arc, Mutex};
use std::task::{Context, Poll, Waker};
use std::thread;
use std::time::{Duration, Instant};

/// One slot, shared between the future and its timer thread.
type WakerSlot = Arc<Mutex<Option<Waker>>>;

enum State {
    Started { deadline: Instant },
    Sleeping { deadline: Instant, slot: WakerSlot },
    Done,
}

struct Delay {
    state: State,
}

Each piece of WakerSlot earns its keep. The Option because the slot starts empty and only fills on the first poll. The Mutex because two threads touch it: the driving thread stores the waker, the timer thread takes it out. The Arc because both sides need to own it, and the atomics inside make that sharing legal across threads. And Waker itself is exactly the cheap, thread-safe handle from page 3.

The state enum is the future's brain. Started means "never polled, no timer yet". Sleeping means "timer armed, waker stashed, waiting". Done is the terminal state that makes polling after completion panic loudly instead of corrupting anything, honoring rule 4 of the contract. Notice what the enum is: a hand-rolled version of exactly the suspended-coroutine state idea from Part 2. Keep that in mind; it becomes the punchline of page 5.

poll, first arm: arming the timer

impl Future for Delay {
    type Output = ();

    fn poll(mut self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<()> {
        match std::mem::replace(&mut self.state, State::Done) {
            State::Started { deadline } => {
                // First poll: create the slot and store the waker (rule 3).
                let slot: WakerSlot = Arc::new(Mutex::new(None));
                {
                    let mut guard = slot.lock().unwrap();
                    *guard = Some(cx.waker().clone());
                }
                let thread_slot = Arc::clone(&slot);
                let remaining = deadline.saturating_duration_since(Instant::now());
                thread::spawn(move || {
                    thread::sleep(remaining);
                    if let Some(waker) = thread_slot.lock().unwrap().take() {
                        waker.wake();
                    }
                });
                self.state = State::Sleeping { deadline, slot };
                Poll::Pending
            }

Walk it slowly; every line is a decision.

std::mem::replace(&mut self.state, State::Done) moves the current state out and leaves a placeholder behind, all in one atomic-looking step, so the match can take the enum apart by value. Each arm then writes the next state back into self.state before returning. If an arm forgets, the placeholder Done is waiting to make the bug loud on the next poll. This move-out-then-restore dance is the standard idiom for advancing an enum state machine through a mutable reference, and it is precisely what the compiler-generated version of this code does internally.

The Started arm runs only once. It creates the empty slot, locks it, and stores a clone of cx.waker(). That clone, taken before any Pending is returned, is contract rule 3 in the flesh: if we return Pending without saving a way to be re-polled, we may never be asked again. The braces around the lock are not decoration: they end the mutex guard's lifetime before the next statement, so the compiler lets us move slot into the new state afterwards.

Then the timer thread. thread::spawn takes a closure that moves in its own Arc clone of the slot, sleeps for the time remaining until the deadline, then locks the slot and calls take(). take swaps the waker out, leaving None: the wake fires exactly once, and if anything polls the future again later, the will_wake check you will see below re-fills the slot. Firing the waker from a plain helper thread is completely legal, because a Waker may be invoked from any thread at all; that freedom was the whole point of page 3.

Finally the state advances to Sleeping, carrying both the deadline and the slot as fields, and the method returns Pending. Total work on the driving thread: a few allocations plus one new thread. No waiting. That is what "poll must return quickly" looks like in practice.

poll, second arm: checking the clock

            State::Sleeping { deadline, slot } => {
                if Instant::now() >= deadline {
                    self.state = State::Done;
                    return Poll::Ready(());
                }
                // Not finished: make sure the CURRENT waker is stored.
                {
                    let mut guard = slot.lock().unwrap();
                    match &*guard {
                        Some(w) if w.will_wake(cx.waker()) => {}
                        _ => *guard = Some(cx.waker().clone()),
                    }
                }
                self.state = State::Sleeping { deadline, slot };
                Poll::Pending
            }
            State::Done => panic!("Delay polled after completion"),
        }
    }
}

The Sleeping arm is deliberately boring, and its boredom is the contract. First question: is the deadline past? If yes, write Done and return Ready; rule 1 says finish the moment you can. If no, re-store the waker before returning Pending again.

Why re-store, when the first arm already stored one? Because of the most-recent-waker rule: only the waker from the latest poll is guaranteed to reach the right place. A future can be handed to a different engine, or the engine can rebuild its wakers; an old stored handle might then wake the void. So each poll refreshes the slot, with the small mercy of will_wake: if the stored waker already wakes the same thing, skip the clone. This re-check matters most when the poll is spurious, a courtesy wake with nothing ready; the arm handles that case for free, because "deadline not past" falls through to the same refresh-and-Pending path.

And the Done arm is the tripwire from page 2's rule 4: polling a finished future is a bug, and this future makes it a loud, local, debuggable one.

The constructor, and a demonstration

fn delay(how_long: Duration) -> Delay {
    Delay {
        state: State::Started {
            deadline: Instant::now() + how_long,
        },
    }
}

The constructor only builds the Started state. No timer is started, no thread exists, nothing is registered anywhere: the future is inert until polled, exactly as promised on page 2. Now a demonstration that drives the future with no machinery beyond a loop. We need some waker to build the cx argument, so here is the smallest useful one: a flag-setter, straight from the page 3 pattern.

use std::sync::atomic::{AtomicBool, Ordering};

struct FlagWaker(AtomicBool);

impl Wake for FlagWaker {
    fn wake(self: Arc<Self>) {
        self.0.store(true, Ordering::Release);
    }
}

A wake is nothing but a flag flip with release ordering, which the waiting side will read with acquire ordering, the cheapest thread-safe mailbox in the language. Now a demonstration that drives the future with no machinery beyond a loop: build the future, wrap the flag in a waker, poll, and between attempts, spin until the flag moves.

fn main() {
    let started = Instant::now();
    let mut delay = delay(Duration::from_millis(50));

    let flag = Arc::new(FlagWaker(AtomicBool::new(false)));
    let waker = Waker::from(Arc::clone(&flag));
    let mut cx = Context::from_waker(&waker);

    loop {
        match Pin::new(&mut delay).poll(&mut cx) {
            Poll::Ready(()) => {
                println!("done after {:?}", started.elapsed());
                return;
            }
            Poll::Pending => {
                while !flag.0.load(Ordering::Acquire) {
                    thread::yield_now(); // busy-wait: page 7 fixes this
                }
                flag.0.store(false, Ordering::Release);
            }
        }
    }
}

Run it and you get done after 50.1…ms-ish, the exact digits depending on your operating system. Now trace the two polls across time, because the timeline is the whole story:

At t equal to zero, poll runs the Started arm: slot created, waker cloned in, timer thread created, state advanced to Sleeping, Pending returned. The driving thread then spins politely on the flag. At t equal to the deadline, the timer thread wakes, takes the waker out of the slot, and fires it, which sets the flag. The driving thread notices, clears the flag, and calls poll again. This time the Sleeping arm runs, the deadline check succeeds, the state becomes Done, and Ready pops out. That is one complete async operation, hand cranked, with every contract rule visible.

Delete the single line *guard = Some(cx.waker().clone()); from the Started arm and run the program again. The timer thread wakes, locks the slot, finds None, and fires nothing. The flag is never set. The driving loop spins forever. There is no error, no warning, no deadlock detector: just a future that is never polled again, anywhere, silently, until the process dies. Forgetting to store the waker before returning Pending is the classic hand-written-future bug, and it is why the contract states rule 3 in bold ink. When a real application hangs in exactly this way, with work asleep that should have finished, this missing line is one of the first suspects.

Notice where the sleeping happens: in a separate thread, never inside poll. If the Started arm had simply called thread::sleep and returned Ready afterwards, it would have worked in this single-future demo, and it would have been a silent disaster in any real engine: for fifty milliseconds, the thread driving futures would be frozen, and every other future behind it would starve. This is the cooperative fairness rule from Part 2 wearing Rust clothes: work between polls must be short, and waiting must be someone else's job.

One honest confession before moving on. A thread per timer is a fine teaching implement and a terrible production one; real engines keep every sleeping future's deadline in one sorted or wheeled structure and use a single timer source for all of them. You will meet that machinery in Part 4. The Delay here is the honest std-only version of the idea, and its structure, one state enum plus one wake-up path, is exactly what the big machinery drives.

Which raises the question you should already be asking. This was eighty lines for one sleep. Nobody writes a networked application as thousands of hand-rolled state machines. Right: nobody does. The compiler does, from async and .await. Next page, we catch it in the act, with the async version of a small state machine and its hand-written twin side by side.

In this chapter

  • A Delay future is an enum state machine (Started, Sleeping, Done) advanced one state per poll, with mem::replace as the move-out-and-restore idiom.
  • The waker slot Arc<Mutex<Option<Waker>>> is shared with a timer thread that sleeps until the deadline and fires the waker exactly once via take().
  • Rule 3 is load-bearing: return Pending without storing the waker, and the future hangs forever with no error anywhere.
  • Each poll refreshes the stored waker (most-recent-waker rule), with will_wake as the cheap skip when nothing changed.
  • All waiting happens off to the side, in the timer thread; poll itself only arms, checks, and returns.
