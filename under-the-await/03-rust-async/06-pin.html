Pin and self-referential futures

Four pages ago, poll's receiver showed up wearing a strange wrapper: self: Pin<&mut Self>. We deferred it, then deferred it again. No more. This page is about the one problem in Rust async that has no equivalent in the languages you met in Part 2, and the two types, Pin and Unpin, that exist to solve it. The machinery is small; the reasoning is subtle; and once you have it, the last line of mystery in poll's signature is gone.

The hazard, reconstructed

Page 5 ended with the wrinkle: an async function that borrows its own inline local across an await. After the transform, the generated struct holds both the data and the reference, and the reference points into the data. Such a value is self-referential: it contains, inside itself, a pointer whose target is also inside itself. Here is the shape again, in full:

struct Blob {
    bytes: [u8; 6],               // six bytes, no heap involved
}

async fn borrowing(blob: Blob) -> usize {
    let head = &blob.bytes[0..3]; // a reference INTO the blob itself
    something().await;            // head must survive this
    head.len()
}

The generated future for borrowing has (conceptually) two fields: blob, the six bytes, and head, a fat reference whose address is the address of the blob field. Not a copy of the bytes. An address into the future's own body. And futures, as page 1 promised and every page since has assumed, get moved: returned from functions, pushed into queues, handed across threads. So ask the ugly question: what does moving do to that address?

Try to write the by-hand version in safe Rust and find out. Safe Rust is way ahead of you:

struct Bad<'a> {
    blob: Blob,
    head: &'a [u8],     // meant to point into blob.bytes
}

fn main() {
    let blob = Blob { bytes: [1, 2, 3, 4, 5, 6] };
    let head = &blob.bytes[0..3];
    let bad = Bad { blob, head };   // <-- try to assemble it here
    println!("{}", bad.head.len());
}
error[E0505]: cannot move out of `blob` because it is borrowed
  --> src/main.rs:12:21

12 |     let bad = Bad { blob, head };

   |                     |

The borrow checker refuses the whole idea. You cannot move a value into a struct while a reference into that value is still live, because moving might relocate the bytes, and a relocated target leaves the reference aimed at the old address. That is E0505, and it is the borrow checker doing exactly its job.

And yet the async transform builds precisely this shape, quietly, every time you hold a borrow across an await. It can, because the transform is exempt from its own rules: the compiler knows where every field lands, and it takes responsibility for the internal reference being consistent as long as the struct never moves. Which leaves exactly one question, and it is the question the entire rest of this page answers: how do you let ordinary user code pass such a struct around, without ever letting it move?

What a move actually breaks

Draw it. Before the move, the future sits at some address, call it 0x1000. Its blob field occupies the first bytes; its head field stores the address of those bytes, 0x1000, everything consistent. Now the engine moves the future to 0x2000: memcpy, the six bytes of blob travel, the stored number 0x1000 in head travels too, unchanged. Numbers do not know they are addresses. The moved head still says 0x1000, which now holds whatever came after the move: stale bytes, someone else's value, anything. Reading through it is the textbook use-after-move, and in a language with this little undefined behavior, that is simply not allowed to be reachable.

Pin: a promise, expressed as a type

The fix is almost embarrassingly direct once stated: if moving is the hazard, stop the moving. Pin is a wrapper around a pointer, Pin<P>, that carries one promise: the value the pointer points to, the pointee, will not be moved before it is dropped, and nobody else gets a pointer through which they could move it. Pin<&mut T> is "a mutable reference to T, minus the ability to relocate T". The wrapper pins the pointee, not the pointer: you can move the Pin itself all you like, copy it, pass it on; what is frozen is the thing at the far end. And it is free: Pin<P> has exactly the same memory layout as P, no tag, no flag, nothing. The promise lives in the type system, not in the bytes.

How does a type enforce "you may not move what I point to" in a language where moving is a memcpy anyone can do? By starving you of the means. From a Pin<&mut T> you can call poll, you can read, you can do everything &mut T does, except obtain the raw &mut T itself, the handle you would need to assign it elsewhere, pass it by value, or otherwise relocate it. The one door that leads to moving is simply not on this wall. (The escape hatches exist, unsafe ones like Pin::new_unchecked and get_unchecked_mut, and they exist so the engine's authors, who are taking responsibility for the promise manually, can get work done. User code never touches them in this book.)

Unpin: the opt-out almost everyone takes

If every value behind a Pin were frozen forever, all of Rust would grind to a halt: sometimes you have a Pin<&mut String> and just want your &mut String back. Enter Unpin: an auto trait, derived by the compiler, meaning "this type is safe to move even while pinned", because it contains nothing that could dangle. String is Unpin. Vec is Unpin. Your struct of plain fields is Unpin. The Delay from page 4 and the PipelineFut twin from page 5 are Unpin, which is why their code could call self.get_mut() and Pin::new freely. For an Unpin type, Pin<&mut T> behaves exactly like &mut T, and that is why almost all Rust code never notices Pin exists.

The types that are not Unpin are the ones that might hold pointers into themselves, and the compiler-generated futures from async fn are the canonical example: the compiler cannot promise that no await borrows a local, so it must conservatively mark the whole generated type as not safe to move once started. If you ever need to build a deliberately immovable type by hand, std provides the marker: add a PhantomPinned field, and your struct becomes !Unpin without a line of unsafe.

TypeUnpin?What it means in practice
String, Vec, integers, most structsyesPinned or not, movable; Pin adds nothing
Delay (page 4), PipelineFut (page 5)yesPlain data; that is why their demos could use Pin::new freely
futures generated from async fn noMight self-reference; once pinned, they stay put until dropped
struct with a PhantomPinned field noDeliberate opt-out for hand-built immovable types

Why poll takes Pin<&mut Self>

Now the signature from page 2 finishes resolving itself. The Future trait must work for every future, including the compiler-generated !Unpin ones. If poll took a plain &mut self, the engine would hold a handle through which the future could be moved, and the self-references inside generated futures would be one careless assignment away from dangling. So the trait demands the pinned reference: hand me the future with a promise attached that it will not relocate. If the concrete future happens to be Unpin, the promise is vacuous and costs nothing, which is exactly the experience your page 4 code had. One trait, both worlds.

Pinning in practice

You will rarely write the word Pin yourself, but you will use two tools that produce it. Box::pin(value) moves the value to the heap and hands back a Pin<Box<T>>: the value now lives at a stable heap address forever, and the smart pointer can be moved, stored in queues, sent across threads, all while the pointee stays fixed. It costs one allocation, and it is how heterogeneous collections of futures are built: a Vec of Pin<Box<dyn Future>> can hold a hundred different generated types, each frozen at its own heap address. Std's pin! macro does the stack version: it shadows a local so that the value is pinned in place for the rest of the scope, no allocation at all. You used both forms already: page 5's demo needed pin! for the compiler-generated future, and page 7's engine will box its futures to store them uniformly.

One last nuance, and it is a mercy: the promise starts when the pinning starts. A freshly created async future can be returned from a function, stored in a variable, moved into a struct, because before it is pinned and first polled it cannot yet hold live internal references; the borrows only materialize as the body runs. The rule you actually live by is short: create it, move it wherever it needs to live, pin it once, and from then on it does not move until it is dropped. Engines do exactly that: Tokio, for instance, keeps every piece of handed-over work as a pinned heap allocation for its entire life; Part 4's second page takes that allocation apart field by field.

That is the whole iceberg. Pin is not extra machinery; it is a promise about addresses, enforced by removing the handles you would need to break it, so that the one struct the compiler builds with a pointer into itself can be passed around like any other value without anyone being able to wreck it. The price of the design is real: a strange receiver in every poll signature, and the occasional Box::pin tax. The payoff is that Rust gets stackless futures with internal borrows, and no other mainstream language had to solve this because none of them let borrows cross suspension points at all.

In this chapter

  • An async fn that borrows an inline local across an await compiles to a self-referential struct; safe Rust refuses to let you build such a struct by hand (E0505), but the transform is exempt.
  • Moving such a struct copies the stored address without updating it, leaving the pointer aimed at the abandoned location.
  • Pin<P> is a zero-cost wrapper promising the pointee never moves before drop; it removes the raw &mut T through which you could relocate it.
  • Unpin is the auto trait for types where the promise is vacuous; nearly everything qualifies, and generated futures are the famous exception.
  • Box::pin (heap) and pin! (stack) are the practical tools; Tokio stores every handed-over piece of work as a pinned heap allocation.
