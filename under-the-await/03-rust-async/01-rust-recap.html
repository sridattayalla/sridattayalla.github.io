The Rust you need for async

Parts 1 and 2 gave you the machine and the classic strategies for juggling many concurrent things on it. Now Rust enters the story. Over the next eight pages you will build the country's entire async machinery out of the standard library alone: the trait at the center, the wake-up mechanism, a suspended computation written by hand, what the compiler does with async and .await, and a working mini engine that drives it all. Tokio gets named along the way as the destination, but we will not open it until Part 4.

Before any of that, this page rounds up the specific Rust features that async leans on. This is not a general Rust tutorial. Every concept here earns its place by paying an async bill later, and each section ends by naming that bill. If you know Rust well, skim the code and read the payoff lines.

Ownership: values that move

Ownership is the rule that every value has exactly one owner at any moment: a variable, a field, a slot in a collection. You can lend a value out by reference, but when the owner is passed somewhere by value, the value moves, and the old binding goes dead. The compiler enforces this at build time, and there is no garbage collector standing behind it. When an owner dies, the value dies with it, right then. That second half of the deal matters so much it gets its own section below.

fn main() {
    let text = String::from("hello");
    let moved = text;          // the String moves: `text` is now dead
    // println!("{text}");     // would not compile: value moved out
    println!("{moved}");
}

The async payoff comes in two parts. First, a suspended async computation is itself a value, a plain object you can store, pass around, and hand to other code, and it will be moved as it travels. Second, because there is no garbage collector, the moment such a computation is dropped, every resource it holds is released immediately and deterministically. Part 4 turns that precision into Rust's entire approach to aborting work: there is no kill signal, there is only "the value went away."

Drop: death has a schedule

When a value's owner goes out of scope, Rust runs the value's destructor before freeing it. The destructor is the Drop trait's drop method, and it runs at a moment you can point at in the source, not "eventually" the way a garbage collector would have it.

struct Connection(&'static str);

impl Drop for Connection {
    fn drop(&mut self) {
        println!("closing {}", self.0);
    }
}

fn main() {
    {
        let _c = Connection("session-1");
        println!("working");
    }                        // Drop runs HERE, not later
    println!("after the scope");
}

Run that and the closing line prints before "after the scope". The async payoff: when an engine abandons a suspended computation mid-flight, dropping it runs every destructor in its state: buffers, guards, sockets. Nothing leaks, nothing lingers, and no separate cleanup call is needed. Aborting work, when you meet it in Part 4, is literally just this.

Traits, trait objects, and vtables

A trait is an interface: a set of methods a type can implement. There are two ways to call trait methods. Generics (fn f<T: Greeter>(g: T)) make the compiler stamp out a copy of f per concrete type, so calls are direct and inlinable. That is static dispatch, and the word static here just means "resolved at compile time".

The other way is a trait object: dyn Greeter, usually behind a pointer like Box<dyn Greeter>. One box can hold any type that implements the trait, and the type can even be chosen at engine. The cost is dynamic dispatch. A trait object is a fat pointer: the data pointer plus a pointer to a vtable, a table of one function pointer per trait method. Every call loads the address out of the table and jumps through it.

trait Greeter {
    fn greet(&self) -> String;
}

struct Casual(&'static str);
struct Formal(&'static str);

impl Greeter for Casual {
    fn greet(&self) -> String { format!("hey, {}!", self.0) }
}

impl Greeter for Formal {
    fn greet(&self) -> String { format!("Good evening, {}.", self.0) }
}

fn main() {
    let greeters: Vec<Box<dyn Greeter>> = vec![
        Box::new(Casual("ada")),
        Box::new(Formal("grace")),
    ];
    for g in &greeters {
        println!("{}", g.greet()); // dynamic dispatch through the vtable
    }
}

The async payoff: an engine that juggles thousands of suspended computations of a hundred different types cannot give each one its own monomorphized type. It stores them uniformly behind trait objects, one vtable per distinct suspended type, and calls the one method that matters through it. You will write the trait being called on the next page, and meet the boxed form of it in the mini engine on page 7.

Send and Sync: can it cross a thread?

Send and Sync are auto traits: the compiler derives them for your types automatically when their contents qualify, and almost everything in std qualifies. Send means the value can be moved to another thread safely. Sync means several threads can hold &references to it at once safely. A type that fails the test, like Rc, is simply marked !Send, and the compiler refuses at the boundary.

Why does async care? Because real engines do not run on one thread. They run a pool of OS threads, like the thread pools you met in Part 2, and suspended computations migrate between those threads. Anything that crosses must be Send. This is exactly why the function that hands a computation to Tokio demands Send plus the lifetime bound below: the workers are different threads, and the value will be moved to whichever one gets it.

use std::rc::Rc;
use std::sync::Arc;

fn main() {
    let shared = Rc::new(vec![1, 2, 3]);
    let cloned = Rc::clone(&shared);
    // std::thread::spawn(move || println!("{:?}", cloned));
    // would NOT compile: Rc is !Send (its refcount is not atomic)
    let _ = shared;

    let shared = Arc::new(vec![1, 2, 3]);
    let cloned = Arc::clone(&shared);
    let handle = std::thread::spawn(move || println!("{:?}", cloned));
    handle.join().unwrap();        // Arc is Send: fine
    println!("{:?}", shared);
}

The difference between the two reference counters in that example is one word, and it is the next section's subject.

Atomics: counting without a lock

An atomic operation is a hardware instruction that reads and writes memory in one indivisible step, even under concurrent access from multiple cores. Types like AtomicUsize wrap those instructions: fetch_add, compare_exchange, load, store, each with a memory-ordering annotation that tells the compiler and CPU how far other operations may be reordered around it. Atomics are the cheap end of shared mutable state: no thread ever sleeps waiting for one.

use std::sync::atomic::{AtomicUsize, Ordering};
use std::sync::Arc;

fn main() {
    let hits = Arc::new(AtomicUsize::new(0));
    let mut handles = Vec::new();
    for _ in 0..4 {
        let hits = Arc::clone(&hits);
        handles.push(std::thread::spawn(move || {
            hits.fetch_add(1, Ordering::Relaxed);
        }));
    }
    for h in handles { h.join().unwrap(); }
    println!("hits = {}", hits.load(Ordering::Relaxed)); // hits = 4
}

Arc ("atomically reference counted") shares ownership across threads by keeping its count in atomics, which is what makes it Send and Sync. Rc keeps a plain counter, which two threads could increment simultaneously and lose an update, so it stays thread-bound forever. The async payoff: the wake-up handles you will build on page 3 get cloned on one thread and fired from another, so they are reference counted exactly the way Arc is, and every coordination counter inside a real engine's queues is an atomic.

'static: owning your whole body

The 'static lifetime is Rust's longest and most misunderstood label. A value is 'static when it can live for the entire rest of the program: either it is a compile-time constant baked into the binary, or it simply owns everything it touches, so nothing can dangle out from under it. A String you build while the program runs is 'static in this sense; a &'a str borrowed from someone else's buffer is not.

When an engine takes your suspended computation and keeps it in a queue of unbounded lifetime, it demands 'static: no borrowed locals from the function that created it, because that function will have returned long before the computation finishes. The standard escape hatch is to move owned data in, wrapped in an Arc if several computations need to share it. You will see this exact bound on Tokio's hand-off function when Part 4 dissects it.

Move closures: capture by value

A closure is a function value plus the environment it captured. By default Rust captures by the least demanding access that works: borrow where possible, move only when forced. The move keyword forces capture by value, ownership and all.

fn main() {
    let name = String::from("ferris");
    let greet = move || println!("hello, {name}");
    // println!("{name}");  // would not compile: moved into the closure
    greet();
}

The async payoff is the deepest one on this page. An async block or function captures its environment exactly like a move closure does, because that is more or less what it compiles to: a generated structure holding the captured variables, plus the machinery to run the body a step at a time. Page 5 opens that structure up on the table. When you write async move you are choosing this capture mode explicitly.

That is the whole toolkit. Nothing exotic: no macros beyond the surface syntax, no hidden engine secreted into your binary. Everything Rust's async story is built from is either on this page or gets built by hand in the next six pages, starting with a trait that is one method long.
