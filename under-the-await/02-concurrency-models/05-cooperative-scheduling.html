Cooperative scheduling

The fifth entry in this tour is not another way to wait. It is the rulebook that the last two strategies cannot live without. Once suspended coroutines (or goroutines) are cheap enough to number in the hundreds of thousands, a new question dominates everything: who runs, on which worker, and for how long? Answer it badly and your million cheap things queue up behind one greedy function. Answer it well and a handful of OS threads serve all of them with barely a complaint.

No alarm clock saves you

Recall how the kernel handles contention: it is preemptive. A timer interrupt fires, the kernel takes the CPU away from whoever is on it, and it hands the CPU to someone else, whether the running code consents or not. No thread can hog a core past its slice. Fairness is enforced by hardware.

Inside a language's own machinery, that safety net is gone. The deciding code, whatever dispatcher or loop your platform runs, only gets a say between pieces of your code. It cannot interrupt a running function mid-arithmetic. It runs when a function pauses or returns, and at no other time. You met this deal on the event loop page as the cooperative contract; now it is the entire subject. Cooperation is not a style choice here. It is a structural fact about anything that schedules inside one thread.

Yield points

A yield point is a place where a running job hands control back to the machinery: an await that is not finished, a sleep, a receive on an empty pipe, an explicit "someone else's turn" call. Between yield points, you own the worker, completely, and nothing can take it from you. The whole fairness question collapses into one sentence: how far apart are your yield points?

Python makes this visible in the smallest possible program. asyncio.sleep(0) does not sleep at all; it is the canonical explicit yield, a pause of zero duration whose only effect is giving the loop a chance to run someone else:

import asyncio

async def ping(name):
    for i in range(3):
        print(name, i)
        await asyncio.sleep(0)   # yield point: "someone else's turn"

async def main():
    await asyncio.gather(ping("A"), ping("B"))

asyncio.run(main())
A 0
B 0
A 1
B 1
A 2
B 2

Two coroutines, one thread, perfectly interleaved, because each one reaches a yield point after every single line. Now the counterexample. Delete the await from a busy loop and the interleaving does not degrade, it ends:

async def rude():
    x = 0
    while True:        # no yield point anywhere inside
        x += 1         # this coroutine now owns the thread, forever

Run rude() alongside anything else and nothing else ever runs again. This is starvation in its purest laboratory form: no lock contention, no slow disk, just one function that never came up for air. The kernel would have evicted it after a few milliseconds. The cooperative dispatcher cannot evict it at all.

Run queues and work stealing

Yield points solve "when does the machinery get control." The next question is "what does it run next." The answer, in every serious implementation, starts with a deceptively boring structure: a per-worker to-do list. A run queue is exactly that, one worker's private queue of runnable jobs, sitting right next to the code that drains it.

Why per-worker, rather than one big shared list? Because the shared list is a hotspot. Every push, every pop, from every worker, through one lock, on every scheduling decision, and the line at that lock grows exactly as fast as your core count. Private queues make the common case lock-free and local: a worker finishing a job grabs the next one from its own list, in cache, with nobody else involved.

Private queues create their own problem: work arrives unevenly, and soon one worker has a backlog while its neighbors idle. The fix is work stealing. When a worker's own queue is empty, it does not go to sleep; it looks at the other workers' queues and takes a portion of the busiest one for itself. In Go, the thief takes half the victim's queue in a single heist, which keeps the whole system balanced with a minimum of thieving traffic:

each worker owns a run queue of runnable jobs

when my queue is empty:
    check the global queue          # shared fallback
    try to steal half of a busy worker's queue
    otherwise sleep in the netpoller

What real systems do

Go's policy you can now read fluently from the GMP page: each P drains its own run queue, steals half a neighbor's when empty, and leans on yield points inside its pipes and locks, plus explicit politeness. Go also arms a backstop for the rude loop: since Go 1.14, a watchdog in the machinery can force a hogging goroutine off the CPU with a signal, roughly once every 10 ms, because a decade of production taught them that somebody always writes while true without a pause in it. The polite call still exists for when you know better:

package main

import (
	"fmt"
	"runtime"
)

func main() {
	go func() {
		fmt.Println("hello from a goroutine")
	}()
	runtime.Gosched() // explicit yield point: "my turn is done"
	fmt.Println("hello from main")
}

Java's virtual thread machinery takes the same default from a different angle: its dispatcher is a work-stealing ForkJoinPool running in first-in-first-out mode, sized by default to the number of available processors, and because suspension there is invisible, the yield points are the blocking calls themselves. You do not mark them. You do not see them. The machinery finds them at the moment a carrier is about to stall.

Python's asyncio is the minimal end of the spectrum: one event loop, one run queue of ready coroutines, no stealing because there is nothing to steal from, and fairness that is exactly as good as your yield discipline. The differences among these systems are real, but note how small they are next to what they share. Run queues, stealing, and the dependence on yield points: the shape is universal.

The rule

Everything on this page compresses into one habit: keep the stretch between your yield points short. Short is not a fixed number, and pretending otherwise would be dishonest. It is a tradeoff between your throughput (yielding has a small cost) and everyone else's latency (never yielding has an unbounded one). The damage you can do is proportional to the longest stretch of unyielding work you ship.

The rule has a thousand disguises. Sorting a big array inside one coroutine. Parsing a large document. Holding a tight loop that "will only take a moment." On a cooperative system, every one of those is a decision made on behalf of every other job on the same worker, and none of them consults those jobs first.

Rust's position on this rule is stricter than any system on this page, and it arrives in two steps. Part 3 builds the machinery that makes suspension a value you control, and Part 4 shows the engine room where this page's ideas, run queues, stealing, and yield points, are enforced with real numbers: workers get queues, thieves get rules, and every job gets an allowance of steps per turn, after which it is pulled over and made to yield whether it wanted to or not.

In this chapter

  • Inside one thread there is no preemption: the machinery runs only between your yield points, so fairness is a contract every job must keep, not a right the kernel enforces.
  • A yield point is any place a running job hands control back: an unfinished await, a sleep, a receive, or an explicit polite call; the distance between them decides everyone else's latency.
  • A run queue is one worker's private to-do list of runnable jobs; private queues avoid a shared hotspot, and work stealing rebalances them when an idle worker takes half a busy neighbor's backlog.
  • Real policies vary: Go steals halves and arms a preemption backstop, Java's dispatcher steals in FIFO order at invisible yield points, asyncio runs one loop and trusts your discipline.
  • The rule underneath all of them: keep the stretch between yield points short. Part 4 shows Tokio enforcing it with a fixed step allowance per job.
