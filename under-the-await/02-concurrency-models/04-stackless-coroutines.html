Stackless coroutines

Strategy four is the one this book has been walking toward, so take it slowly. Green threads made suspension cheap by shrinking the stack. This strategy makes one observation sharper: if you only ever pause where you chose to mark, you do not need a stack at all. The pause can be stored as a small value. And a value, unlike a stack, is something your program can own, inspect, move, and hand to a loop. That inversion, from "the machinery owns my paused code" to "my paused code is a value I own," is the seed of everything in Parts 3 and 4.

A function that pauses

A coroutine is a function that can pause mid-run, keep its place and its local variables, and be resumed later from that exact place. Regular functions cannot do this. When a regular function returns, its locals are gone and its stack frame is reclaimed. A coroutine suspends instead: it steps off to the side, and everything it needs to continue survives.

JavaScript had the bare mechanism years before it had async, in the form of generators. Look at one pausing in mid-function:

function* countdown() {
  console.log("started");
  yield 3;              // pause: hand back 3, keep your place
  console.log("resumed");
  yield 2;              // pause again
  return 1;
}

const it = countdown();   // nothing has run yet
it.next();  // logs "started", returns { value: 3, done: false }
it.next();  // logs "resumed", returns { value: 2, done: false }
it.next();  // returns { value: 1, done: true }

Read that last block again, because it is the whole strategy in four lines. countdown() did not run when called. It produced an object, it, that stands for a computation frozen at the very start. Each next() thaws it, runs to the next yield, and refreezes it. The paused function is not a concept. It is an object sitting in a variable, waiting to be asked for its next step.

async/await: coroutines with a contract

Generators hand values back. What suspension-for-I/O needs is a slight variation: hand control back, and be resumed when some operation completes. That is exactly what async/await is. An async function is a coroutine that pauses at every await, and each await marks a suspension point: the place control can leave this function.

Here is the three-file flow from the callback pyramid, rewritten. Same operations, same order, same single thread:

const fs = require("fs/promises");

async function renderPage() {
  const text = await fs.readFile("config.json", "utf8");       // pause 1
  const config = JSON.parse(text);
  const template = await fs.readFile(config.template, "utf8"); // pause 2
  const footer = await fs.readFile(config.footer, "utf8");     // pause 3
  return render(config, template, footer);
}

The wedge became a straight line. The code reads top to bottom, exactly like the blocking code from Part 1, but it never blocks a thread. At each await, if the result is not ready, the function suspends: it returns control to whoever asked it to run, carrying a promise to continue later. When the file arrives, the loop resumes it at that exact line, with text and config intact, as if nothing had happened.

Python's version makes the object-nature impossible to miss. Calling a coroutine function does not run it. It builds a coroutine object and hands it to you:

import asyncio

async def greet():
    print("started")
    await asyncio.sleep(1)   # the marked pause
    print("finished")
    return "done"

coro = greet()      # calling it runs nothing yet
print(coro)         # the object itself, printed like any value
asyncio.run(coro)   # the loop drives it through its pause
<coroutine object greet at 0x7f31c9a5f340>
started
finished

That first line of output is not a metaphor. A paused computation printed its address, because it is an object on the heap with an identity, the same as any list or dict you have printed. Nothing inside it ran until the loop asked it to.

Stackless: what a pause actually stores

Here is the distinction this page owns. Green threads are stackful: pausing preserves an entire call stack, so the pause can happen anywhere. Coroutines like these are stackless: the function keeps no private stack at all. It may pause only at its marked suspension points, and what survives a pause is the compiler's own minimal summary:

what the compiler stores for renderPage() at pause 2, conceptually:

    +-------------------------------------------------+
    | state: WAITING_ON_TEMPLATE                      |
    | live locals: text, config                       |
    | resumption: just after the template read        |
    +-------------------------------------------------+

a state tag, the two locals still in use, nothing else. no stack.

The compiler turns the async function into a small state machine: one state per await, and the fields are exactly the locals alive across that await. Nothing more is kept, because nothing more can be needed: the pause can only resume at a marked point, and between those points the regular stack does its regular job.

Where it can pause anywhere, even ten calls deep only at marked suspension points
What a pause stores an entire call stack a state tag plus the live locals
Memory per paused thing kilobytes upward the size of a small struct
Who finds the machinery invisible: the language hides it visible: every pause is in your source

The suspended coroutine is a value

Now the payoff, stated as plainly as I can manage. A suspended coroutine is a value. You can assign it to a variable. You can put it in a list. You can pass it to a function, return it from one, keep it for a millisecond or an hour. And whenever you like, you can ask it to continue. When you ask, exactly one of two things happens: it runs to its next suspension point and answers "still waiting," or it runs to completion and hands you its return value.

Two answers. "Still waiting," or "here is the result." Hold onto that pair; you will meet it again, wearing different clothes, as the load-bearing idea of Part 3.

Compare what suspension costs in each model. Pausing a green thread leaves you holding a liability: a whole preserved stack that must be kept alive and managed by machinery you cannot see. Pausing a stackless coroutine leaves you holding an asset: a small object, the size of its live variables, that your code can own like any other value. The event loop from two pages ago can keep a million of them in a collection, and each time a readiness event arrives, ask the matching paused coroutine to continue. This is precisely how asyncio, and Node under its syntax, and Tokio after them, actually work.

The general concept deserves its name before we go on. A continuation is "the rest of the computation," packaged as a thing. Every function you have ever called had a continuation: the code waiting at the call site. What these coroutine objects give you is a continuation you can hold in your hand, a materialized "and then," that you can choose to run, defer, or abandon. Callbacks, from the previous page, are continuations spelled out by hand, one nested function at a time. Promises are continuations with a contract. Stackless coroutines are continuations the compiler packages for you, automatically, at every await.

This is the door Rust picks: door number four. In Rust, the paused function becomes a plain value with a strict, small protocol for being asked to continue, built by the compiler from your async functions. Part 3 names it, builds one by hand before the keyword does it for you, and then takes the compiler's transform apart line by line.

The tax: function coloring

Nothing in this strategy is free, and its cost has a famous name. Suspension is now part of a function's type. An async function does not return a value; it returns a promise of one, or a coroutine object. A plain function that calls it receives that object, and cannot stand still and wait for the value inside: waiting requires being able to pause, and plain functions cannot pause. So the caller must become async too, and its caller, and so on outward. This virality is function coloring: two colors of function in one program, and the boundary between them must be managed by hand, usually at the top of your program.

You have already written this boundary without noticing. asyncio.run(...) exists precisely to let ordinary Python drive a colored function. Node's top-level await exists for the same reason. And every library author in the JS and Python ecosystems has faced the question "should this function be async?", knowing the answer stains every caller.

Go has no such boundary, and that is a genuine, daily ergonomic win for green threads: every function may block, so there is one color and nobody thinks about it. The stackless world pays in colors what the stackful world pays in kilobytes.

There is a refund, though, and it is not sentimental. In the stackless world, every place control can possibly leave your function is marked in your source with await. You can look at a function and know exactly where it might be interrupted, because it can only be interrupted there. Reasoning about interleavings becomes a local, readable property instead of a global, invisible one. When Part 4 shows you where a Rust program may be paused, resumed, or quietly abandoned, the marks will already be in front of you.
