Green threads

The event loop made waiting nearly free and made your code pay for it in shape. Strategy three refuses that trade. It asks: what if a thread were cheap? Not the kernel's threads, which come with megabyte stacks and microsecond price tags, but threads you build yourself, in user space, where you decide what a thread is made of.

A green thread is exactly that: a thread implemented by your language's own machinery rather than by the kernel. The kernel still owns the real threads, and there are only a handful of those. Your language's dispatcher maps the many cheap threads onto the few expensive ones. The shorthand is M:N scheduling: M green threads ride on N OS threads. Every green thread behaves like a thread. It can block. It can be blocked on. It just does not cost a kernel thread while it waits.

Go: goroutines and GMP

Go is the flagship of this strategy. Its green threads are called goroutines, and starting one is a single keyword:

package main

import "fmt"

func greet(name string) {
	fmt.Println("hello,", name)
}

func main() {
	go greet("ada")   // a new goroutine, launched and forgotten
	go greet("grace")
	fmt.Scanln()      // keep the program alive while they run
}

That go keyword is the entire user-facing API, and its cheapness is the point: a goroutine starts with a few kilobytes of stack, so a program can hold millions of them without anyone budgeting for it. When a goroutine's stack outgrows its start, Go's machinery allocates a bigger one and copies the old contents over, so deep recursion still works.

Compare that to the kernel's bill from Part 1: a real thread reserves about 8 MB of stack address space by default and measures in megabytes, not kilobytes, per waiter. A hundred thousand goroutines at a few kilobytes each is a manageable amount of memory. A hundred thousand OS threads is not a server, it is an incident.

How do the pieces fit? Go's answer is usually summarized as GMP, and you will want the three letters later:

  • G is a goroutine: your function, its small growable stack, and a note of where its execution stands.
  • M is a machine: a real OS thread, the only thing that can actually execute code.
  • P is a processor: the right to run Go code on some M, plus a ready list of runnable goroutines. An M must hold a P to execute your functions.

The number of Ps is capped at GOMAXPROCS, which defaults to your CPU count, so no matter how many goroutines exist, only that many run simultaneously:

package main

import (
	"fmt"
	"runtime"
)

func main() {
	fmt.Println(runtime.GOMAXPROCS(0)) // how many Ps exist here
}

The elegant part is what happens when a goroutine blocks. Say it reads a socket. The Go machinery knows about the read, hands the waiting job to its built-in network poller (its private epoll-shaped layer), and immediately runs a different goroutine on the same M. The OS thread never sleeps. It does not even know a context switch of the interesting kind happened; from the kernel's point of view, that thread has been busy the whole time.

Goroutines need to talk to each other, and Go hands them typed pipes, spelled chan in code. One goroutine puts a value in, another takes it out, and if one side is not ready the other suspends until it is:

package main

import "fmt"

func produce(out chan int) {
	for i := 0; i < 3; i++ {
		out <- i // hand a value to whoever receives
	}
	close(out)
}

func main() {
	out := make(chan int)
	go produce(out)
	for v := range out { // receives until the pipe closes
		fmt.Println("received", v)
	}
}

Stackful: the fine print on "anywhere"

Notice what Go never asked you to mark. A goroutine can block deep inside a nested call, ten frames down, inside a library you do not control. That works because green threads are stackful: each one carries its own call stack, so to pause it, the machinery saves the whole stack, registers and all, and can later resume it exactly where it stood, however deep that was. Suspension can happen anywhere, because everything needed to resume is kept.

That power is also the bill. A stack per green thread means kilobytes at minimum, megabytes if a call graph gets deep, and it means the stack must be managed: grown by copying, or chopped into segments, both of which cost and both of which have bitten real implementations. And it means trouble at the edges of the language. Foreign function interfaces expect to run on a real thread's stack; mixing your own stack switching with C code that was never told about it is a permanent source of exotic bugs. Every stackful system pays a complexity tax at that boundary.

Java's virtual threads: the same idea, arriving officially

Java spent years on the thread-per-request model, hit exactly the arithmetic you saw in Part 1, and then shipped the M:N fix as virtual threads. A virtual thread is a java.lang.Thread that is not tied to any particular OS thread. A small pool of real "carrier" threads (a default of one per available processor) runs them, and when a virtual thread performs a blocking operation in the standard library, the JDK quietly performs a non-blocking call instead, unmounts the virtual thread from its carrier, and frees the carrier for other work:

public class Main {
    public static void main(String[] args) throws Exception {
        try (var pool = java.util.concurrent.Executors
                .newVirtualThreadPerTaskExecutor()) {
            for (int i = 0; i < 100_000; i++) {
                int id = i;
                pool.submit(() -> {
                    Thread.sleep(1000); // suspends the virtual thread only
                    return id;
                });
            }
        } // closing waits for all 100,000 to finish
    }
}

A hundred thousand sleeping threads, done in a page of code, with the ordinary blocking style. The catch has two parts. First, unlike the cooperative loop of the previous page, you control nothing about when the switch happens: it is invisible, decided by the JDK at blocking calls, which is ergonomic magic and a debugging puzzle at the same time. Second, the escape hatches leak: inside a synchronized block, or any native call, a virtual thread cannot unmount, and its carrier is held hostage for the duration. The official guidance is to swap long-blocking synchronized sections for ReentrantLock in hot paths.

M:N is a contract with the language's own machinery, and the contract has fine print. If a library does I/O in a way the machinery cannot see, the green thread cannot let go of its OS thread, and your N quietly grows toward your M. Every green thread ecosystem keeps a list of "known ways a thread gets stuck to its carrier," and every operator of one has personally found an entry the hard way.

The honest ledger

Green threads deliver the dream ergonomics: blocking-style code that scales to enormous concurrency, one color of function, no inversion of control. The price is paid in memory, kilobytes per waiter instead of bytes, and in machinery: your language needs a dispatcher, stack management, a network poller, and answers for every awkward boundary like foreign calls. Go and the modern JVM decided that price is worth paying, and they may well be right for their goals.

The next page keeps what green threads bought, cheap suspension at scale, and throws away the thing that made it heavy. If you only suspend at points you choose, you do not need a stack at all. The pause can be a value.

Rust walked through this door once: green threads shipped in its pre-1.0 days and were deleted before 1.0. Part 3 explains the bet Rust made instead. It is door number four.
