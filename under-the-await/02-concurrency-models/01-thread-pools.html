Thread pools

Part 1 ended with a ledger instead of a verdict. One OS thread per wait gives you code that reads top to bottom, but every waiting thread costs you a whole kernel thread with its own stack. Handling waits with readiness events is cheap, but it asks you to restructure your program around them. Part 2 tours the ground between those two poles: five strategies that languages and platforms have built for keeping many things in flight at once.

The first strategy is the least exotic of the five, and you have almost certainly already used it. It keeps the thread-per-job model and attacks a different cost: creation. Stop building threads when you need them. Reuse the ones you have.

The tax you are avoiding

Creating a thread is not free. On modern Linux, measuring thread creation lands somewhere between 5 and 20 µs, and each new thread reserves around 8 MB of stack address space by default. The stack reservation is virtual memory, most of it untouched, so it is cheaper than it first sounds. The construction and teardown cost is real though, and a server that builds a fresh thread for every request pays it on every burst of traffic. Kernel work, allocator work, teardown work, all to run a few milliseconds of your code.

There is a second reason to cap the count. The kernel divides each core's time among every runnable thread, and every context switch between them costs a microsecond or two of pure overhead before your code does any useful work at all. A handful of threads per core and the kernel barely notices. Thousands of them, and the bookkeeping starts eating the meal.

A thread pool is the fix, and it is exactly what the name suggests: a fixed crew of OS threads created once, kept alive, and fed from a shared queue of jobs. Code that wants work done puts a job on the queue. Every worker runs the same tiny loop for its entire life, and it never changes:

a shared FIFO queue of jobs
N worker threads, each running:

    loop forever:
        job = take the next job from the queue   # sleeps while the queue is empty
        run job to completion
        repeat

When the queue is empty, the workers sleep inside the kernel and cost you nothing but memory. When work arrives, a worker wakes, runs the job, and goes back for more. No thread was created. No thread was destroyed. The expensive part of the pattern happened once, at startup.

Two pools, two languages

You rarely hand-roll this. Every mainstream platform ships a pool, and the APIs all hide the queue and the workers behind one method: "here is a function, run it somewhere that is not me."

Python's standard library version takes a function and a list, fans the work out, and gathers the results:

from concurrent.futures import ThreadPoolExecutor
import urllib.request

URLS = [...]  # a few hundred addresses to fetch

def size_of(url):
    with urllib.request.urlopen(url) as response:
        return len(response.read())  # blocks this worker, not your program

with ThreadPoolExecutor(max_workers=32) as pool:
    results = list(pool.map(size_of, URLS))

Java's is older and more explicit, but the shape is identical. You submit closures to a service, and a fixed crew runs them:

import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;

public class Main {
    public static void main(String[] args) {
        ExecutorService pool = Executors.newFixedThreadPool(8);
        for (int i = 0; i < 100; i++) {
            pool.submit(() -> System.out.println("job on " + Thread.currentThread()));
        }
        pool.shutdown();
    }
}

Notice what both APIs refuse to show you. You never see the queue. You never see the workers. You cannot say which thread ran your job, because the whole point is that it does not matter. The pool has bought you parallelism and a little isolation, and it has quietly bought something else: your job must now be self-contained, because it will run on a thread you do not own, on a stack you share with every job that came before you.

Sizing the crew

How many workers should you hire? The answer depends on what the jobs do, and the two cases pull in opposite directions.

Kind of workSensible sizeWhy
CPU-bound (hashing, parsing, image work) about one worker per core extra workers just queue up and add switching overhead
I/O-bound (HTTP calls, database queries) dozens, sometimes a few hundred workers spend most of their life asleep, so more of them fit
A mix of both measure, then split the pools the honest answer, always

The I/O row is where the temptation lives. If workers sleep through most of their jobs, why not add more? You can, and for a while it works beautifully. But every added worker is still a real OS thread with a real stack, and the arithmetic from the C10K page has not gone anywhere: 10,000 threads at 8 MB of reserved stack each is on the order of 80 GB of virtual address space, plus creation cost, plus switching overhead, plus kernel limits on total thread counts. A pool makes each thread cheap to reuse. It does not make the thread cheap to have.

The ceiling: blocked is blocked

Here is the limit that matters most for where this book is going. A pool amortizes thread creation. It changes nothing about what blocking means. When a worker calls read() on an empty socket, that worker enters the kernel and sleeps on a wait queue exactly as it would have without a pool. The pool cannot rescue it. The kernel cannot rescue it. From the outside, the pool just got one worker smaller, and it stays that way until data arrives.

This failure mode has a name: head-of-line blocking. When the item at the front of a line cannot proceed, everything queued behind it waits too, no matter how quick and ready those later items are. In a pool it shows up two ways. Locally: a worker stuck in one slow call is a worker that cannot take the next job. Globally: if every worker is stuck in the same slow call, the queue grows without bound and freshly submitted jobs pile up behind everyone else's bad luck.

The classic production incident: a downstream service slows down, every worker submits a call to it, every call hangs for TCP's full retry window, and suddenly your "pool" is a waiting room with zero employees. The pool was sized for throughput, not for stuckness. If a job can block for minutes, no pool size saves you; you need a different way to wait.

What pools are genuinely great at

None of this is an argument against pools. For CPU-bound parallelism they are the correct tool, full stop: one worker per core, no more, and the machine hums. For modest I/O concurrency, dozens to a few hundred simultaneous operations, they are simple, debuggable, and fast enough that nobody complains. The code inside each job stays in the comfortable, blocking style you know. That is a real ergonomic win, and Part 1 already showed you what the alternatives cost in code shape.

The pool just has a ceiling, and the ceiling is architectural rather than tunable. Past a few hundred concurrent waits you are renting threads to sleep in. To juggle tens of thousands of waits, you need to stop paying one thread per wait, which means the waiting itself has to change shape. The next strategy does exactly that: keep one thread, keep the kernel's readiness events, and register functions to call when things become ready.

Rust keeps this trick in its back pocket. Part 4 shows a pool of plain OS threads living inside Tokio, reserved for work that insists on blocking. But Rust's main road runs elsewhere, through door number four, and the next two pages walk up to it.

In this chapter

  • A thread pool is a fixed crew of OS threads created once, draining a shared FIFO queue of jobs; you pay thread creation once instead of per job.
  • Sizing follows the work: about one worker per core for CPU-bound jobs; more only for I/O-bound jobs, where workers sleep through most of their shifts.
  • A pool reuses threads but cannot unblock them: a worker sleeping in the kernel is still gone from the crew, and head-of-line blocking piles jobs up behind it.
