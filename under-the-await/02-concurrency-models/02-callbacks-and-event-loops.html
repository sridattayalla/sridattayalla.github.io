Callbacks and event loops

Strategy one kept one thread per wait and made the threads reusable. Strategy two goes further: it keeps exactly one thread for all the waits. You already own every piece of machinery this needs, because Part 1 built it. Non-blocking I/O lets you ask "is there data?" instead of "give me data." epoll lets one thread ask that question about thousands of sockets at once and sleep until the kernel reports readiness. The only thing still missing is the answer to: when socket 7 finally has data, whose code should run?

One thread, one table, one loop

The answer is a table, and the table turns out to be the whole architecture. For every socket you care about, you register a function: "when this one is readable, call me." Then you write a loop that lives forever: ask the kernel what became ready, look up each answer in the table, call the matching function, repeat. This arrangement, a loop that reacts to readiness events by dispatching pre-registered handlers, is called a reactor, and it is the skeleton underneath Node.js, nginx, Redis, and every GUI toolkit you have ever used.

The loop itself is the event loop: one thread running a cycle of wait, dispatch, run, repeat. Written out, it is almost embarrassingly small:

a table mapping each watched fd to a handler function

loop forever:
    ready = wait for readiness on the watched fds   # epoll_wait: sleeps here
    for each ready fd:
        handler = table[fd]                          # "when 7 is readable, call this"
        handler()                                    # runs to completion, returns here
    run any expired timers, then repeat

Every registered function is a callback: a piece of code you hand to someone else, to be called later when a condition arrives, not now when you write it. The word is older than event loops. You have used callbacks for buttons and timers forever. The event loop just makes them the primary way a server expresses "and then."

Look at what this buys you. Ten thousand open sockets cost you a table with ten thousand entries and one sleeping thread. Memory use is a few bytes of bookkeeping per connection. The C10K arithmetic that crushed thread-per-connection simply does not apply here, because there are no threads to pay for.

Node.js: the flagship

Node.js made this model famous by bolting it to JavaScript. Underneath sits libuv, a small C library that implements exactly the loop above: a table of handlers, an epoll (or kqueue, or IOCP) backend, and a queue of expired timers. On top of that, every I/O operation in Node's standard library takes a callback as its last argument. Reading a file looks like this:

const fs = require("fs");

fs.readFile("config.json", "utf8", (err, text) => {
  if (err) return console.error("config:", err);
  const config = JSON.parse(text);

  fs.readFile(config.template, "utf8", (err, template) => {
    if (err) return console.error("template:", err);

    fs.readFile(config.footer, "utf8", (err, footer) => {
      if (err) return console.error("footer:", err);
      render(config, template, footer);
    });
  });
});

console.log("still running: readFile returned immediately");

Three files, each read only after the previous one finishes, and the code has already collapsed into a wedge. Each callback receives the results of the step before it, and each must handle its own error, because there is no enclosing function left to catch anything. Trace what happens when readFile is called: it returns immediately (that last line proves it), and your function is stashed in the table for later. Control flow no longer follows the shape of the code on screen. It follows the order the kernel reports events.

This inversion has a name that stuck before the nicer syntax arrived: callback hell. The symptoms are visible above: nesting that grows rightward with every sequential step, error handling repeated by convention in every layer, and stack traces that end at the loop, because by the time your callback runs, the function that registered it returned long ago. Your handler runs on a fresh, nearly empty call stack. The code that was logically "after" your read is no longer below you on the stack. It is a different function, registered somewhere else, waiting for its own moment.

The deal you signed

Here is the part that will matter for the rest of this book. The event loop never interrupts a running handler. There is no timer, no preemptive machinery, nothing that tears your function off the CPU. The loop gets control back exactly once: when your handler returns. Until then, every other connection on the server waits, including ones whose data is already sitting in the kernel, ready.

An arrangement where running code decides when to give the CPU back, by returning, is cooperative. The word will follow you to the last page of this book, so fix it now: the alternative, the kernel's model, is to rip control away on a timer whether you like it or not. The loop cannot do that. It only schedules between your functions, never during them.

Two consequences follow, and they are two faces of the same coin. Fairness is the property that every registered handler gets its turn in reasonable time. Starvation is what happens when one handler breaks the deal: a function that runs for a second starves every other connection for that second, completely, no matter how idle the machine is.

Real incidents look like this: a handler parses a huge uploaded JSON document synchronously, or runs a regex over untrusted input, or sorts a large array, and the p99 latency of every unrelated request on the server spikes for exactly that long. The event loop was not slow. One tenant of it was. Nothing on a single-threaded loop is concurrent; everything on it is merely interleaved.

There is a genuine upside hiding next to that cliff. Because one thread runs every handler, two handlers can never be mid-flight at the same instant, so they cannot race on shared state the way two threads can. No locks between handlers. The price is that your data structures can still be observed half-updated across callbacks: state you set before an asynchronous step may surprise the callback that runs after it. Concurrency did not disappear. It moved into your program's logic.

Promises: the same deal, better handwriting

JavaScript later grew Promise objects to flatten the pyramid. A Promise is a placeholder for a result that does not exist yet, plus a chain of functions to call when it arrives:

const fs = require("fs/promises");

fs.readFile("config.json", "utf8")
  .then((text) => JSON.parse(text))
  .then((config) => fs.readFile(config.template, "utf8")
    .then((template) => render(config, template)))
  .catch((err) => console.error("any step:", err));

Flatter, and the error handling is fixed in one place, which is a real improvement. But look closely at what .then(...) takes: a function, to be called later by someone else. A Promise is a callback with a contract, a memory, and nicer syntax. The inversion of control is still there, one layer down. You still cannot write "load the config, then use it" as consecutive lines of code.

That final step, writing asynchronous flows as flat, consecutive lines, needs functions that can pause without dying. That is the next strategy but one, and the page you are building toward. First, though, the industry took a detour through a genuinely different idea: what if threads themselves were cheap?

This door, one thread plus a table of wake-up functions, is the one Node opened. Rust walks a later door, but the table returns: Part 4 shows the same idea, a registry mapping readiness events to wake-ups, living at the bottom of Tokio's I/O machinery.

In this chapter

  • A reactor registers handlers for readiness events; the event loop around it cycles through wait, dispatch, run, repeat, on a single thread.
  • Callbacks invert control: your code runs in fragments, on fresh stacks, in an order driven by the kernel's events rather than by your source layout.
  • Callback hell is this inversion compounding: nesting per sequential step, error handling by convention, and stack traces that end at the loop.
  • The model is cooperative by necessity: the loop cannot interrupt a handler, so fairness depends on every handler returning quickly, and one long handler starves everyone.
  • Promises flatten the pyramid but keep the deal: .then still registers functions to be called by someone else, later.
