The Tokio runtime: an overview

Part 3 ended with you building an executor in about sixty lines of standard Rust. It polled a future, parked the thread when the future said “not yet,” and woke up when the waker fired. It worked. It was also, deliberately, a toy: one thread, no sockets, no timers, and fairness only if every future behaved. Point it at a real server with ten thousand connections and it falls over in the first minute.

Tokio is that same idea scaled up until it stops being a demo and starts being infrastructure. This part of the book takes the machine apart, bolt by bolt. This page is the map: every piece in one picture, each piece named once, each with a pointer to the page that opens it. Everything described here is Tokio 1.x, the line the Rust ecosystem has converged on, and every number on the following pages was read out of the runtime’s source, not out of a blog post’s memory.

What “runtime” means

Rust’s standard library ships the primitive and not the machine, as Part 3’s closing page argued: Future exists in std, but nothing in std will poll it for you. A runtime is the machine you add. It is the whole bundle of threads, queues, and bookkeeping that sits between “here is a future” and “that future finished.” When people say “the Tokio runtime,” they mean, concretely:

  • a small set of worker threads, each polling futures in a tight loop;
  • the queues those workers pull from: one private run queue per worker, plus one shared inject queue;
  • a pool of extra plain threads for work that must never be allowed to stall a worker;
  • two drivers that talk to the kernel about sockets and about time, and hand woken futures back to the queues.

That is the entire cast. The rest of this part is character studies.

What the attribute builds

You normally meet all of this through one attribute:

#[tokio::main]
async fn main() {
    println!("hello from inside a runtime");
}

The attribute is a thin wrapper. It builds a runtime, hands your main future to it, and calls block_on (the trick you wrote by hand in Part 3) so the program’s original thread sleeps until main finishes. Which thread gets created first, which driver gets armed when, and what exactly happens before the first line of your code runs: that sequence deserves a page of its own, and Part 5 opens with it. Here we care about what exists, not the order it arrives in.

The map

The workers

A worker is an ordinary OS thread (Part 1 defined threads) running a very tight loop: take a future off a queue, poll it, repeat. The default runtime creates one worker per CPU core, all of them at startup. Each worker owns exactly one thing of value: its private run queue, the concept Part 2 named when it talked about cooperative scheduling. Everything else a worker touches, it shares politely or steals boldly.

Workers, their queues, and the rules that decide who runs what and when are together called the scheduler. Its full rulebook, including the order a worker searches for work and the fairness arithmetic that keeps any single future from hogging a core, is page three of this part.

The queues

Futures wait in queues; workers drain them. There are two tiers. Each worker’s local run queue is a fixed ring with room for 256 futures, lock-free for its own worker to push to. The single global inject queue accepts submissions from anywhere: the main thread, the extra threads below, anywhere that is not a worker. It also catches the overflow when a local ring fills up. Idle workers check the inject queue on a cadence and steal from busy siblings, taking half a victim’s queue in one heist. None of this is new machinery: page five of Part 2 described run queues and work stealing in general; Tokio’s exact numbers and search order are page three’s job here.

The pool for work that must not touch a worker

Some work cannot cooperate, ever. A file read that sleeps in the kernel, a DNS lookup, a hashing loop that runs for three seconds: if a worker did any of that, every future in its queue would freeze behind it, and Part 1 already showed you what parked threads cost at scale. So the runtime keeps a blocking pool: a separate set of plain OS threads, created on demand, for exactly that work. It is deliberately dumb, a thread pool from Part 2 wearing a name tag, and that simplicity is the point. Page four covers it, along with the one law it exists to enforce: a worker must never sleep in the kernel.

The drivers

A driver is the runtime’s ambassador to one source of events outside the process. Two ship by default, and both end the same way: something in the kernel says “now,” and the driver turns that into a waker call, putting a waiting future back into a queue.

The I/O driver registers every socket with epoll (or kqueue on macOS), the readiness machinery you wrestled with in Part 1’s multiplexing page. Bytes arrive, epoll reports the socket, the waiting future is woken. It is the reactor pattern from Part 2, minus callbacks, plus wakers. Page five dissects it; page six then traces a single socket read through it, hop by hop, until bytes land in your buffer.

The time driver does the same job for clocks. Sleeps and deadlines are futures too, and something has to remember when they are due without burning a thread or a sorted-list scan on every check. Page seven shows the wheel it uses.

Notice the arrows in the map: idle workers park inside the drivers. A worker with nothing to do does not spin (the busy-poll trap) and does not exit; it goes to sleep inside epoll, and the kernel itself wakes it when a socket speaks or a timer comes due. Parked is not parked the way Part 1 meant it: the runtime holds the leash and can shake it awake at any queue push.

Two more pages finish the part, and both are about what flows through this machine rather than the machine itself. Page eight covers the synchronization primitives that wait by parking the future instead of the thread. Page nine covers what happens when a future is simply never polled again.

Where Part 3 plugs in

Nothing you learned in Part 3 is wasted here; all of it is load bearing. The map above is your Part 3 vocabulary, distributed across threads:

  • Your async fn is still a state-machine enum the compiler wrote. That enum, and nothing else, is what the runtime stores.
  • Once queued, a future must not move, because it may point into itself: Pin is why the runtime stores futures as pinned heap allocations. The wrapper that makes that true is the very next page.
  • Wakers are the doors back into the machine. Every “wake” in the diagram is a waker call whose only job is to get one future back into one queue.
  • The mini executor’s loop is the worker loop, minus stealing, minus drivers, minus fairness.
  • epoll, which you drove by hand in C, sits under the drivers unchanged. Tokio adds bookkeeping on top, not a new kernel.

Two flavors

Everything above describes the multi-thread flavor, the default. The current-thread flavor runs the same queues and drivers on exactly one worker: no siblings to steal from, and the worker-conversion trick from page four is not available there. You opt into either through the builder, which is also where the knobs live:

use tokio::runtime::Builder;

let rt = Builder::new_multi_thread()
    .worker_threads(4) // default: one per CPU core
    .enable_all()      // arm the I/O driver and the time driver
    .build()?;

The numbers behind those knobs, and when a smaller runtime is the right call, come up on page three of this part and again during the boot sequence. What matters on this page is only the shape: a handful of smart threads for millions of tiny futures, a pile of dumb ones for a few long sleeps, and two drivers keeping the kernel’s news flowing. Hold that picture; the next six pages zoom into it.

In this chapter

  • A runtime is workers, queues, extra threads for blocking work, and two drivers; the rules that tie workers and queues together are page three’s subject.
  • Workers are plain OS threads, one per core by default, each draining a private 256-slot run queue; a global inject queue takes work from any other thread.
  • Idle workers steal half a busy sibling’s queue and, when all is quiet, park inside the drivers so the kernel can wake them.
  • Work that cannot cooperate (files, DNS, long CPU loops) is exiled to a separate pool of plain threads; workers never sleep in the kernel.
  • Everything from Part 3 is still here: poll, wakers, Pin, and epoll, just distributed across threads.
