Task anatomy

The map page showed futures flowing through queues, but it cheated a little: what flows through Tokio’s queues is not a bare future. The moment you hand a future to the runtime, Tokio wraps it in bookkeeping: state bits, a reference count, a function pointer, a home address. The wrapped unit is a task, and this page takes one apart on the bench.

The act of handing a future over is tokio::spawn. In code it is one line:

#[tokio::main]
async fn main() {
    let handle = tokio::spawn(async {
        let mut total = 0u64;
        for i in 0..10 {
            tokio::time::sleep(std::time::Duration::from_millis(10)).await;
            total += i;
        }
        total
    });

    // the spawned future runs on a worker while we are free to do other things
    let total = handle.await.expect("the task panicked");
    println!("total: {total}");
}

Two things just happened, and both are load bearing. First, ownership moved: the future left your hands entirely. That is why spawn demands a future that is Send and 'static (Part 3’s Rust recap covered both): a task can sit in a queue for an arbitrary lifetime and then be polled by any worker, on any thread. A borrowed local would dangle; a non-sendable type would be a data race waiting to happen. Second, you got a JoinHandle back, a receipt you can await later. We will open that receipt near the end of the page.

One allocation, three parts

What does spawn cost? One heap allocation, sized to exactly three things laid out end to end:

Start from the right, because it is the part you already know. Your async block is a compiler-written state-machine enum: one variant per suspension point, locals as fields. Tokio stores that enum inline in the allocation, sized to the byte. There is no Box<dyn Future> inside the task; the future is the tail of the allocation. This is why spawn is generic over the future type: each future shape gets its own task layout, monomorphized at compile time.

But queues hold futures of many different shapes, so they cannot hold tasks by value. They hold pointers to the header, which is always first, always the same shape. The per-shape knowledge (how big this task is, how to poll and drop it) hides behind the schedule function, a raw function pointer in the middle. If you recognize the vtable trick, yes: this is that trick, used once more, so that one queue can carry every task in the process.

The header, field by field

The header is a handful of machine words doing the work of an entire operating-system process table:

// simplified from tokio/src/runtime/task/ (fields trimmed)
struct Header {
    state: AtomicUsize,               // lifecycle bits + reference count
    scheduler: UnsafeCell<*const ()>,  // back-pointer: which queue machinery
    waker: UnsafeCell<Option<Waker>>, // the waker this task polls with
}

The state word is the interesting one. It packs lifecycle bits in the low digits and a reference count in the high ones. The bits, straight from the source:

// task state bits, simplified from runtime/task/state.rs
const RUNNING:       usize = 0b0001;   // being polled right now
const COMPLETE:      usize = 0b0010;   // future returned Ready, was dropped
const NOTIFIED:      usize = 0b0100;   // sits in a run queue right now
const JOIN_INTEREST: usize = 0b1000;   // somebody holds a JoinHandle
const JOIN_WAKER:    usize = 0b10000;  // join slot holds a waker
const CANCELLED:     usize = 0b100000; // runtime wants this task dropped

Every rule the runtime follows about a task is a compare-and-swap on these bits. A task may be in exactly one run queue at a time (NOTIFIED guards that). A task is polled by exactly one worker at a time (RUNNING guards that). A wake that arrives while the task is being polled does not get lost: it sets NOTIFIED again, so the worker re-queues the task the moment the current poll returns. Lossless waking is not a protocol on top of the header; it is the header.

Above the bits lives the reference count, and a fresh task starts at three: one reference for the queue entry, one for the JoinHandle, one for the task’s own waker slot. Every cloned waker adds one; every drop of a handle or waker subtracts one; when the count reaches zero the task frees its single allocation. It is the Arc idea from Part 3, done by hand in one atomic word, because a task must be simultaneously queued, awaited, and referenced by wakers without any of those freeing it early.

The remaining header fields are a back-pointer to the queue machinery that owns the task (so a waker knows where to file the wake) and the cached waker the task’s future will be polled with. Between the back-pointer and the schedule function, a task always knows how to get itself back onto some run queue from anywhere in the process.

The JoinHandle

spawn returns a JoinHandle<T>, where T is your future’s output. It is a future itself, and awaiting it works the way every await works: if the task is not done yet, the awaiting code registers a waker in the task’s join slot (that is what JOIN_WAKER marks) and goes idle. When the task finishes, that waker fires, the awaiting code resumes, and the output moves out through the handle.

Panics do not kill workers. A panic inside a task unwinds only as far as the task boundary, where the runtime catches it, records it, and delivers it as an error value to whoever awaits the handle. That is the expect in the example above: a task that panicked resolves to an error rather than a value, and the worker that was polling it moves on to the next task, unharmed.

Now the part that surprises everyone: dropping the handle does not stop the task. There is no stop signal, no kill switch, nothing to press. The handle is a receipt, not a leash. Drop it, and the task simply keeps running; it has shed one reference (and cleared JOIN_INTEREST), nothing more. This is called detaching, and it is occasionally exactly what you want:

#[tokio::main]
async fn main() {
    // no handle is kept: nobody will ever await this task
    tokio::spawn(async {
        loop {
            tokio::time::sleep(std::time::Duration::from_secs(5)).await;
            export_metrics().await;
        }
    });

    serve_requests().await;
}

What actually happens to a future that stops being polled, on purpose or by accident, is a whole topic of its own; page nine is devoted to it. The one-line version: in this runtime, stopping means dropping, and dropping runs destructors.

The lifecycle

Put the bits together and a task’s life is a small state machine:

A freshly spawned future enters as scheduled: bits set, reference count three, pointer filed into a queue. A worker claims it, which means winning the race to flip RUNNING. The poll happens. If it returns Pending, the task goes idle, and its own future is responsible for having parked a waker somewhere (a socket, a timer, a lock) before that poll returned; that is the future’s contract from Part 3. When the waker fires, the task is re-scheduled and the cycle continues. If the poll returns Ready, the future is dropped, the output is set aside, COMPLETE goes up, and the join waker, if any, fires.

There is one more arrow: a running task can go back to scheduled without being idle first, voluntarily, by yielding. Why a well-behaved task would do that, and what the runtime does to the ones that refuse, is the very first subject of the next page.

Task is not thread

The comparison you should keep in your body:

threadtask
stack megabytes reserved, kernel-managed none: a state machine on the heap
switching a kernel context switch (Part 1 measured those) a function returning, plus a queue hop
creation a syscall and a stack allocation one heap allocation and a queue push
who decides when it runs the kernel, preemptively the runtime, at suspension points
sleeping mid-work allowed; that is what threads are for forbidden; such work is exiled to the pool (page four)

A thread costs megabytes of reserved stack plus a kernel object, which is why ten thousand of them hurt. A task costs one allocation: a header measured in machine words plus your future. For a typical future the whole package lands in the low hundreds of bytes. A busy service holds hundreds of thousands of them without noticing, because nothing about a task touches the kernel until it actually needs the kernel. Spawn is not “make a thread.” Spawn is “make one allocation and push a pointer onto a queue,” and the next page is about that queue.

In this chapter

  • tokio::spawn wraps your future in a task: one heap allocation holding a header, a schedule function pointer, and the future inline behind them.
  • The header’s state word packs lifecycle bits plus a reference count; a new task starts at count three, and lossless waking is enforced by NOTIFIED itself.
  • A JoinHandle is a receipt, not a leash: awaiting it collects the output (or the panic), and dropping it merely detaches the task.
  • The lifecycle is idle → scheduled → running → idle or done, with every arrow an atomic bit operation.
  • A task is one allocation of a few hundred bytes, not a thread with megabytes of stack; that gap is the entire economics of async Rust.
