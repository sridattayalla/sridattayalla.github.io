The blocking pool

Everything in this part so far serves one law: a worker must never sleep inside the kernel. The scheduler page showed workers parking when idle, and that is fine, even healthy. The difference between parking and blocking is who holds the leash. A parked worker is idle by choice, asleep in epoll with the runtime able to shake it awake the instant work arrives (the same park and wake pair you built in Part 3, at runtime scale). A blocked worker is asleep inside a syscall: read on a slow disk, a DNS lookup, a std mutex held by someone else. The kernel holds that leash, and all the runtime can do is wait for the syscall to return.

One blocked worker is one fewer lane for every task in the machine. Every worker blocked is the nightmare: the queues stop draining, the drivers have nobody to wake, timers stop firing, and the whole runtime is frozen while every thread sits politely in the kernel. Part 1 showed what parked threads cost; here they cost the same and buy nothing.

What counts as blocking

The usual suspects: file I/O on ordinary files, DNS resolution, database clients built on synchronous APIs, foreign functions that sleep, locks from std::sync held across a slow path. Each one sends the calling thread into the kernel for an unbounded nap, and none of them knows what a future is.

Heavy computation is a different crime with a different sentence. A CPU loop never sleeps, so it does not lose the thread to the kernel; it just refuses to yield, and the cooperative budget eventually forces it to the back of the queue. The budget can save you from compute. Nothing in this runtime can save a worker from a syscall that sleeps; the thread is simply gone until the kernel gives it back. That is why blocking gets its own pool of threads to be wrong in.

This is the single most common way to hurt a Tokio service, and it looks so innocent:

async fn bad() {
    // the worker disappears into the kernel for the full second
    std::thread::sleep(std::time::Duration::from_secs(1));
}

Every task queued behind bad on that worker now waits a second, and every timer due in that second fires late. Part 5’s pitfalls page starts with this exact mistake.

spawn_blocking

The clean tool is spawn_blocking: hand the blocking closure to the blocking pool, a separate set of plain OS threads whose entire job is to be allowed to sleep in the kernel:

#[tokio::main]
async fn main() -> std::io::Result<()> {
    let contents = tokio::task::spawn_blocking(|| {
        std::fs::read_to_string("Cargo.toml") // sleeps in the kernel
    })
    .await // our worker stays free while a pool thread reads
    .expect("the closure panicked")?;

    println!("{} bytes", contents.len());
    Ok(())
}

Mechanically: the closure is queued; an idle pool thread picks it up, or a fresh one is spawned if the cap allows; you get a JoinHandle back, and awaiting it parks your task, not your thread, until the result arrives. Each pool thread runs one blocking call at a time: a thread stuck in read cannot also take the next job, which is why the pool grows rather than queues when work piles up.

The pool’s numbers, from the source. Pool threads are not pre-created; they are spawned on demand, up to a default cap of 512 threads, and an idle one exits after 10 seconds with nothing to do. Both are builder knobs (max_blocking_threads, thread_keep_alive). The true ceiling is slightly higher than the knob suggests, because the conversion trick below borrows threads outside the count: the cap works out to the blocking maximum plus the worker count. And the submission queue has no brake of its own: submit blocking work faster than the pool can drain it and the queue simply grows. If you expect bursts of blocking calls, bound them yourself.

Two sharp edges to keep in mind. A blocking closure cannot be stopped once it has started: there is no suspension point inside read for the runtime to leverage, no polite place to intervene, so the runtime does not try. Related: at shutdown, the runtime waits for blocking calls that have already started, which is why a timed shutdown variant exists for programs that cannot afford to wait. Design your blocking calls to be short, or to be cancellable by their own logic (check a flag, poll a pipe), because nobody can do it for you.

block_in_place

The second tool is rarer and stranger. block_in_place does not send work to the pool; it converts the worker you are standing on into blocking duty. Before running your closure, the worker hands its entire core, the run queue, the LIFO slot, all the bookkeeping from the scheduler page, to a freshly spawned OS thread, and that thread carries on scheduling while the original thread blocks:

#[tokio::main]
async fn main() {
    let digest = tokio::task::block_in_place(|| {
        hash_the_entire_file() // seconds of plain CPU, no awaits inside
    });

    println!("digest: {digest}");
}

The fine print matters. This only works on the multi-thread runtime; on the current-thread flavor it panics, because there is no sibling machinery to inherit the queues. Before handing off, the worker moves its LIFO-slot task into the run queue so that task stays stealable while its former owner is stuck. And anything else running concurrently inside the same task, a sibling branch you are awaiting alongside, is suspended for the whole duration: the task’s poll simply does not return until your closure does.

When would you reach for this? Almost never by choice. It exists for the cases where reorganizing the code is harder than the hack: you are deep inside an interface that insists on being synchronous, on a worker, with no way to move the work to the pool without tearing apart a trait or a callback contract. For new code, spawn_blocking is the honest tool: it says what it does (run this elsewhere and await the result) where block_in_place says something stranger (borrow this thread’s identity and make the machine work around me).

Why not just add workers

The tempting alternative: run a hundred workers and let thirty of them block. It fails on arithmetic you already know. Workers are generalists: each one polls tasks, drains queues, and takes its turn at the drivers, and the default count matches the CPU core count because more workers than cores just context-switch and churn the cache without adding capacity. A worker sitting in a blocking read is the most expensive thread in the process doing the least work: it carries a run queue nobody is draining.

A pool thread is the opposite trade. It is a specialist with no queue, no wakers, no fairness duties: born on demand, parked in the kernel for seconds at a time, retired after 10 idle seconds. It is a thread pool from Part 2 in its plainest form, and that plainness is the compliment. The split keeps each population shaped for its workload: a few smart lanes for millions of tiny tasks, a dumb and patient army for a few long sleeps.

Choosing, in one breath

  • There is an await-ready API for it (sockets, timers, async libraries)? Use it; that is what the drivers are for.
  • It must block (files, DNS, a synchronous client, a long CPU loop)? spawn_blocking, and await the handle.
  • You are on a worker, cannot restructure, and the call is unavoidable? block_in_place, with its fine print read.
  • You are about to hold a std lock or sleep a thread inside async code? Stop; that is the crime this whole page polices.

In this chapter

  • Parking is runtime-controlled idling; blocking is a kernel-controlled nap. Workers may do the first and must never do the second.
  • spawn_blocking exiles blocking closures to a separate pool of plain OS threads: 512 by default, spawned on demand, retired after 10 idle seconds, one blocking call each.
  • A blocking closure cannot be stopped once started, and runtime shutdown waits for started ones; keep them short or make them check a flag.
  • block_in_place hands the worker’s whole core to a fresh OS thread and runs the closure in place; multi-thread runtime only, and sibling awaits in the same task stall until it returns.
  • The pool is deliberately dumb, the plainest thread pool from Part 2, because dumb is exactly right for work whose only requirement is a thread that is allowed to sleep.
