TcpStream, end to end

This is the page the whole book has been walking toward. Here is one ordinary line of Tokio code:

use tokio::io::AsyncReadExt;

let mut buf = [0u8; 4096];
let n = stream.read(&mut buf).await?;
//     everything between `read` and this comment is this page

By the end of this page you will know what that single .await did: every structure it touched, every waker it parked, every queue it landed in, and the exact moment the kernel decided it was time to come back. Nothing new gets introduced. The task is a pinned state machine, the poll protocol and the waker are Part 3, the scheduler and the I/O driver were the last few pages. This page just runs them, all at once, in order.

The traits: AsyncRead and AsyncWrite

Two traits define what “async byte stream” means in Tokio. AsyncRead is the trait for sources you can read bytes from without blocking a thread; AsyncWrite is its sibling for sinks you can write to. TcpStream implements both. Here is the read half, which is the one we will trace:

pub trait AsyncRead {
    fn poll_read(
        self: Pin<&mut Self>,
        cx: &mut Context<'_>,
        buf: &mut ReadBuf<'_>,
    ) -> Poll<io::Result<()>>;
}

pub trait AsyncWrite {
    fn poll_write(self: Pin<&mut Self>, cx: &mut Context<'_>,
                  buf: &[u8]) -> Poll<io::Result<usize>>;
    // poll_flush and poll_shutdown have the same shape
}

Compare that with std's Read and the difference is the whole book: there is no way to block, only to say Pending. The socket underneath is non-blocking, so a read on an empty socket returns an error immediately: the kernel's EAGAIN, which Rust surfaces as ErrorKind::WouldBlock. The poll protocol turns that “not yet” into an arranged callback.

The scene

Set the stage precisely, because every detail will matter:

  • The connection is fresh. The socket's receive queue is empty, and this read future has never been polled.
  • The socket was registered with the driver on first use, so a ScheduledIo exists for it: readiness word zeroed, waiter list empty.
  • Your task is running on worker 2. It owns a slice of the scheduler's budget and is executing the state machine that async built around your function.

Hop 1: the poll lands

Your function hits .await. The generated state machine calls poll on the read future, which calls poll_read on the socket wrapper. Riding along in the Context is the waker for your task: the scheduler's business card, the one thing that can get this task queued again.

Hop 2: the try

poll_read does the honest thing first: it attempts the read syscall right now. The socket is non-blocking, so this costs nothing but the trip. The kernel looks at the empty receive queue and refuses: EAGAIN, wrapped by the wrapper as WouldBlock. No harm done. This was the readiness question from Part 1, asked for real.

Hop 3: the registration

Not ready, so the wrapper registers to be told. It links a new waiter into the ScheduledIo's waiter list, holding two things: your task's waker, and read interest. The push onto that list is the entire “arrange a wakeup” clause of the Future contract, now concrete.

Hop 4: Pending, and the task steps aside

poll_read returns Pending. The read future returns Pending. Your state machine stores where it was, returns Pending upward, and the task yields the worker. Worker 2 immediately moves to the next task in its local queue. From the runtime's point of view, your task has vanished from all queues and exists only as a parked state machine plus one waker sitting on a bench inside the ScheduledIo.

Hop 5: the packet

Kernel time. Some milliseconds later, a TCP segment arrives: the network card interrupts, the kernel runs, and the bytes land in the socket's receive queue. The socket transitions to readable. epoll, which has held this socket since registration, adds it to the ready list, once, edge-triggered.

Hop 6: the wake

Meanwhile some worker, say worker 0, had empty queues and was parked inside the driver in epoll_wait. The packet wakes it. The driver gets (token, readable), finds the ScheduledIo by token, merges the readiness bits into the readiness word, and walks the waiter list. One waiter is registered, its interest is read, and read overlaps readable. Its waker fires.

Hop 7: the scheduling

The waker flags your task ready to run and queues it. Worker 0, now awake and holding a fresh driver result, loops back around looking for work, checks its own queues, and quite possibly picks up the very task it just woke. The handoff from “I/O happened” to “scheduler's problem” happened inside waker.wake(), and it was just a queue push plus some atomics.

Hop 8 and 9: the re-poll, and Ready

A worker polls your task. The state machine resumes exactly where it stopped, at the same await, and calls poll_read again. This time the readiness word says readable. The wrapper clears the read-readiness bits, guarded by the driver tick so a fresher event cannot be lost, and retries the syscall. The kernel copies the queued bytes into buf, up to buf's capacity, and reports how many. poll_read returns Ready, the await resolves, and your next line runs with n real bytes and a task that never left user space while it waited.

The whole flight on one card

Two readers, one socket

What if two tasks read the same socket? Nothing in the machinery prevents it, and the structures handle it gracefully. Each poll that finds no readiness links its own waiter, waker and interest, onto the same ScheduledIo. When readiness lands, the wake pass touches every waiter whose interest overlaps, so both tasks get queued. They race. The winner's syscall drains the bytes and clears the readiness; the loser resumes, finds the readiness word empty again, links a fresh waiter, and returns Pending for another round. The waiter list is a queue of second chances, and it is also why one wake can usefully schedule several tasks.

The write side, briefly

Every step above has a mirror for AsyncWrite. A write on a socket whose send buffer is full returns WouldBlock; poll_write links a waiter with write interest; when the kernel drains the send buffer, epoll reports writable, and the same token-to-waker-to-queue flight delivers the task back to retry the send. Reads wait for the outside world to give; writes wait for it to make room. Same bench, same bell.

Now scale the picture in your head. Ten thousand connections each sitting in the middle of this exact trace means ten thousand parked state machines, ten thousand wakers on benches inside ten thousand ScheduledIo records, and a small pile of workers cycling through the loop you just followed worker 2 and worker 0 through. No thread ever entered the kernel to wait for a socket. The arithmetic that sank the thread-per-connection servers of Part 1 never gets a chance to start, because the thing that would have been parked, a whole stack-munching thread, was replaced by one queued waker. That substitution is the entire payoff of the book, and you have now traced it happening one hop at a time.

This was the machine's-eye view: structures, wakers, queues. The same read wearing user clothes, inside a complete echo server with an accept loop and one task per connection, is the second page of Part 5. Read this page for the machinery, that one for the program.

One thread of inquiry remains. We said the parked worker's nap is capped by the nearest deadline, and that timers exist. Where do deadlines live, and how does a runtime with a million armed sleeps avoid checking a million of them? The answer is the wheel behind every sleep, on the next page.

In this chapter

  • AsyncRead and AsyncWrite are the poll protocol applied to byte streams: no blocking, only Pending with a stashed waker.
  • A first poll_read tries the syscall, eats the WouldBlock, then parks a waiter (waker plus read interest) in the socket's ScheduledIo.
  • When the packet arrives, the driver merges readiness bits and wakes every overlapping waiter; the waker is a scheduler handle, so waking is a queue push.
  • The re-poll clears readiness under the tick guard, retries the syscall once, and returns Ready(n).
  • Concurrent readers queue on the same waiter list; losers re-register and sleep again. Writes run the same flight mirrored.
