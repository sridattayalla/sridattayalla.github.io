The I/O driver

Everything so far in this part has been supply side: how a task is allocated, how the scheduler stores it, steals it, and polls it. Now the demand side. A task parked in the middle of an .await is worthless unless something, somewhere, notices that the outside world changed and puts that task back where a worker can reach it. That something is the I/O driver: the part of the runtime that owns the single polling relationship with the kernel, and whose entire job is converting “this socket became ready” into “that task should run again.”

You met the driver as a box on the runtime map. This page opens the box. The good news is that you have already seen every idea inside it. epoll is Part 1 material, wakers are Part 3, and the run queues it feeds were the subject of the scheduler page. The driver is the knot where those three threads are tied together.

One poller, wrapped once

Recall the shape of epoll: one thread registers interest in thousands of sockets once, then calls epoll_wait and sleeps until the kernel reports that at least one of them is ready. It is the multiplexing trick that lets a handful of threads serve a huge number of connections, and it runs on the kernel's notion of readiness rather than on blocking waits.

Tokio does not call epoll directly. Between the runtime and the operating system sits mio, a small crate that wraps the OS polling facility behind one portable API. On Linux mio uses epoll; on macOS and the BSDs it uses kqueue; on Windows it uses IOCP; on Solaris and illumos, event ports. Tokio inherits whichever backend mio picks, so on Unix the driver is a readiness poller through and through. (The completion-based alternative, io_uring, exists in Tokio but as an unstable, opt-in, Linux-only path; the default remains the readiness model.)

The driver itself is deliberately small: one mio::Poll instance created when the runtime boots, one reusable buffer that epoll_wait fills with events, and one reserved wakeup token so the rest of the runtime can interrupt a parked poll without going through a socket. In mio terms, everything the driver does for one socket reduces to a registration like this: 

// What tokio does once per source, written in raw mio:
let mut poll = mio::Poll::new()?;            // one per runtime
let registry = poll.registry().clone();

poll.registry().register(
    &mut socket,                                 // the OS handle
    mio::Token(fd_as_usize),                   // the lookup key
    mio::Interest::READABLE | mio::Interest::WRITABLE, // what to report
)?;

Interest and tokens

Two small registered values do all the work, and both ride along with every event the driver later reports.

Interest is the set of events a source currently cares about: readable, writable, or both. A socket that wants to read registers read interest. A socket whose send buffer is full registers write interest, so it learns the moment the kernel drains it. A freshly registered source can ask for both at once and narrow later. Interest is not a promise to act; it is a request to be told.

A token is the return address. When you register a source with mio, you attach a token, an ordinary integer, and mio hands that same integer back attached to every event for that source. The token is how the driver gets from “something is ready” back to “this exact socket, this exact bookkeeping.” Tokio derives each token from the source's raw descriptor or pointer, so the driver can jump straight to the right record with no translation table in between.

Registration is lazy. Creating a TcpStream touches nothing. The registration happens on first use, when the socket is first polled: at that moment the runtime allocates one ScheduledIo record for the source out of a slab and registers the source with mio under its token.

ScheduledIo: a readiness word and a bench of wakers

The ScheduledIo is the per-source half of the driver, and it is exactly two things.

First, a readiness word: one atomic integer packed as [shutdown (1 bit) | driver tick (15 bits) | readiness (16 bits)]. The readiness field is a bitset of everything the driver has reported for this source: readable, writable, closed, and friends. Asking “may I read now?” is a load and a mask. No syscall is involved.

Second, a waiter list: a queue of waiters, each holding one task's waker plus the interest that task is waiting for. This is the bench where sleeping tasks sit. When a poll finds no readiness for what it wants, the polling code links a waiter onto this list and returns Pending.

Look at what this buys. The Future contract from Part 3 says: if you return Pending, you must have arranged to be woken first. The entire mechanism of “arranging” is a push onto a linked list. Every async socket read you have ever written bottomed out in that one push.

The wake path

Here is the whole driver in motion: one socket, one sleeping task, from arriving bytes to a run queue.

  1. Bytes arrive. The network card raises an interrupt, the kernel runs, and the bytes land in the socket's receive queue. The socket transitions to readable.
  2. epoll, which has held this socket in its interest list since first use, adds it to the ready list. In edge-triggered mode this happens once, at the transition.
  3. Some worker is sitting in epoll_wait. Which worker, and why it is there, is the last section of this page. The call returns a small pile of events: (token, readable).
  4. The driver takes the token, finds the ScheduledIo, and merges the reported events into the readiness word with an atomic OR.
  5. Then it wakes. The driver walks the waiter list, and every waiter whose registered interest overlaps the new readiness gets its waker fired.
  6. The waker is a scheduler handle in disguise. Firing it queues the task: local queue, LIFO slot, or inject queue, depending on who woke it and from where.
  7. A worker picks the task up and polls it. The future resumes exactly where it suspended, checks the readiness word it stashed a waker for, and this time it proceeds.

Edge-triggered, without the lost wakeups

Edge-triggered epoll is the efficient choice, but it has a famous failure mode: the event is reported once, at the transition. If a task clears its cached readiness, attempts the read, and finds nothing there, the kernel will not re-report anything. The task could sleep forever on a socket that is, in truth, ready.

Tokio's guard is small and exact, and it explains those fifteen tick bits in the readiness word. Every driver pass increments the tick and stamps it into the word. When a task clears readiness before trying a syscall, only the bits whose tick matches the current driver pass get cleared. A readiness event that lands after the clear carries a newer tick, survives the clear, and the next poll sees it. The classic edge-triggered lost wakeup cannot happen.

Who calls epoll_wait?

The tempting mental model is “the driver is a thread.” It is not, and believing it will mislead you. The driver is a data structure plus a function. Workers drive it.

When a worker has searched the LIFO slot, its local queue, the global queue, and its siblings' queues, and found nothing, it parks. But it does not park on a bare condition variable. It parks inside the driver, in epoll_wait. The same nap now serves two masters: any readiness event, on any of the runtime's thousands of sockets, wakes the worker with useful work already attached.

The nap is bounded. epoll_wait accepts a maximum wait, and the runtime fills it in from its clocks: the nearest pending deadline becomes the cap, so a sleeping worker doubles as an alarm that cannot oversleep. That deadline comes from the timer machinery, two pages ahead. If nothing is sleeping, nothing bounds the nap, and the worker rests until I/O happens or another worker wakes it.

What about a worker that never runs dry? It never parks, so on its own it would never poll the driver, and sleeping tasks would pile up behind a busy runtime. To prevent that, the scheduler folds driver turns into the ordinary worker loop: every so many scheduler ticks, a busy worker takes one driver pass between tasks. The default interval is 61 ticks.

That is the driver, complete: one poller, a slab of readiness words and waiter benches, and a wake path that ends in a run queue. Every piece is now on the table separately. The next page runs one actual read().await through all of it at once, hop by hop.

In this chapter

  • The I/O driver is mio over epoll (kqueue on macOS): one poller for the whole runtime, not a thread.
  • Registration is lazy: on first use, each source gets a ScheduledIo holding a packed readiness word and a waiter list of wakers.
  • Interest says what a source wants to be told about; the token is the return address that maps an epoll event back to its ScheduledIo.
  • The wake path is always the same: bytes, epoll, token, waker, run queue, poll.
  • Tick bits in the readiness word make edge-triggered epoll safe against lost wakeups, and parked workers double as the runtime's alarm clocks.
