Tokio's sync primitives

The last three chapters were about tasks waiting on the world: a socket, a clock. Most waiting in a real program is much closer to home. Task A cannot proceed until task B releases a lock, fills a queue, finishes a computation, or simply rings a bell. This chapter is about that waiting, and it begins with a rule you already know: never park a worker. Every primitive below is the same trick applied to a different shape of waiting: park the task, never the thread.

The wrong park

Reach for std::sync::Mutex inside async code and the trouble is not the mutex; it is what the mutex does on contention. lock() on a held lock blocks the calling OS thread. If the caller is a worker, you have just seized a scheduler asset: the worker's entire local queue of runnable tasks now sits behind one lock, and if the lock's current owner is itself waiting for a task stranded on that worker, you have a deadlock. The official guidance is blunt: do not hold a std mutex guard across an .await; use the async mutex or move the work to the blocking pool.

Park the task, not the thread

tokio::sync::Mutex makes one change to the contract, and it changes everything: lock() is async. On contention, the losing task does not block anybody. It links a node holding its waker into the lock's waiter queue and returns Pending. The worker immediately moves on to other work. When the guard is dropped, the lock hands the permit to the head of the queue, that task's waker fires, the scheduler queues it, and its next poll resumes holding the lock. Underneath, tokio's mutex is a thin wrapper over a semaphore with a fair, first-in-first-out permit queue. 

use tokio::sync::Mutex;

let lock = Mutex::new(ledger);

// the guard may cross .await points: the worker stays free
let mut guard = lock.lock().await;
let entry = fetch_row().await;   // awaiting while holding: legal
guard.push(entry);
drop(guard);                     // permit goes to the next waiter

Cost honesty, since the docs insist on it: the async mutex is more expensive than the std one. For a tiny critical section that never crosses an .await, std's mutex is the better tool. The async one earns its keep exactly when the guard must survive across suspension.

The semaphore

A semaphore is a counter of permits. acquire().await takes one if any exist, or parks the caller in the same fair, first-in-first-out waiter queue as the mutex; the guard returned by acquire puts the permit back on drop. Because the queue is fair, permits are handed out in the order tasks asked for them, which makes the semaphore predictable under contention in a way lock-free counters are not. The mutex, the bounded queue below, and half the ecosystem's rate limiters are all semaphores in costume: a connection limiter is a semaphore of size N, a mutex is a semaphore of size one.

use std::sync::Arc;
use tokio::sync::Semaphore;

let sem = Arc::new(Semaphore::new(3)); // three permits

let permit = sem.clone().acquire_owned().await?;
do_scoped_work().await;   // at most three tasks ever pass the gate
drop(permit);             // permit returns; the queue head wakes

Channels

A channel is a pipe for handing values between tasks: one side sends, the other receives, and both sides may legitimately have to wait. Waiting is where the chapter's rule bites, so every tokio channel parks tasks, never workers: a blocked sender or receiver is a waker on a bench, and the worker walks away to other work. Tokio ships five shapes, and choosing among them is mostly answering two questions: how many producers and consumers must share the pipe, and must consumers see every value, or only the newest, or only the ones they can keep up with?

mpsc: the workhorse

mpsc means multi-producer, single-consumer, and it is the default pipe of async Rust. The bounded version has a capacity you choose, and its superpower is what happens when the buffer is full:

let (tx, mut rx) = tokio::sync::mpsc::channel(8);

tokio::spawn(async move {
    for i in 0..100 {
        // when 8 values sit unread, this await parks the producer:
        // its waker joins the queue's waiter list, worker stays free
        if tx.send(i).await.is_err() { break; } // receiver gone
    }
});

while let Some(i) = rx.recv().await {
    println!("got {i}");
}

That parking is backpressure, made mechanical. The producer cannot outrun the consumer by more than the buffer: every send past the eighth waits for a receive. No polling, no dropping of values, no explicit coordination; the producer's waker simply sits on a bench until the consumer makes room. Internally the queue is a linked list of blocks, each holding up to 32 values for the bounded flavor, and the capacity limit itself is policed by an internal semaphore.

The unbounded flavor removes the brake: send never parks, because the list of blocks grows as long as it must. That is a feature when bursts must be absorbed and a hazard when the producer is chronically faster than the consumer: memory grows with the backlog, and nothing in the pipe will tell you.

oneshot: the single shot

A oneshot channel carries exactly one value, once, from one sender to one receiver. The receiving side is itself a future. This is the shape of a reply that will eventually exist: spawn a task, hand it the sender, await the receiver.

let (tx, rx) = tokio::sync::oneshot::channel();

tokio::spawn(async move {
    let answer = expensive_lookup().await;
    tx.send(answer).ok(); // Err only if nobody waits anymore
});

match rx.await {
    Ok(answer) => println!("got {answer}"),
    Err(_sender_gone) => println!("the task died first"),
}

watch: the latest value

A watch channel keeps only the most recent value. It is not a queue: slow consumers do not fall behind, they just see the current state on the next changed(). Configuration, leadership state, shutdown flags: anything where only the newest value matters. Internally it is built on Notify, the primitive at the bottom of this page. 

let (tx, rx) = tokio::sync::watch::channel("idle");

tokio::spawn(async move {
    let mut rx = rx;
    while rx.changed().await.is_ok() {
        println!("state is now {}", *rx.borrow());
    }
});

tx.send("busy").ok(); // replaces, never queues
tx.send("idle").ok(); // a slow reader sees only "idle"

broadcast: the megaphone

A broadcast channel is multi-producer and multi-consumer: every value sent is seen by every live receiver, each keeping its own cursor into a shared ring buffer. The ring has a fixed size, so a receiver that dawdles past it does not stall the sender; it learns how far behind it fell. 

use tokio::sync::broadcast;

let (tx, _) = broadcast::channel(16); // ring of 16 values
let mut fast = tx.subscribe();
let mut slow = tx.subscribe();

tx.send("event-1").ok();
tx.send("event-2").ok();

// fast.recv().await -> Ok("event-1"), then Ok("event-2")
// if 17 more sends happen before slow calls recv(),
// slow.recv().await -> Err(Lagged(1)): one value was overwritten

The failure mode to internalize: broadcast never slows the producer. Lag is the receiver's problem, reported as a count. That is the opposite trade from bounded mpsc, where the producer waits and nothing is ever lost.

Notify: the doorbell

Strip everything above to its skeleton and one primitive remains: Notify, a bare “ring the bell” and “wait for the bell.” Its whole state is a single stored permit plus a queue of waiters.

notify_one() either stores one permit, if none is stored, or wakes one waiting task. Storing rather than dropping is what makes it safe to ring before anyone listens: the next notified().await consumes the stored permit and returns immediately. notify_waiters() wakes every current waiter and stores nothing, for broadcast-style shutdowns. And one quirk to burn in: repeated notify_one() calls coalesce into a single permit. Notify is a doorbell, not a counter; if you need counting, you wanted the semaphore. 

use std::sync::Arc;
use tokio::sync::Notify;

let notify = Arc::new(Notify::new());
let bell = notify.clone();

tokio::spawn(async move {
    prep_work().await;
    bell.notify_one(); // permit stored even if nobody waits yet
});

notify.notified().await; // consumes the permit, then continues

Look back over the chapter and the family resemblance is total. The mutex's queue, the semaphore's waiters, the bounded channel's parked senders, watch's change signal: each is a list of wakers plus a policy for who gets woken when, and the policy is the only thing that differs. Once you have seen the pattern, no primitive in this toolbox can surprise you. What can still surprise you is what happens to a task that never gets woken at all, because someone dropped the future it was living in while it waited. Dropping a future has consequences, and sorting the safe ones from the dangerous ones is the last page of this part.

In this chapter

  • std locks park the worker thread; tokio's park the task: a waker joins a waiter queue and the worker moves on.
  • The async mutex is a semaphore wrapper with a fair, first-in-first-out queue; use it only when the guard must cross an .await.
  • Bounded mpsc turns a full buffer into a parked sender: backpressure for free. Unbounded has no brake; broadcast never slows the sender and reports receiver lag instead.
  • oneshot moves one value once; watch keeps only the latest value and is built on Notify.
  • Notify is the bare doorbell underneath: one stored permit, coalescing rings, waiters woken one or all.
