Cancellation and select!

Every runtime chapter so far has been about tasks that run to the end. This one is about the ones that do not. Async Rust's signature superpower is that a task can be stopped mid-flight, at an await, with no kill signal, no unwind, and no ceremony. That power is also its sharpest edge, and most of the folklore around “async is hard” traces back to not knowing exactly what stopping a task does. This page makes it precise.

Drop is cancel

To cancel a future is to stop polling it forever and destroy it. That is the entire mechanism. There is no interrupt: the runtime never reaches into a running future. There is no unwind: no stack frames roll back, because a suspended future has no stack, only a state machine and its fields. What does run is drop: each field of the state machine is destroyed in order, buffers freed, guards released, and that is the cleanup ceremony, complete.

Where can it happen? Only between polls, which in your source means at .await points, the yield points from Part 2. A future that is executing inside poll finishes that poll; cooperative scheduling means nobody preempts it. A future parked at an await is exactly as killable as a future that has not started, because in both cases the only thing that exists is a value, and values can be dropped.

Three roads lead there. First, explicit abort: a task's state word has a dedicated bit meaning “this task should be dropped”, set by JoinHandle::abort() and honored the next time the task is between polls. Note the neighbor fact: dropping a JoinHandle does the opposite, detaching the task to run on. Second, scope exit: a wrapper future that gives up drops whatever inner future it was holding. Third, and most frequent by far: select!, dropping the branches that lost a race. That one gets a whole section below.

Two footnotes for honesty. A late wake aimed at an already-dropped task is wasted work, never corruption: the task header is reference-counted precisely so that wakers can outlive the future without touching freed memory. And work handed to spawn_blocking cannot be aborted at all once it has started; runtime shutdown waits for started blocking tasks, which is why shutdown_timeout exists.

Cancellation safety

Cancellation safety is the property you have to reason about: a future is cancellation-safe if dropping it at any of its await points leaves the system in a state you can defend. The runtime side is always safe. The logical side is where things break, in three characteristic ways:

  • Work consumed and lost. Bytes that a read future pulled from the socket into its own local buffer, then died before handing them up, are gone from the stream forever. The kernel does not un-read them.
  • Side effects half-done. The request reached the server and the future died before the response arrived. A blind retry duplicates the work, or worse, duplicates a purchase.
  • State lost. Counters, parsed prefixes, position in a protocol: anything the dropped future was tracking evaporates with it.

The rules of thumb fall out directly. Do side effects after the final await of an operation, not before an intermediate one. Keep resumable state outside any future that might be dropped, in an owner that survives. Treat every await inside a raced branch as a possible death point, because it is one. And when a fragment of work must either finish or not run at all, give it a task of its own: a spawned task is only stopped by an explicit abort, never by a losing branch.

Broken: a dropped half-message

The classic wound. Length-prefixed messages over one TCP stream, two awaits per message:

use tokio::io::AsyncReadExt;
use tokio::net::TcpStream;

// BROKEN under a racing select: two awaits, one logical unit
async fn next_message(socket: &mut TcpStream) -> Option<String> {
    let mut header = [0u8; 4];
    socket.read_exact(&mut header).await.ok()?;
    let len = u32::from_be_bytes(header) as usize;
    let mut body = vec![0u8; len];
    socket.read_exact(&mut body).await.ok()?;
    String::from_utf8(body).ok()
}

Call this from inside a race, say against a shutdown signal. The race drops the loser between the two read_exacts. The header's four bytes have been consumed from the socket, but the body has not, and the local header array, which held the only record of that fact, just died. The next call to next_message reads the first four body bytes as a length. The protocol is now silently corrupt, and nothing will error until a length comes out absurd.

Fixed: own the state across drops

Move the whole read loop into a task that nobody drops mid-message, and race only against complete messages arriving over a channel:

let (tx, mut rx) = tokio::sync::mpsc::channel(32);

tokio::spawn(async move {
    let mut socket = socket;
    loop {
        match next_message(&mut socket).await {
            Some(msg) => { tx.send(msg).await.ok(); }
            None => break, // stream closed: exit cleanly
        }
    }
});

loop {
    tokio::select! {
        Some(msg) = rx.recv() => handle(msg), // whole messages only
        _ = shutdown.recv() => break,         // reader keeps its state
    }
}

The repair is structural, not tactical. The droppable future now holds no protocol state: the risky sequence runs inside a task that survives branch races, and the race only ever chooses between finished work and a shutdown. That is the shape of most cancellation-safety fixes: move resumable state out of the future that might die, into an owner that will not.

select!

Now the macro itself, since it was named as the main culprit. select! races futures: it takes one future per branch, polls them together, and runs the handler of whichever branch is ready first.

tokio::select! {
    msg = rx.recv() => handle(msg),
    _ = shutdown.recv() => {
        // whichever future lost this race is dropped, right here
    }
}

The mechanics deserve exact wording. For each branch, select! owns a future. On each poll of the whole select! expression, it polls the branch futures; the moment one returns Ready, its handler runs and every other branch future is dropped where it stands, mid-await. First ready wins; the losers are cancelled. This is why the previous section exists: each branch of a select is a drop point for whatever future you wrote in it.

Two details of fairness and bias. By default, the order in which branches are polled is randomized each time, so no branch systematically wins when several are ready at once; that protects you from accidental starvation. Writing biased; as the first thing inside the macro switches to polling branches top-down, in written order: deterministic and slightly cheaper, but now a busy top branch can starve everything below it, so the order you write becomes a priority list you must defend.

And the shape you will actually write most: a loop. Each iteration re-creates the branch futures from their expressions, which is why branches are written as calls like rx.recv() rather than named futures: recv() builds a fresh one-shot attempt per iteration. Every re-creation is also a fresh cancellation hazard, which is why the cancel-safety rules above live closest to this macro.

loop {
    tokio::select! {
        Some(msg) = rx.recv() => handle(msg),
        _ = shutdown.recv() => break,
    }
}

A time limit is a select

The most raced-against future in existence is a sleep, so finish with the two standard shapes of giving up. The timeout wrapper is a select against a relative timer: it arms a fresh limit at the moment you call it, races your future against the clock, and drops the loser.

use std::time::Duration;
use tokio::time::timeout;

// Shape 1: relative. A fresh timer starts now; losing the race
// means work()'s future is dropped where it stood.
match timeout(Duration::from_secs(1), work()).await {
    Ok(result) => handle(result),
    Err(_too_slow) => retry_or_give_up(),
}

Every call re-arms. That is right for “each attempt gets one second” and subtly wrong for “the whole job ends at noon”, because a loop of relative limits can drift forever if each attempt resets the clock. The second shape fixes it with one absolute deadline, reused across the whole loop:

use tokio::time::{sleep_until, Instant};

// Shape 2: absolute. One deadline for the entire loop;
// iterations cannot drift past it, because it never moves.
let deadline = Instant::now() + Duration::from_secs(60);
loop {
    tokio::select! {
        _ = sleep_until(deadline) => break, // the wheel fires once
        Some(job) = queue.recv() => run(job),
    }
}

The sleep in both shapes is a timing wheel entry armed through the time driver; the race mechanics are the select above; and the loser, again, is dropped. Relative when each attempt deserves its own budget, absolute when the batch has a wall to hit. The walking-tour versions of these combinators, with traced poll orders, are in Part 5.

In this chapter

  • To cancel is to never poll again and drop: no signal, no unwind, only Drop running on the future's fields, and only between polls, at await points.
  • Abort sets a task state bit honored at the next poll boundary; dropping a JoinHandle detaches instead, and started spawn_blocking work cannot be stopped at all.
  • Cancellation safety is a property of your logic: watch for consumed-and-lost work, half-done side effects, and lost state. Keep resumable state in an owner that survives.
  • select! polls branch futures together, the first Ready wins, and every losing branch future is dropped mid-await. Random polling by default, biased; for written order.
  • A time limit is a select against a sleep: relative limits re-arm per call, absolute deadlines hold a wall for the whole loop.
