Pitfalls

Almost every async Rust bug you will meet is one of two shapes: code that blocks a thread that is never allowed to block, or code that drops a future that was not finished. The five classics below are all variations on those two themes. Each one gets the same treatment: the wrong code, the trace through the machinery you now understand, and the fix, which is almost always to move the work to the layer that was built for it.

A blocking sleep in async clothing

Wrong first. This retry loop looks innocent and parks a worker:

async fn health_check(db: &Db) -> bool {
    for _ in 0..3 {
        if db.ping().await.is_ok() {
            return true;
        }
        std::thread::sleep(std::time::Duration::from_millis(500));
    }
    false
}

Trace it. The task is mid-poll when it reaches the sleep, so the thread that sleeps is the worker's own OS thread, the one that is supposed to be polling every other task in its queues. For half a second, that worker is gone: its run queues back up, its budget accounting is useless because the budget counts polls and there are none, and the scheduler has no idea anything is wrong. On a runtime with one worker, or in the main future under block_on, the entire program freezes. Nothing crashed; everything is just waiting for a thread that is asleep in the kernel.

The fix depends on what the sleep was for. Waiting for time to pass is the time driver's job: tokio::time::sleep arms a wheel entry, returns Pending, parks the task, and the worker moves on to someone else's work. Genuinely blocking work, a database driver stuck in a C library, a std::fs call, a lock you cannot scope, belongs on the blocking pool via spawn_blocking, where parking a thread is the entire point. The rule is one sentence: nothing inside a poll may stop the thread it runs on.

A guard held across the await

Wrong again, and this one fails two different ways depending on where the future runs:

async fn refresh_if_missing(cache: &Cache, key: String) {
    let guard = cache.map.lock().unwrap();
    if guard.contains_key(&key) {
        return;
    }
    let value = read_from_disk(&key).await;
    guard.insert(key, value);
}

The first failure is at compile time, and it is the kind one. The future holds a std::sync::MutexGuard across an await, so the future itself is not Send, and handing it to tokio::spawn is rejected on the spot, with an error message that names the guard. The compiler just stopped you from moving a lock between threads. The second failure happens when you dodge the spawn, say by polling this future directly, and a second task wants the same lock: your task holds the guard, parks at the disk read, the worker polls the other task, that task calls lock(), and a std mutex blocks the worker's thread on the spot. The disk read finishes and queues your task to be woken, but the thread that would wake it is blocked waiting for the very guard your task is holding. Deadlock, one worker gone, no error message anywhere.

The fix in most code is not the async mutex; it is scope. Hold the guard only for the synchronous part, drop it before awaiting, and take it again after:

async fn refresh_if_missing(cache: &Cache, key: String) {
    if cache.map.lock().unwrap().contains_key(&key) {
        return;
    }
    let value = read_from_disk(&key).await;
    cache.map.lock().unwrap().insert(key, value);
}

When a critical section genuinely must await while holding the lock, that is what tokio::sync::Mutex from the sync chapter is for: its lock().await parks the task instead of the thread. Treat it as the exception; most locked sections want to be short and synchronous, and scoping makes them so.

The channel without a brake

let (tx, mut rx) = tokio::sync::mpsc::unbounded_channel();

tokio::spawn(async move {
    while let Some(tick) = feed.next().await {
        tx.send(tick).expect("consumer gone");
    }
});

// elsewhere: a batch writer drains rx between disk flushes

The trace is a slow-motion one. unbounded_channel exists to make send synchronous: the value goes into a queue that grows on demand, the call returns immediately, and nobody parks, ever. That is exactly what you want for a few log lines, and exactly wrong for a hot producer feeding a slow consumer. The feed is faster than the disk, so the queue grows, and grows, and every item you are buffering is memory held plus latency added, with no signal reaching the producer to slow down. The program does not deadlock and does not error; it just quietly converts a fast input stream into an ever-larger heap while the consumer falls further behind. The backpressure demonstration from the pipeline page showed the healthy version of this exchange; the unbounded channel is that demo with the brake sawn off.

The fix is the bounded channel: mpsc::channel with a small capacity, and send(...).await so the full buffer parks the producer at the lip. Pick the capacity for how much burst you want to absorb, not for how much data you hope never arrives; a bounded channel that is always full is doing its job, keeping memory flat and the producer honest.

Fire, forget, and never hear

tokio::spawn(handle_request(socket));

One line, no binding, and the JoinHandle drops on the spot. The task is now detached: it runs for as long as it likes, and nothing in your program will ever know how it ended. Trace the failure modes. If the task panics, the panic is caught at the task boundary and packaged as a JoinError, which is then dropped along with the handle you never kept; a supervisor that swallowed every exception would be called broken, and this is that supervisor. If your program exits while the task is mid-await, the runtime stops it at its next yield point, which for a protocol handler means half a response written and the socket dropped mid-conversation. And if the task is stuck in an infinite loop you forgot about, nothing will ever collect it.

Sometimes fire-and-forget is correct: metrics ticks, log flushes, work that truly has no failure your program could act on. Make those deliberate. For everything else, own the outcome: keep the handle and await it at the closing bracket, or, better, spawn into a JoinSet and drain it with join_next, so panics surface where you can log them and shutdown waits for stragglers instead of cutting them. The pipeline page showed the whole ceremony; it is four lines, and it converts invisible failures into ordinary Results.

Racing a write that must not lose

The last one is the most subtle, because every line looks right and the program mostly works. A connection loop that wants to honor shutdown races its socket write against a shutdown signal:

loop {
    // ... assemble frame from upstream work ...
    tokio::select! {
        _ = socket.write_all(&frame) => {}
        _ = shutdown_rx.changed() => break,
    }
}

Here is the trace. write_all is documented as not cancellation-safe: it loops internally until the whole buffer is out, and nothing outside can see how far it got. Suppose the socket's send buffer fills partway through the frame, the write parks, and shutdown fires: select! drops the write future mid-flight. The first half of the frame is already on the wire; the second half never will be. The loop breaks, the connection closes politely, and the peer is left holding a truncated frame, which it will usually parse as garbage or, worse, glue onto the front of whatever comes next. No function returned an error. The corruption is silent and rare, which is why this bug shape survives testing.

The fix is to move the race to the right granularity: race for work, never inside a unit of work. Select on “next frame from upstream, or shutdown”, and do the write, uninterrupted, in the branch:

loop {
    let frame = tokio::select! {
        frame = frames_rx.recv() => match frame {
            Some(f) => f,
            None => break,
        },
        _ = shutdown_rx.changed() => break,
    };
    socket.write_all(&frame).await?;
}

Shutdown now lands between frames, never inside one. When the writer must stay responsive while a large write drains, give the write its own task fed by a channel and close the channel to shut it down, the close-by-ownership pattern; or use the library's write_all_buf variant, which advances its buffer as it writes so a cancelled attempt resumes where it stopped instead of restarting from the top. All three fixes share one idea: cancellation is only safe at points you chose, and the cancellation chapter's question, “what happens if this await is dropped right now?”, is worth asking at every select branch you write.

In this chapter

  • Nothing inside a poll may stop its thread: std::thread::sleep and blocking locks park the worker; use tokio::time::sleep or the blocking pool.
  • A std mutex guard held across an await is a compile error under spawn and a deadlock elsewhere; scope the guard, and reserve the async mutex for critical sections that truly await.
  • Unbounded channels remove backpressure; a bounded channel plus send().await keeps memory flat and producers honest for free.
  • A dropped JoinHandle detaches its task and silently discards its panic; await handles or drain a JoinSet so outcomes surface.
  • Race for work, never inside it: write_all dropped mid-write loses the tail of the frame, so select on “next message or shutdown” and write uninterrupted in the branch.
