A TCP echo server, await by await

Here is the oldest useful program in networking: whatever a client sends, send back. Thirty lines of Tokio, and inside them, every piece of machinery from Part 4 gets used at least once. This page walks the whole program from your chair: what each line does, what each .await enters, and what the runtime does behind it. One await, the socket read, already has its own page: Part 4 traced one read through the I/O driver hop by hop, down to the waker lists and the readiness bits. This page will point at that trace instead of repeating it. Read this page for the program, that one for the machinery.

The whole server

First the setup and the accept loop:

use tokio::io::{AsyncReadExt, AsyncWriteExt};
use tokio::net::{TcpListener, TcpStream};

#[tokio::main]
async fn main() -> std::io::Result<()> {
    let listener = TcpListener::bind("127.0.0.1:7878").await?;
    println!("echoing on {}", listener.local_addr()?);

    loop {
        let (socket, peer) = listener.accept().await?;
        tokio::spawn(async move {
            if let Err(e) = echo(socket).await {
                eprintln!("{peer}: connection error: {e}");
            }
        });
    }
}

Then the per-connection task, the entire protocol:

async fn echo(mut socket: TcpStream) -> std::io::Result<()> {
    let mut buf = vec![0u8; 4096];
    loop {
        let n = socket.read(&mut buf).await?;
        if n == 0 {
            return Ok(()); // the peer closed its end
        }
        socket.write_all(&buf[..n]).await?;
    }
}

That is the complete server. Bind once, accept forever, one task per connection, read until the stream closes, write back what arrived. The interesting part is not the code; it is what each of those five awaits walked into.

Every await, annotated

The awaitWhat it entersDetails
bind(...).await kernel socket setup, then the I/O driver The socket, bind, and listen syscalls run during the first poll. The fd is marked non-blocking and registered with the driver, which allocates its bookkeeping record. Then the future returns Ready. This await waits for nothing; it is where the kernel object is born.
accept().await the listener's waker bench Try accept now; the backlog is empty, so the kernel answers EAGAIN. Park a waker with read interest on the listener, return Pending. A connection arrives, epoll reports the listener readable, the waker fires, a worker re-polls, and accept hands back a fresh non-blocking socket, already registered.
tokio::spawn(...) the scheduler, via the inject queue Not an await, but it sits in the loop and deserves its row. The connection future is boxed into a task. Because the caller here is the main thread from the boot sequence, the task lands in the global inject queue for a worker to adopt. Inside a worker, the same call would use the LIFO slot instead.
read(...).await the full Part 4 flight Try the read, eat the WouldBlock, stash the waker, sleep as a parked state machine until a packet arrives, wake, retry, hand over the bytes. That is the page you already read, all twelve hops of it.
write_all(...).await the mirror flight Write what fits now. If the socket's send buffer is full, the kernel says WouldBlock, the task parks a waker with write interest, and the driver waits for the buffer to drain. write_all repeats until your whole buffer is out; each stall parks the task, never the worker.

Notice the shape of the answer every await gives: try the operation immediately, and only if the kernel says “not yet” does the task arrange a wakeup and step aside. That two-step, the readiness question before the data question, is the contract Part 1 spent a page establishing, and it is baked into every AsyncRead and AsyncWrite implementation in the ecosystem.

One connection, in slow motion

Trace a single client through the server's first minute. A telnet connects: the kernel completes the handshake, the listener becomes readable, and the parked accept wakes through the driver. The accept loop gets a socket and a peer address, spawns one echo task, and immediately parks again at the top of the loop. Somewhere nearby, a worker adopts that task from the inject queue and polls it for the first time.

The task's first poll runs straight through echo's setup, the buffer allocation included, and into read, which tries the socket, finds it empty, parks a waker, and returns Pending. The task has now executed perhaps a microsecond of real work and will sit dormant for as long as the user thinks. The worker, having spent that microsecond, is already polling somebody else. When the user finally types, the packet lands, epoll fires, the waker queues the task, a worker polls it, and the read hands over the line of text. The task flows into write_all, which usually completes immediately on a fresh socket, and loops back into read to park again. Ping, pong, park, over and over, each round costing one queue push and one poll, and the thread count never moving off the number it booted with.

When the client quits, the kernel marks the socket read-at-end-of-stream; the next read wakes, returns zero, and the task returns Ok, drops its socket, its buffer, and its state machine, and disappears from every queue without ceremony. The whole lifecycle of a connection, birth to death, moved four pieces of state: one task allocation, one driver registration, one waker bench reservation at a time, and zero threads.

Ten thousand connections, zero new threads

Start a few thousand clients against this server and watch what changes: almost nothing. Each connection costs one task, a heap allocation of a few hundred bytes holding a pinned state machine, and nothing else. No thread is created, no 8 MB stack is reserved, no kernel wait queue gains a sleeper. The arithmetic that sank thread-per-connection servers in Part 1 never even begins, because the thing that would have been parked, a whole thread, was replaced by a parked state machine and one waker on a bench.

Where do all those tasks run? On the same handful of workers that booted before your first line. Idle connections are invisible: a task blocked in read sits in no run queue at all, only in the driver's waiter lists. Active connections take turns, and each gets a budget of polls before being re-queued at the back, so one client streaming data at full speed cannot starve the others. When a packet arrives for any connection, the wake path is always the same: epoll, token, waker, queue, poll. The scheduler does not know or care that the task happens to be speaking TCP.

The one thread that is not busy is the main thread. After the accept loop's first iteration, it lives entirely inside accept().await, parked in block_on, waking only when the listener produces a connection. A common refinement is to spawn the accept loop itself as a task and let the main future do nothing but wait for a shutdown signal, which is exactly where we are heading.

Graceful shutdown

As written, the server runs until you kill it, and killing it is ungraceful by definition. The standard sketch races the accept loop against the keyboard interrupt:

use tokio::signal::ctrl_c;

#[tokio::main]
async fn main() -> std::io::Result<()> {
    let listener = TcpListener::bind("127.0.0.1:7878").await?;

    loop {
        tokio::select! {
            res = listener.accept() => {
                let (socket, _peer) = res?;
                tokio::spawn(echo(socket));
            }
            _ = ctrl_c() => break,
        }
    }

    println!("accept loop stopped; open connections continue");
    Ok(())
}

You know this macro from the cancellation chapter, so only the walkthrough-specific facts matter here. Both futures are polled together; when Ctrl-C lands, the signal future wins, the pending accept future is dropped mid-await, and the loop breaks. Two details make this loop safe. First, accept on a listener is cancellation-safe: it either handed over a connection or did not, so dropping it between polls loses nothing. Second, the branch futures are rebuilt every iteration, which is why the shutdown check never goes stale.

What happens to the connection tasks still running when the loop breaks? They are detached, and they keep running: the accept loop owns none of them. The program then returns, the runtime drops, and, as the boot page's ending showed, every task is stopped at its next yield point. For a real server you would hand each connection task a shutdown signal, a watch channel is the usual choice, and wait for the stragglers before returning; the tool for that waiting arrives on the next-but-one page.

The fully graceful shape, in words since the pattern is now familiar: create the watch channel before the accept loop and give every connection task a receiver. The connection loop races its read against rx.changed(), and on the shutdown notice it drains what it can, flushes its writes, and returns cleanly instead of being cut at a yield point. The main task, after Ctrl-C, waits for the connection count to reach zero before letting the runtime drop. Nothing in that design needs machinery you have not already seen; it is drivers, wakers, queues, and one channel all the way down.
