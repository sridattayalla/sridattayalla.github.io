Hello, Tokio: the boot sequence

Part 4 took the runtime apart while it stood still. That first page was the map: workers, queues, drivers, the pool for blocking work, all laid out in one picture. This part sits down in the user's chair, and it starts by running the film instead of studying the photograph. What actually happens, in order, between typing cargo run and seeing your first print? Which threads exist before your code runs? Where does your main execute? What dies when the program ends? You already know every part; this page is the assembly order.

What the attribute really is

Every Tokio program you have written so far began with one attribute. Here it is once more, next to what it expands to:

#[tokio::main]
async fn main() {
    println!("hello from inside a runtime");
}
// what the macro generates (trimmed to the interesting lines)
fn main() {
    use tokio::runtime::Builder;

    return Builder::new_multi_thread()
        .enable_all()                 // arm the I/O driver and the time driver
        .build()
        .expect("Failed building the Runtime")
        .block_on(async {
            println!("hello from inside a runtime");
        });
}

The macro is thin. Your async fn main becomes the body of an ordinary, synchronous main that does three things: build a runtime, hand it your main future, and call block_on, the parking trick you wrote by hand in Part 3. No magic survives the expansion; everything interesting happens inside build() and block_on(). So follow them in order.

One word in the expansion deserves a pause: enable_all. By default the builder ships a runtime with both drivers switched off; sockets and timers simply would not work, and any .await on one would hang forever. The attribute opts you into the full machine. When you construct a runtime by hand with Builder::new_multi_thread(), forgetting enable_all is the classic reward: a program that compiles, runs, and freezes at the first network call, because nobody is ever going to knock on the door.

The timeline

Before your first line runs

The process starts the way every process does, as one thread named main with an empty file descriptor table. Then build() goes to work, and by the time it returns, four things exist that did not exist before:

The I/O driver. One mio poller wrapped around a single epoll instance, which is itself just one more file descriptor. No sockets are registered with it yet; registration is lazy, on first use. The driver exists, armed, and empty.

The time driver. The timing wheel, all six levels of it, empty and ticking on driver turns. Building it cost no thread; it is a data structure, not a sleeper.

The workers. One OS thread per CPU core, all created at startup, each named tokio-rt-worker, each grabbing a private run queue with room for 256 tasks, a LIFO slot, and a tick counter. They enter their loops immediately, find nothing to run, and park inside the driver, exactly as the map in Part 4 promised. Your program has not executed one line of your code, and the machine is already idling at full readiness.

The blocking pool, on paper only. The blocking pool is configured but not created. Its threads are spawned on demand, retire after ten idle seconds, and stop at a cap of 512. If your program never calls spawn_blocking, not one of those threads is ever born.

Count the cast before curtain: the main thread plus one worker per core, an epoll instance, an empty wheel, three kinds of empty queues. That is the entire stage.

block_on: the main thread becomes an executor

Now block_on takes your main future, and something worth noticing happens: the main thread runs it itself. Your future is not boxed into a task, not pushed into any queue. The main thread becomes a single-future executor of exactly the design you built in Part 3's mini executor: poll the future; if it says Pending, park the thread; the waker handed down through every poll is the key that unparks it. The production runtime scales that pattern across workers, but for the root future, the original design is used verbatim.

The first poll runs eagerly, as every poll does. Your async main is a state machine, and the machine drives forward through your code until the first await that cannot be satisfied, parks, and hands the Pending upward. Only then does the main thread sleep, and only until a wake arrives.

Adoption: where your spawns go

The moment your main future calls tokio::spawn, the future is boxed into a task and pushed onto the global inject queue, because the caller, the main thread, is not a worker. Workers check that queue on a tuned cadence; one of them adopts the task, moving it into its local run queue, and from then on the task belongs to the scheduler at large: it runs on whichever worker picks it up, its wakes land in the LIFO slot or the local queue of whoever woke it, and it may migrate between workers mid-life. Tasks are not married to threads. You will see that with your own eyes in a moment.

Watch it boot

Run this little instrument, and the boot sequence becomes observable. It prints which thread each piece of your program ran on:

use std::time::Duration;

fn where_am_i() -> String {
    let t = std::thread::current();
    format!("{} {:?}", t.name().unwrap_or("?"), t.id())
}

#[tokio::main]
async fn main() {
    println!("[main] starts on   {}", where_am_i());

    let mut kids = Vec::new();
    for i in 0..4 {
        kids.push(tokio::spawn(async move {
            println!("[task {i}] first poll {}", where_am_i());
            tokio::time::sleep(Duration::from_millis(50)).await;
            println!("[task {i}] woke      {}", where_am_i());
        }));
    }

    for h in kids {
        h.await.unwrap();
    }
    println!("[main] ends on     {}", where_am_i());
}

On a four-core machine, one run printed this. Thread numbers and assignment order vary from run to run; the shapes do not:

[main] starts on   main ThreadId(1)
[task 0] first poll tokio-rt-worker ThreadId(2)
[task 1] first poll tokio-rt-worker ThreadId(4)
[task 2] first poll tokio-rt-worker ThreadId(3)
[task 3] first poll tokio-rt-worker ThreadId(5)
[task 0] woke      tokio-rt-worker ThreadId(3)
[task 1] woke      tokio-rt-worker ThreadId(2)
[task 3] woke      tokio-rt-worker ThreadId(5)
[task 2] woke      tokio-rt-worker ThreadId(4)
[main] ends on     main ThreadId(1)

Four facts are sitting in that output, and each one is a chapter of this book made visible:

  • The main future ran on the thread named main: block_on drove it personally, start to finish.
  • No spawned task ever ran on main. Workers adopted every one of them from the inject queue before it executed a single line.
  • Every task was polled, went to sleep, and woke on a thread named tokio-rt-worker, because workers are the only threads that poll tasks.
  • Task 0 started on ThreadId(2) and woke on ThreadId(3). Its timer fired in the time driver while the task sat in a queue, and a different worker picked it up. The task never moved in memory, being pinned in its allocation; only the thread holding it changed.

If you add a spawn_blocking call to the instrument, its closure will report a brand-new thread id and the same default name, tokio-rt-worker. The name covers every thread the runtime spawns by default; the fresh id is the pool arming itself on demand. Use Builder::thread_name_fn when you need to tell them apart in production logs.

How it ends

Your main future returns. block_on returns. main returns. Then the runtime value, living in the generated wrapper, drops, and shutdown runs three steps in order. Workers are told to stop: tasks keep running until they yield, then are dropped; nothing is guaranteed to finish. The blocking pool is joined: started blocking calls run until they return, and the thread that dropped the runtime waits for them, which is why shutdown_timeout exists for the impatient. Finally the threads exit and the process dies. Between the first print and the last, not one detail of that ending was visible from inside your code, and none of it needed to be.

That is the boot sequence. The machine assembles itself in a fixed order, adopts your work as you create it, and dismantles itself deterministically at the end. Next, keep the machine running and point it at the oldest program in networking: an echo server, awaited one line at a time.

In this chapter

  • #[tokio::main] expands to a synchronous main that builds a multi-thread runtime and calls block_on; nothing else survives the macro.
  • Before your code runs: one epoll instance, one timing wheel, and one worker thread per core, all created at startup; the blocking pool is configured but armed only on demand.
  • block_on drives your main future on the main thread itself, poll-park-wake, the Part 3 mini executor used verbatim; the root future is never a queued task.
  • Spawns from the main thread land in the inject queue and are adopted by workers; tasks migrate between workers, and the thread-name instrument makes all of it visible.
  • Shutdown drains workers (tasks stop at their next yield), joins the blocking pool, and exits; dropping tasks at yield points is the same cancellation you met at the end of Part 4.
