Pipelines: spawn and channels

The echo server gave you a shape: many independent tasks, no conversation between them. The combinators gave you the other extreme: many waits, one task. Most real programs live in between, as pipelines: stages of spawned work connected by channels, each stage free to await at its own pace. This page builds one small pipeline, three generators feeding a transform feeding a sink, and then stares at the two things that make pipelines behave: what a channel await really parks, and who is allowed to outlive whom.

The shape

The program

Stage one: the generators. Each one owns a clone of the pipe's sending end, so the pipe stays open as long as any generator lives. Note the explicit drop of the original sender right after the spawn loop; hold that thought for two sections.

use tokio::sync::{mpsc, JoinSet};

fn generator(id: u32) -> impl Iterator<Item = u32> {
    (0..4).map(move |i| id * 100 + i)
}

#[tokio::main]
async fn main() {
    let (raw_tx, mut raw_rx) = mpsc::channel(4);
    let mut set = JoinSet::new();

    for id in 1..=3u32 {
        let tx = raw_tx.clone();
        set.spawn(async move {
            for item in generator(id) {
                tx.send(item).await.expect("pipe broke");
            }
        });
    }
    drop(raw_tx);

Stage two: the transform worker drains the raw pipe and feeds a second one, and the sink, running inline in the main future, prints whatever arrives. When the pipe drains, the joins settle:

    let (cooked_tx, mut cooked_rx) = mpsc::channel(4);
    set.spawn(async move {
        while let Some(item) = raw_rx.recv().await {
            cooked_tx.send(item * 10).await.expect("pipe broke");
        }
    });

    let mut count = 0u32;
    while let Some(item) = cooked_rx.recv().await {
        println!("sink received {item}");
        count += 1;
    }
    println!("sink received {count} items total");

    while let Some(res) = set.join_next().await {
        res.unwrap();
    }
}

Three generators, four items each, twelve lines of output in an order that shuffles run to run, and always the same last line:

sink received 1000
sink received 2000
sink received 1010
sink received 3000
... (interleave varies run to run)
sink received 12 items total

What a channel await parks

Look at tx.send(item).await the way you looked at socket.read. The send future's first poll checks the buffer. A slot is free, so the value lands in it and the send returns Ready; if a receiver is parked waiting, the channel hands the value over directly and fires that receiver's waker instead. Only when the buffer is full does the interesting branch run: the sending task parks, its state machine frozen mid-send, sitting in no run queue at all, registered with the channel itself. The next recv() that frees a slot fires the parked sender's waker, a worker adopts the task, and the send completes. recv().await on an empty pipe is the mirror image.

Notice what did not appear in that paragraph: no I/O driver, no timing wheel, no kernel object anywhere. Every wakeup on a channel is caused by another task calling send or recv on the same channel. Sockets are woken by packets, sleeps by deadlines, and channels by your own program; the parked task costs the same nothing in all three cases. That is the whole trick of pipelines: stages connected by waits that never spin, never allocate threads, and never wake anybody without a reason.

Closing the pipe

A recv() loop has to end somehow, and the mechanism is ownership. The receiver returns None only when every sender clone has been dropped: not one left in a variable, not one captured by a task that is still running. That is why the program drops raw_tx immediately after spawning; from that moment the pipe's lifetime is exactly the union of the generator tasks' lifetimes. Each generator finishes its four sends, returns, and drops its clone on the way out. The last one to leave closes the pipe, the transform's recv() returns None, its loop ends, and its own sender clone drops, which closes the second pipe under the sink. The cascade closes the whole program from the inside, and the sink loop falls out by itself. The expect("pipe broke") arms the other direction: if the receiving end is ever dropped first, sends fail immediately instead of parking forever.

Backpressure, watched live

The buffer is not an optimization; it is a backpressure device, and you can watch it work. Here is the minimal experiment: a buffer of two slots, a producer sending six items, a consumer that sleeps for a hundred milliseconds between receives, and a timestamp on every print:

use std::time::{Duration, Instant};
use tokio::sync::mpsc;
use tokio::time::sleep;

fn stamp(t0: Instant) -> String {
    format!("[{:>5}ms]", t0.elapsed().as_millis())
}

#[tokio::main]
async fn main() {
    let t0 = Instant::now();
    let (tx, mut rx) = mpsc::channel(2);

    tokio::spawn(async move {
        for i in 1..=6 {
            tx.send(i).await.unwrap();
            println!("{} sent {i}", stamp(t0));
        }
    });

    while let Some(i) = rx.recv().await {
        println!("{} got {i}", stamp(t0));
        sleep(Duration::from_millis(100)).await;
    }
    println!("{} consumer done", stamp(t0));
}

And the output, stable across runs in everything but the print order inside a single tick:

[    0ms] got 1
[    0ms] sent 1
[    0ms] sent 2
[    0ms] sent 3
[  100ms] got 2
[  100ms] sent 4
[  200ms] got 3
[  200ms] sent 5
[  300ms] got 4
[  300ms] sent 6
[  400ms] got 5
[  500ms] got 6
[  600ms] consumer done

Read the shape of that log. At time zero, three items moved: one into the consumer's hands and two into the buffer, exactly the buffer's capacity plus the item in flight. Then the producer stopped mid-send on item four, parked as a state machine, and from that point on it emitted exactly one item per consumer wake. Nobody wrote a rate limiter. The producer ran as fast as the pipe allowed and no faster, because a full buffer turns send().await into a park, and the only thing that empties a buffer is the consumer. Swap the sleep for a database call and you have the standard shape of a service under load: fast stage upstream, slow stage downstream, bounded memory in between, all from one number in channel(...).

One consumer: fan-in, fan-out

The pipeline above already used fan-in: three generators shared one pipe, and mpsc is multi-producer, single-consumer by name and by enforcement. Many senders are free; the receiving end is single-owner, full stop, and the type system checks it. That one rule decides pipeline topology. Fan-in needs nothing but cloned senders. Fan-out, one pipe feeding many workers, has to be built, and the standard build is a dispatcher task: it owns the single receiving end and a table of per-worker channels:

let (dispatch_tx, mut dispatch_rx) = mpsc::channel(4);
let mut workers = Vec::new();

for _ in 0..4 {
    let (tx, mut rx) = mpsc::channel(4);
    workers.push(tx);
    set.spawn(async move {
        while let Some(job) = rx.recv().await {
            handle(job).await;
        }
    });
}

set.spawn(async move {
    let mut next = 0;
    while let Some(job) = dispatch_rx.recv().await {
        workers[next].send(job).await.expect("worker gone");
        next = (next + 1) % workers.len();
    }
});

Jobs walk round-robin to whichever worker pipe is next. When a worker is slow, its private buffer fills, and the dispatcher's send().await parks until that worker catches up; backpressure automatically becomes load balancing. The round-robin is naive, and that is fine more often than you would think, because the parked-send rule already keeps fast workers fed and slow workers from hoarding. When you need true least-loaded routing or shared work, you have the machinery to build it: one queue, N receivers, and the synchronization primitives from the sync chapter.

Structured concurrency

There is one loose end in the program, and it is the most important idea on the page. Every task in the pipeline was spawned into a JoinSet, and the main future did not exit until it had drained that set with join_next. That pattern has a name: structured concurrency. Concurrent work is launched inside a scope that owns it; the scope does not return until every child has finished or been cancelled; and no child can outlive the code that started it. It is structured control flow, a function cannot return while its callees still run, lifted from calls to tasks. The opposite is what you already know from dropped JoinHandles: a spawned task nobody waits on is detached, running on past the end of the function that created it, free to be cut down at an arbitrary yield point when the runtime drops.

JoinSet is the owner that makes the discipline cheap. It tracks every child you spawn into it. join_next() yields each child's outcome as it completes, in completion order rather than spawn order, and the outcome is a Result: if a child panicked, you receive a JoinError at the join point instead of the panic unwinding into whichever task happened to be polling. The pipeline's res.unwrap() is the strictest policy, crash the parent on any child's failure; if let Err(e) logging and continuing is one line away. And the closing bracket is free: dropping a JoinSet immediately aborts every child still in it, so early returns, error paths, and panics in the parent all clean up their children by ownership, the same way a Vec drops its elements. No child leaks past the scope, no scope exits over a running child, and the while let Some(res) = set.join_next().await loop is the entire ceremony required.

Put together, the pipeline program never mentions the scheduler, the drivers, or a single waker, and yet every line runs on exactly that machinery: spawned stages adopted by workers, channel waits parked as state machines, wakes caused by sibling tasks, and a scope that owns its children. You wrote a concurrent program by writing ordinary code with five special words in it, and the runtime did the rest. In this chapter

  • A pipeline is spawned stages connected by bounded channels; each stage awaits at its own pace and parks as a state machine when its neighbor is not ready.
  • Channel wakeups come from other tasks, not from the kernel: send and recv complete into free buffer slots or park until a sibling empties or fills one.
  • A pipe closes by ownership: recv returns None when the last sender clone drops, which cascades shutdown through every downstream stage.
  • The buffer is backpressure: a producer outruns its consumer by exactly the buffer size plus one item, then locks to the consumer's pace with no code written to enforce it.
  • mpsc is single-consumer: fan-in is free, fan-out needs a dispatcher, and a dispatcher's parked send is a load balancer.
  • Structured concurrency: a JoinSet owns its children, delivers panics as JoinError at the join point, and aborts the rest on drop; scopes outlive tasks, never the reverse.
