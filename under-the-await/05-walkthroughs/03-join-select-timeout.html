join!, select!, timeout

Spawning is not the only way to run things at once. Tokio ships three combinators that combine futures inside the task you are already in: one waits for everything, one waits for whichever comes first, and one puts a clock on any of them. None of the three creates a task, touches a queue, or asks anything of the scheduler. They are pure future algebra, which makes them the cheapest concurrency you will ever write. This page runs each one with print statements inside, so you can watch the poll order with your own eyes.

join!: everything, in one task

join! awaits a fixed set of futures to completion and returns all of their outputs as a tuple. It builds a single future that, on every poll, drives each child in turn until the child returns Pending, and finishes only when the last child has returned Ready. One task, many waits: concurrency without parallelism, and without Send bounds, because nothing ever leaves the task.

Here is the instrumented version, with a print before and after each sleep:

use std::time::Duration;
use tokio::time::sleep;

async fn step(name: &str, ms: u64) -> String {
    println!("{name}: start");
    sleep(Duration::from_millis(ms)).await;
    println!("{name}: done");
    format!("{name}!")
}

#[tokio::main]
async fn main() {
    let (a, b) = tokio::join!(step("a", 10), step("b", 30));
    println!("join! returned ({a}, {b})");
}

And the output, on one thread, every time:

a: start
b: start
a: done
b: done
join! returned (a!, b!)

Read that output as a poll trace. The first poll of the joined future drove child a, which printed its start and parked in the timing wheel; then, still inside the same poll, it drove child b, which did the same. Two sleeps armed concurrently, one poll, no queue. When the shorter deadline fired, the wheel woke the whole joined future; the second poll resumed a past its await, collected its output, re-polled b, found it still sleeping, and stopped. The third poll, at the later deadline, finished b and let join! return. Total elapsed time tracks the longest child, not the sum, and the whole thing ran on the main thread, driven by block_on, never touching a worker.

What does the macro actually build? The same thing every .await builds, one level up. You saw how the compiler turns an async fn into a state machine; a combinator is the manual, library-written version of that idea. join! expands to a generated enum whose variants are “a is pending, b is pending”, “a is done, b is pending”, and so on, plus storage for each child future and its eventual output. Its poll matches on that state, polls whichever children are still alive, records the ones that finish, and returns Ready only from the last remaining state. There is no hidden task, no queue entry, no scheduler involvement; the joined future is just a bigger state machine that your caller parks and wakes as one unit. select! builds the same kind of enum with a race policy instead of a completion policy, which is why both macros feel free to accept references and non-Send values: nothing ever crosses a thread.

One practical footnote before moving on: join! wants every child to succeed and has no way to say otherwise. If a child returns a Result and you want the first error to finish the whole race, reach for try_join!, the fallible sibling that short-circuits on Err and drops the still-pending siblings exactly like a losing select! branch would. The success side returns the tuple of outputs; the failure side returns the first error alone. In the request handler idiom, fan out to the cache, the database, and the rate limiter with try_join!, and one failing dependency fails the request while the others are dropped, not leaked and not awaited to completion.

select!: the first to finish

You have already met select! as the place where cancellation bites, and that page owns the rules: poll the branches, first Ready wins, the losers are dropped mid-await, order is randomized unless you ask for biased. Here is the same macro under the tracer, so you can see the drop happen:

use std::time::Duration;
use tokio::time::sleep;

#[tokio::main]
async fn main() {
    tokio::select! {
        _ = sleep(Duration::from_millis(10)) => println!("short timer won"),
        _ = sleep(Duration::from_millis(30)) => println!("long timer won"),
    }
    println!("select! finished");
}
short timer won
select! finished

One line of output for two armed timers. The first poll armed both sleeps in the wheel, just like join! did. The shorter deadline fired first, its branch returned Ready, its handler ran, and then select! dropped the other branch's sleep future where it stood. Dropping a sleep removes its entry from the wheel in constant time; the longer timer will never fire, because the thing that was waiting for it no longer exists. Cancel is drop, once again, now seen from the combinator's side.

timeout: a clock on anything

timeout races any future against a freshly armed timer and returns a Result: Ok with the future's output if it finished in time, Err(Elapsed) if the clock won. It is select! against the time driver wrapped in one library call:

use std::time::Duration;
use tokio::time::{sleep, timeout};

async fn slow_answer() -> u32 {
    sleep(Duration::from_secs(1)).await;
    42
}

#[tokio::main]
async fn main() {
    match timeout(Duration::from_millis(50), slow_answer()).await {
        Ok(answer) => println!("got {answer}"),
        Err(_too_slow) => println!("gave up waiting"),
    }
}
gave up waiting

The walkthrough facts: the fifty-millisecond limit is armed at the moment timeout is called, the inner future runs untouched until the race resolves, and when the clock wins, the inner future is dropped where it stood. Here that costs nothing; when the inner future is a half-finished operation, it costs exactly what the cancellation chapter warned you about. One shape note from that page, worth repeating because loops amplify it: every call to timeout arms a fresh clock. For “each attempt gets its own limit” that is right; for “the whole job stops at a wall” use one absolute deadline and race against sleep_until, or the loop can drift past your wall one retry at a time.

Concurrency versus parallelism, made visible

All three combinators so far ran on one thread, and that is the point: they provide concurrency, the interleaving of waits, without parallelism, the simultaneous use of multiple cores. The difference becomes visible the moment you print thread names. First, the joined version:

use std::time::Duration;
use tokio::time::sleep;

fn here() -> String {
    std::thread::current().name().unwrap_or("?").to_string()
}

#[tokio::main]
async fn main() {
    tokio::join!(
        sleep(Duration::from_millis(20)),
        sleep(Duration::from_millis(20)),
        sleep(Duration::from_millis(20)),
    );
    println!("joined three sleeps on {}/all one task", here());
}

All three children live inside the main future, so they run on the main thread, interleaved by polls, and the three sleeps finish in roughly the time of one. Now the spawned version:

#[tokio::main]
async fn main() {
    let mut handles = Vec::new();
    for _ in 0..3 {
        handles.push(tokio::spawn(async {
            sleep(Duration::from_millis(20)).await;
            here()
        }));
    }
    for h in handles {
        println!("slept on {}", h.await.unwrap());
    }
}

slept on tokio-rt-worker
slept on tokio-rt-worker

Same wall time, different world. Those three sleeps ran as three tasks adopted from the inject queue by different workers, and on a machine with a spare core or two they were genuinely idle at the same instant on different threads. Nothing about the output proves it, because sleeping is not work; replace the sleeps with tight computation and the joined version takes the sum of the three runtimes while the spawned version takes the longest, cores permitting.

So when to use which? join! and select! for batching inside a task: a handful of waits that belong to one logical step, benefit from sharing locals, and cost nothing to create. spawn for independent units of work that the scheduler should spread across workers: long-lived loops, connection handlers, anything that deserves its own budget slice and its own failure isolation. A useful default: batch with combinators, structure with tasks, and reach for tasks the moment work outlives the await that started it.

In this chapter

  • join! drives a fixed set of futures to completion inside one task: each poll advances every child until Pending, and the join resolves when the slowest child does.
  • select! polls branches together, the first Ready wins, and the losing branch futures are dropped mid-await; a dropped sleep quietly removes itself from the wheel.
  • timeout races a future against a freshly armed timer and drops the future if the clock wins; use absolute deadlines when a whole loop must respect one wall.
  • Combinators give concurrency on one thread; spawn gives parallelism across workers; print thread names and the difference stops being abstract.
  • Rule of thumb: batch with join! and select!, structure with tasks; the combinators cost nothing to create and impose no Send bounds.
